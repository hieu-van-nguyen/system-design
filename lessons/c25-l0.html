Requirements & Storage Estimation

lesson
⏱ 12 min
📖 Chapter 25, Lesson 1

🎯 Learning Objectives

  • Scope functional requirements for tweet search — keyword/phrase/hashtag/user search with relevance+recency ranking and near-real-time indexing — distinct from a general web crawler-based search engine
  • Derive read and write QPS from Twitter-scale numbers (250M DAU, 500M tweets/day, 2B searches/day) including peak multipliers
  • Estimate inverted index storage size (raw corpus vs. compressed postings) and size the hot in-memory tier vs. the cold on-disk tier
  • Justify an eventual-consistency, AP-leaning design given the latency and availability targets of a search system

Requirements & Storage Estimation

1. Clarifying Questions

"Search" is deceptively broad. Twitter search is not a general web search engine — the corpus is short, high-velocity, structured posts rather than crawled web pages. Ask these before drawing anything:

QuestionWhy It MattersTypical Answer
Full-text search over ALL tweets ever posted, or recent tweets only?Determines index retention. Twitter's default search is recency-biased; "Advanced Search" covers full history. Retention drives storage cost directly.Full 2-year history is searchable, but ranking and caching are biased toward the last 30 days
Do we need exact phrase / quoted-string search?Phrase queries require storing term positions in the index (2–4× larger postings). Keyword-OR queries only need doc IDs.Yes — quoted phrase search is a common feature
Is ranking pure relevance, or relevance blended with recency/engagement?Classic IR scoring (TF-IDF/BM25) alone would surface a 3-year-old viral tweet over breaking news. Twitter search must weight recency and engagement heavily.Blend: BM25 relevance score + exponential recency decay + engagement (likes/retweets)
How fresh must results be after a tweet is posted?Drives whether indexing can be a batch job (minutes) or must be a streaming pipeline (seconds).New tweets searchable within ~1–5 seconds
Do deleted or moderated tweets need to disappear from search immediately?A deleted tweet still appearing in search results after removal is a privacy/compliance incident, not just a staleness quirk.Yes — deletion must be reflected within ~1 second, even if physical index cleanup lags
What's the read:write ratio?A search-heavy workload justifies optimizing for query fan-out and caching over raw write throughput.~4:1 — searches significantly outnumber tweets posted

2. Functional Requirements

  • Keyword / phrase search: Match one or more terms, including quoted exact phrases, across tweet text.
  • Structured filters: from:handle, #hashtag, since:/until: date range, language.
  • Relevance + recency ranking: Results are not purely chronological (like a timeline) nor purely relevance-scored (like classic web search) — they blend both, plus engagement signals.
  • Near-real-time indexing: A tweet must become searchable within a few seconds of being posted.
  • Deletion propagation: Deleted/moderated tweets must stop appearing in results almost immediately, even before the index is physically compacted.
  • Pagination: Cursor-based pagination through result pages, not offset-based (offsets drift under a constantly-growing corpus).

Out of scope for this chapter: autocomplete/typeahead, semantic/vector search, image/media content search — each is its own design problem.

4. Traffic Estimation (QPS)

Assume Twitter-like scale: 250M daily active users, 500M tweets posted/day, 2B searches/day (people search far more than they post).


// WRITE PATH (tweet ingestion → indexing pipeline)
500,000,000 tweets/day ÷ 86,400 s/day  ≈ 5,787 tweets/sec (avg)
Peak (3× avg, breaking news)           ≈ 17,361 tweets/sec

// READ PATH (search queries)
2,000,000,000 searches/day ÷ 86,400 s/day ≈ 23,148 searches/sec (avg)
Peak (3× avg)                              ≈ 69,444 searches/sec

// Read:Write ratio ≈ 70,000 : 17,000 ≈ 4:1
// → optimize for read fan-out and caching; writes are the smaller problem
💡 Note the asymmetry with hot keys: the 3× multiplier above describes overall system peak. A single trending hashtag can see 10–50× its normal query volume within minutes — that's a hot-partition problem, not a global-capacity problem, and it's addressed by sharding strategy (Lesson 2), not by over-provisioning the whole cluster.

5. Storage Estimation

Average tweet: ~100 bytes of text (well under the 280-char cap) + ~200 bytes of metadata (tweet_id, user_id, timestamp, reply/quote refs, hashtag/mention arrays, language tag) ≈ 300 bytes raw per tweet. Media is stored separately in blob storage/CDN and is out of scope here.


// RAW CORPUS (2-year retention)
500M tweets/day × 300 bytes            = 150 GB/day
150 GB/day × 730 days (2 yr)           ≈ 110 TB raw text + metadata

// TOTAL DOCUMENTS TO INDEX (2-year corpus)
500M tweets/day × 730 days             = 365 billion tweets

// INVERTED INDEX SIZE (compressed postings — see Lesson 2 for compression scheme)
~18 indexed terms/tweet (post-tokenization, incl. hashtags/mentions)
~4 bytes/posting (delta-encoded doc ID + varint + position, compressed)
365B tweets × 18 terms × 4 bytes       ≈ 26.3 TB compressed index (single copy)

// WITH 3× REPLICATION (fault tolerance — Lesson 3)
26.3 TB × 3                            ≈ 79 TB total physical index storage

// HOT TIER — last 30 days (most search traffic is recency-biased)
500M/day × 30 days                     = 15 billion tweets
15B × 18 × 4 bytes                     ≈ 1.08 TB (single copy) → ~3.2 TB w/ 3× replication
// Fits comfortably in memory across a modest cluster (~30–40 nodes, 96GB RAM each)
TierData AgeStorage MediumQuery Volume Served
HotLast 30 daysIn-memory (RAM-resident index segments)~90% of searches (recency-biased)
Warm30 days – 6 monthsSSD-backed~8% of searches
Cold6 months – 2 yearsSSD/object storage, larger merged segments~2% of searches (advanced search, date-ranged)

Key Takeaways

  • This is not web search: short, structured, high-velocity documents with a recency-biased ranking function, not a crawled corpus with PageRank-style relevance.
  • Reads dominate writes ~4:1 — 70K peak searches/sec vs. 17K peak tweets/sec. Design for read fan-out and caching first.
  • The index is ~24% the size of the raw corpus (26.3TB vs. 110TB) thanks to delta encoding and varint compression of posting lists.
  • Hot/warm/cold tiering matters more than total size: the last 30 days (1TB) must be memory-resident; the other 25TB can live on cheaper, slower storage.
  • Eventual consistency is acceptable for new tweets, but not for deletions — moderation takedowns need a fast path, addressed in Lesson 3.

Interview Tips

  • State the recency-vs-relevance tension explicitly: "Pure BM25 relevance would surface old viral tweets over breaking news — I'll blend relevance with a recency decay and engagement signal." This is the single most distinguishing insight for this problem.
  • Do the arithmetic out loud: tweets/day → tweets/sec → peak QPS → bytes/tweet → total corpus size → compressed index size. Interviewers are grading the process, not just the final number.
  • Call out the hot-key problem early: a trending hashtag isn't a "the whole system got 3× busier" problem — it's a single-partition problem, which foreshadows the sharding deep dive and shows systems-level thinking.
  • Separate "index" from "source of truth": the index is a derived, rebuildable projection over the durably-stored tweet corpus — this framing pays off directly in the fault-tolerance discussion.
