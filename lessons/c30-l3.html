🎯 Learning Objectives

  • Design the queue mechanics: signed entry tokens and a Redis sorted-set position tracker

Deep Dive — Waiting Room & Flash Sale

Per Lesson 1, ~500,000 requests/sec can arrive for 50,000 seats. Lesson 3's lock-plus-DB mechanism keeps that traffic correct, but the reservation service still can't usefully process 500K requests/sec of real DB work. The waiting room's job is to solve a different problem: not correctness, but admission control — controlling the rate at which traffic is even allowed to reach the reservation path.

1. Why a Queue: Admission Control, Not a UI Feature

It's tempting to treat the waiting room as cosmetic ("show people a spinner so they don't get mad"). Its real function is rate-matching:

Measured reservation-service capacity: ~5,000 holdSeat() attempts/sec
                                        it can process correctly end-to-end
Incoming demand at on-sale moment:      ~500,000 req/sec

Without admission control: 100x overload hits the reservation service
  directly → Lesson 3's Redis lock still protects correctness, but response
  latency degrades for everyone, including the ~5,000/sec who could have
  been served fine.

With admission control: queue absorbs the burst, releases into the
  reservation service at ~5,000/sec — its actual measured throughput.
💡 Interview signal: Framing the queue's admit rate as "the reservation service's measured throughput," not an arbitrary number, shows you understand the waiting room as a capacity-matching mechanism — the same idea as backpressure in a streaming pipeline, applied at the user-request level.

2. Queue Mechanics

1. User hits the on-sale page → assigned a position:
     ZADD waiting_room:{eventId} {arrival_timestamp} {userId}   // Redis sorted set
2. Client polls (or holds an SSE connection) for its position:
     ZRANK waiting_room:{eventId} {userId}  → "you are #48,203"
3. Background admitter, running at the reservation service's safe rate:
     every 200ms: pop next 1,000 users off the sorted set (5,000/sec)
     → issue each a signed, short-lived entry token (JWT, ~2 min TTL)
4. Client presents the entry token to the reservation service
     → Reservation Service verifies signature + TTL, then proceeds to
       Lesson 2's normal seat-selection/hold flow

The sorted set gives O(log N) position tracking for millions of waiting users cheaply, and the signed token means the reservation service can verify "this request was legitimately admitted" without a database round trip or a call back to the queue service on every request.

3. FIFO vs. Randomized Lottery Admission

Admission orderTradeoff
FIFO (first arrival, first admitted)Feels fair to humans, but rewards whoever's script/bot hits the page microseconds earlier — advantages automated traffic over real users
Randomized lottery (all arrivals within a short window get shuffled before admission)Removes the reward for being fractions of a millisecond faster, which is specifically what bots optimize for — arriving first no longer guarantees admission first

A practical middle ground: batch arrivals into short windows (e.g., 1 second), randomize order within each batch, then admit batches in arrival order. This keeps a coarse sense of "earlier is better" for real users while eliminating the sub-millisecond bot advantage that strict FIFO rewards.

💡 Interview signal: Naming bots explicitly as the reason to avoid strict FIFO — rather than assuming all traffic is a real human clicking a button — reflects the actual adversarial nature of flash-sale traffic, which interviewers who've worked on this kind of system will specifically probe for.

4. Putting It Together: A Flash Sale End-to-End

1. On-sale time hits → 10M users land on the event page
2. Waiting Room admits users at ~5,000/sec (batched, randomized within
   each 1s window), issuing signed entry tokens
3. Admitted user → Reservation Service: holdSeat() protected by Lesson 3's
   Redis-lock-filter + DB-transaction-source-of-truth
4. User completes payment within the hold TTL (Lesson 1/2) → BOOKED
5. Users still waiting see a live position estimate; ~9.95M of the
   original 10M eventually see "sold out" — by design, not failure
   (per Lesson 1's contention ratio)

Key Takeaways

  • The waiting room performs admission control: it matches incoming request rate to the reservation service's actual measured processing capacity, not to how fast a spinner "feels"
  • A Redis sorted set gives cheap position tracking; signed, short-lived entry tokens let admitted requests skip a queue-service round trip
  • Strict FIFO admission unintentionally rewards bots; batching arrivals and randomizing within each batch removes the sub-millisecond advantage automation has over humans
  • The waiting room and the lock/DB mechanism from Lesson 3 solve different problems — capacity matching vs. correctness — and both are necessary

Interview Tips

  • Justify the admit rate with a number (measured downstream throughput), not "as fast as feels reasonable"
  • Bring up bots unprompted when discussing queue ordering — it's the detail that separates a surface-level answer from one grounded in how real flash sales are attacked
  • Keep the waiting room and the concurrency-control mechanism (Lesson 3) conceptually separate when explaining the design — conflating "queueing" with "locking" is a common confusion
  • Acknowledge upfront that the vast majority of waiting users will not get a seat, and that communicating this clearly is part of the design, not a UX afterthought
