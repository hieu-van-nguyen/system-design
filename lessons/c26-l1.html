High-Level Design & URL Frontier

Per Lesson 1's numbers: ~386 pages/sec average, ~1,157 peak, with a discovered-URL universe (~10B) an order of magnitude larger than the crawled set (~1B/month). The architecture has to move URLs through a pipeline without ever hammering one host, losing frontier state, or re-fetching the same content twice.

1. End-to-End Pipeline

┌──────────┐    ┌───────────────┐    ┌─────────┐    ┌────────┐    ┌───────────┐
│  Seed    │───▶│  URL Frontier │───▶│ Fetcher │───▶│ Parser │───▶│ URL Filter │
│  URLs    │    │ (front/back Q)│    │  pool   │    │        │    │ (dedup +   │
└──────────┘    └───────▲───────┘    └────┬────┘    └───┬────┘    │  robots)   │
                        │                 │             │         └─────┬─────┘
                        │            DNS Resolver   Content Store       │
                        │            (cached)      (raw HTML blob)      │
                        └─────────────────────── new outbound links ────┘

Each stage is an independently scalable service, connected by queues so a slow fetcher fleet never blocks link discovery and a burst of new URLs never overwhelms the fetchers directly.

2. The URL Frontier (Mercator design)

The frontier has two competing jobs: (a) surface high-priority URLs first, and (b) never issue two requests to the same host back-to-back. A single priority queue can't do both — a burst of URLs from one prolific host would monopolize the top of the queue. The standard solution (used by Mercator, the crawler design this pattern is named after) splits the frontier into two queue layers:

                    ┌─────────────┐
  new URL ─────────▶│ Prioritizer │  assigns priority 1..F based on
                    └──────┬──────┘  change-frequency estimate / PageRank-ish score
                           ▼
                 ┌───────────────────┐
                 │ Front Queues F1..Fn │  one per priority level (biased-random or
                 │  (priority order)   │  weighted round-robin select — high-priority
                 └──────────┬─────────┘  queues drained more often, never starved)
                            ▼
                 ┌────────────────────┐
                 │  Host-to-Queue Map  │  hash(host) → back queue Bk
                 └──────────┬─────────┘
                            ▼
                 ┌────────────────────┐      ┌─────────────────────────┐
                 │ Back Queues B1..Bm  │◀────▶│ Ready-Time Min-Heap      │
                 │ (1 host per queue,  │      │ keyed by nextFetchTime;  │
                 │  strict FIFO)       │      │ worker only pops a queue │
                 └──────────┬─────────┘      │ whose time has arrived   │
                            ▼                └─────────────────────────┘
                        Fetcher pulls
                        from ready Bk
  • Front queues encode priority — how important/fresh a URL is (a news homepage vs. a rarely-linked blog post)
  • Back queues encode politeness — each back queue holds URLs for exactly one host (or a small host bucket), so draining it is naturally one-at-a-time per host
  • The ready-time heap is what actually enforces the delay: when a worker finishes fetching from host H, it computes nextFetchTime = now + max(politenessDelay, robotsCrawlDelay) and reinserts H's back queue into the heap at that time — not before
  • Number of back queues m is typically sized to be several times the fetcher worker pool so workers rarely block waiting for a ready host
💡 Interview signal: this two-layer split is the single most-tested detail in "design a web crawler." If you only remember one diagram from this lesson, remember this one.

3. DNS Resolution Caching

A synchronous DNS lookup takes tens to hundreds of milliseconds and many OS resolvers are not built for the request volume a crawler generates — at ~1,157 peak fetches/sec, naive DNS resolution alone would saturate typical resolver libraries and become the bottleneck. The fix: a dedicated, horizontally-scaled DNS resolver service in front of the fetcher pool, with an in-memory cache (TTL-bound by the record's own TTL) so repeat lookups to the same host are O(1) map reads instead of network round trips.

4. Fetcher Pool Sizing (Little's Law)

Little's Law: L = λ × W
  L = number of concurrent in-flight requests needed
  λ = arrival rate (throughput)
  W = average time a request spends in the system

Assume average fetch latency (connect + TLS + download) ≈ 300 ms = 0.3 s

At peak throughput (1,157 pages/sec):
  L = 1,157 × 0.3 ≈ 347 concurrent connections

Add ~30% headroom for slow hosts / retries / timeouts:
  347 × 1.3 ≈ 451 concurrent connections

→ Provision ~450-500 concurrent fetch slots, distributed across a fetcher
  fleet (e.g., 50 nodes × 10 connections each), independently autoscaled
  from the parser/filter stages.

5. Fetcher → Parser → Filter

  • Fetcher: issues the HTTP GET, respects timeouts (e.g., 5s connect / 10s total), follows redirects up to a bounded depth (avoid redirect loops), records HTTP status
  • Parser: extracts visible text + outbound <a href> links, normalizes relative URLs against the page's base URL, computes a content fingerprint (Lesson 4)
  • URL Filter: checks the URL-seen dedup structure, checks cached robots.txt rules, checks per-host/per-depth caps — only URLs that pass all three re-enter the Frontier via the Prioritizer

Key Takeaways

  • Split the frontier into front queues (priority) and back queues (one-host-per-queue, politeness) — a single priority queue cannot satisfy both goals
  • A ready-time min-heap is what actually enforces the per-host delay, decoupling it from overall system load
  • DNS resolution needs its own cached, horizontally-scaled service at this request volume — don't rely on default OS resolution
  • Little's Law turns a throughput target into a concrete worker-pool size: ~450-500 concurrent fetch slots at peak, per Lesson 1's estimates

Interview Tips

  • Draw the front-queue/back-queue split unprompted — it's the detail interviewers are listening for
  • Use Little's Law out loud when sizing any worker pool; it turns a guess into a derivation
  • Call out that the Prioritizer, Fetcher, and Parser scale independently — don't present this as one monolithic worker
  • If asked "what breaks first at 10× scale," point to the back-queue count and host-to-queue hashing, not the fetchers
