Tweet Storage — Cassandra Schema

Tweets are write-once, read-many, append-only (no UPDATE after post). Cassandra's LSM-tree is perfect for this access pattern.

-- All tweets: primary storage
CREATE TABLE tweets (
    tweet_id        BIGINT      PRIMARY KEY,    -- Snowflake ID (time-ordered)
    user_id         BIGINT      NOT NULL,
    content         TEXT,                       -- up to 280 chars (560 bytes max)
    reply_to_id     BIGINT,                     -- NULL if not a reply
    quote_tweet_id  BIGINT,                     -- NULL if not a quote-tweet
    is_retweet      BOOLEAN     DEFAULT FALSE,
    original_tweet_id BIGINT,                   -- populated if is_retweet=TRUE
    media_keys      LIST<TEXT>,                 -- CDN URLs for images/video
    hashtags        SET<TEXT>,                  -- extracted at write time for search
    mentions        SET<BIGINT>,                -- user_ids mentioned (@alice)
    lang            TEXT,                       -- detected language code
    is_deleted      BOOLEAN     DEFAULT FALSE,  -- soft-delete (GDPR + "unsend")
    created_at      TIMESTAMP,
    like_count      COUNTER,                    -- WARNING: Cassandra counters have quirks
    retweet_count   COUNTER
);
-- Note: Cassandra COUNTER is eventually consistent and can't be used in same table as regular cols.
-- In practice: tweet_id PK only; like/retweet counts stored in Redis → separate counts table.

-- User timeline: O(1) paginated tweet list per user
CREATE TABLE user_tweets (
    user_id     BIGINT,
    tweet_id    BIGINT,        -- Snowflake ID (time-ordered DESC)
    PRIMARY KEY (user_id, tweet_id)
) WITH CLUSTERING ORDER BY (tweet_id DESC);
-- Query: SELECT tweet_id FROM user_tweets WHERE user_id = ? LIMIT 50
-- Pagination: WHERE user_id = ? AND tweet_id < {cursor} LIMIT 50

-- Follow graph (dual-table for O(1) both directions)
CREATE TABLE following (
    follower_id     BIGINT,
    followee_id     BIGINT,
    followed_at     TIMESTAMP,
    PRIMARY KEY (follower_id, followee_id)
);
-- Query: "who does Alice follow?" → SELECT followee_id FROM following WHERE follower_id = alice

CREATE TABLE followers (
    followee_id     BIGINT,
    follower_id     BIGINT,
    followed_at     TIMESTAMP,
    PRIMARY KEY (followee_id, follower_id)
);
-- Query: "who follows Alice?" → SELECT follower_id FROM followers WHERE followee_id = alice
-- Fan-out: SELECT follower_id FROM followers WHERE followee_id = tweeter LIMIT 5000 (paginate)

Snowflake ID — Why Not UUID or Auto-Increment

Snowflake ID structure (64-bit integer):
  [63..22] = 41 bits = milliseconds since Jan 1, 2010
              → 69 years of unique timestamps
  [21..12] = 10 bits = datacenter_id (5 bits) + worker_id (5 bits)
              → 1,024 unique generators, no coordination
  [11..0]  = 12 bits = per-worker sequence
              → 4,096 tweets per millisecond per generator

Why NOT UUID v4 (random):
  ❌ 128 bits vs 64 bits = 2× storage in Cassandra index
  ❌ Random order = no time locality = B-tree/SSTable scattering
  ❌ Cannot use as Redis sorted-set score (too large; requires separate timestamp field)
  ❌ Cannot infer time from ID (useless as cursor)

Why NOT auto-increment (PostgreSQL SERIAL):
  ❌ Single point of failure: generator becomes bottleneck at 5,787 tweets/sec
  ❌ Distributed counters require coordination (2-phase commit) — kills write latency
  ❌ Sequential IDs are enumerable: bots can scrape tweet N, N+1, N+2...

Snowflake wins because:
  ✅ Time-ordered: tweet_id encodes timestamp → use as Redis sorted-set score directly
  ✅ Distributed: 1,024 generators, each maintains local sequence → no coordination
  ✅ Monotonic per generator: consecutive tweets from same generator are sequenced
  ✅ 64-bit: fits in BIGINT, 2× smaller than UUID, efficient B-tree index

Redis sorted-set example:
  ZADD timeline:alice 8675309000000001 8675309000000001
  Score = tweet_id = timestamp-embedded integer → no separate timestamp field needed
  ZREVRANGE timeline:alice 0 49 → 50 most recent tweet IDs, newest first

Tweet Post Flow — 5 Steps

Step 1 — Client POSTs tweet to API Gateway:
  POST /v1/tweets
  Body: { content: "Hello world! #hello", media_keys: [], client_tweet_id: "client-uuid-123" }
  Header: Authorization: Bearer {JWT}

Step 2 — Tweet Service processes and persists:
  a. Validate JWT → extract user_id
  b. Check client_tweet_id dedup: SELECT tweet_id FROM tweet_dedup WHERE client_tweet_id = 'client-uuid-123'
     → Miss: proceed. Hit: return existing tweet_id (retry-safe)
  c. Assign Snowflake tweet_id from local generator
  d. Extract hashtags (regex), detect language (langdetect)
  e. Cassandra BATCH WRITE:
     INSERT INTO tweets (tweet_id, user_id, content, ...) VALUES (...)
     INSERT INTO user_tweets (user_id, tweet_id) VALUES (...)
  f. Insert into Redis: ZADD timeline:{user_id} tweet_id tweet_id   ← user sees own tweet immediately
  g. Return 201: { tweet_id: 8675309, created_at: "..." }

Step 3 — Kafka publish (async, after response to user):
  Kafka producer: produce(topic='tweet-events', key=user_id, value={ tweet_id, user_id, follower_count })
  key=user_id ensures all tweets by same user go to same partition → ordered fan-out per user

Step 4 — Fan-out Workers consume Kafka:
  Consumer group "fanout-workers" reads tweet-events partitions
  For each tweet:
    - Fetch follower list: SELECT follower_id FROM followers WHERE followee_id = user_id (paginated, 5K/batch)
    - Filter: remove accounts with last_login < 90 days (zombie filter → saves ~30% writes)
    - Classify: if follower_count < 1M → ZADD to all follower timelines
                if follower_count ≥ 1M → skip ZADD (celebrity; handled at read time)
    - Redis pipeline: batch 100 ZADDs per round-trip → ~580 ZADDs/sec/worker for avg user
    - Trim each sorted set: ZREMRANGEBYRANK timeline:{follower_id} 0 -801 (keep top 800)

Step 5 — Search + Notification (parallel async):
  Elasticsearch indexer: index tweet_id, content, hashtags, user_id, created_at ← within 15s
  Notification Service: for each @mention and for direct replies → FCM/APNs push

Key Takeaways

  • User sees own tweet immediately (Step 2f: ZADD to own timeline before Kafka publish) — fan-out is async but own-timeline is synchronous
  • Cassandra dual-table for follow graph: following(follower PK, followee clustering) + followers(followee PK, follower clustering) — O(1) in both directions without scatter-gather
  • Snowflake ID = Redis score: tweet_id encodes timestamp as high bits → sort by tweet_id = sort by time; no separate score column needed in sorted set
  • Zombie filter saves 30%: 30% of Twitter followers are inactive/bots; filtering last_login < 90 days before fan-out saves 30M Redis writes on a celebrity tweet
  • 100 ZADDs per Redis pipeline: batching reduces round-trips from N to N÷100; critical when fanning out to 500K normal-user followers

Interview Tips

  • Describe the BATCH WRITE to Cassandra: tweets + user_tweets in one atomic batch — without it, a crash between the two writes leaves the user's timeline missing the tweet
  • When asked "what if fan-out falls behind?" → "Kafka's consumer lag metric triggers auto-scaling of fan-out workers; backlog is bounded by Kafka retention (7 days)"
  • Mention client_tweet_id for idempotency proactively: "network retry after timeout could double-post without a client-generated dedup key checked server-side"
  • For the follow graph, justify dual-table explicitly: "a single table (follower_id, followee_id) requires ALLOW FILTERING for one direction — that's a full table scan at 500B rows"
