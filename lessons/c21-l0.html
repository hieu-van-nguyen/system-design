Requirements & Estimations

lesson
⏱ 8 min
📖 Chapter 21, Lesson 1

🎯 Learning Objectives

  • Derive the 100:1 read-to-write ratio that defines Twitter's architecture as fundamentally read-optimized — and explain why that one number drives every major design decision
  • Calculate the celebrity fan-out math: why writing Katy Perry's tweet to 100M Redis sorted sets takes 33 minutes on a single node and what threshold forces a hybrid strategy
  • Size the timeline cache: 200M active users × 800 cached tweet IDs × 8 bytes = 1.28 TB Redis and explain why storing IDs only (not full tweet payloads) is the right choice
  • Identify the four hard problems unique to Twitter: celebrity fan-out, trending topic counting at 5,787 tweets/sec, near-real-time search, and like-count scalability

Step 1 — Clarifying Questions

Twitter has many features. Scope to the three that drive 80% of the architectural complexity: tweets, timelines, and search.

Do we need the algorithmic "For You" timeline or chronological only?Algorithmic timeline requires two-tower DNN ranking — a separate ML subsystem. Scope separately.Both: chronological (Following) + algorithmic (For You)

Step 4 — Back-of-Envelope Estimation

Tweet Write Throughput

DAU:                       200M
Tweets per user per day:     2.5  (most users read; fewer post)
Total tweets/day:            500M
Peak multiplier:               4×  (major live events: Super Bowl, World Cup, elections)

Average tweets/sec:          500M ÷ 86,400       =  5,787 tweets/sec
Peak tweets/sec:             5,787 × 4           = 23,148 tweets/sec

Timeline Read Throughput

DAU:                       200M
Timeline refreshes/user/day: 30   (check app ~every 30 minutes while awake)
Total timeline reads/day:    200M × 30           = 6B reads/day
Average timeline reads/sec:  6B ÷ 86,400         = 69,444 reads/sec
Peak timeline reads/sec:     69,444 × 8          = 555,556 reads/sec

Read:Write ratio:            555K ÷ 23K          ≈ 24:1 at peak (100:1 at average)
Conclusion: optimize aggressively for reads — pre-compute timelines, not compute at read time.

Celebrity Fan-Out Math — The Core Problem

Scenario: Katy Perry (100M followers) posts a tweet.

Write fan-out approach:
  For each of 100M followers: ZADD timeline:{follower_id} {tweet_id} {tweet_id}
  Redis ZADD throughput per node:    ~50,000 ops/sec
  Time on 1 Redis node:              100M ÷ 50,000         = 2,000 seconds = 33 minutes
  Time on 100 Redis nodes (parallel): 100M ÷ (50K × 100)  = 20 seconds — still unacceptable

  → Cannot use write fan-out for celebrities. Need hybrid strategy.

Threshold derivation:
  Acceptable fan-out time: 5 seconds
  Redis nodes dedicated to fan-out: 100
  Max followers for write fan-out: 5s × 50K × 100 nodes = 25M followers
  Twitter uses 1M as the practical threshold (conservative; leaves headroom for fan-out workers)

Timeline Cache Sizing

Active users with cached timeline: 200M
Tweet IDs cached per user:         800     (beyond 800 tweets deep, use is negligible)
Bytes per tweet ID:                  8     (Snowflake ID = 64-bit integer)
Total cache size:                  200M × 800 × 8B = 1.28 TB

Redis cost at $0.20/GB-hr:         1,280 GB × $0.20 = $256/hr = $2.24M/year
Savings: serves 555K reads/sec from RAM vs. 555K Cassandra reads at 10ms each
         → 555K × 10ms = 5,550 server-seconds of Cassandra work per second (impossible without cache)

Storage

Tweet row size:      ~1 KB (280-char content + metadata: user_id, timestamps, counts, reply refs)
Tweets/day:          500M
Storage/day:         500M × 1 KB         = 500 GB/day
5-year storage:      500 GB × 365 × 5   = 912.5 TB ≈ 1 PB
After 3× replication: 1 PB × 3          = 3 PB physical

Like counts (Redis, periodic flush to Cassandra):
  500M users × 10 likes/day = 5B likes/day = 57,870 likes/sec
  Redis INCR: trivial (1M+ INCR/sec per node)
  Cassandra flush: batched every 60s → 57,870 × 60 = 3.5M updates per flush interval (batched writes)

The Four Hard Problems

  1. Celebrity fan-out: Can't write Katy Perry's tweet to 100M Redis sorted sets in acceptable time → hybrid: write fan-out for < 1M followers; read-time merge for celebrities
  2. Trending topic counting: 5,787 unique hashtags/sec — exact counting (HashMap) needs 128 MB per window; Count-Min Sketch (4 MB) gives 0.003% error at 97% memory savings
  3. Near-real-time search: Tweets must appear in search within 15 seconds of posting — requires near-real-time Elasticsearch indexing, not the standard 1-minute refresh
  4. Like count scalability: 57,870 likes/sec overwhelms PostgreSQL (5K writes/sec) by 12×; Redis INCR + periodic Cassandra flush is the only viable approach

Key Takeaways

  • 100:1 read:write ratio — the single number that justifies pre-computed timeline caches, aggressive read replicas, and the entire fan-out architecture
  • 1.28 TB Redis timeline cache — serves 555K reads/sec from RAM; without it, 555K Cassandra reads/sec would need thousands of nodes
  • Celebrity threshold = 1M followers — derived from acceptable fan-out time (5s) ÷ 50K ZADD/sec × 100 Redis nodes = 25M safe; 1M is the practical conservative threshold
  • Count-Min Sketch — probabilistic structure for trending: 4 MB vs 128 MB exact; 0.003% error; must mention this when discussing trending

Interview Tips

  • State the 100:1 read:write ratio in the first 2 minutes — it signals you know the system's fundamental constraint
  • When asked about fan-out: do the Katy Perry math live — "100M followers × 50K ZADD/sec = 2,000 seconds = 33 minutes — that's why we need hybrid"
  • Mention zombie account filtering: "30% of Twitter followers are inactive/bots; filtering them reduces fan-out work by 30% — that's 30M fewer Redis writes for Katy Perry"
  • Don't say "use Redis for caching" generically — say "Redis sorted set keyed by user_id, score = Snowflake tweet_id, ZREVRANGE returns 50 tweet IDs in O(log N + 50)"
