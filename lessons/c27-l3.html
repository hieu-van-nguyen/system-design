Deep Dive — Feed Ranking Algorithm

Lessons 2-3 built the pipeline that gets candidate posts into (or reachable from) a user's feed. This lesson answers the last question: given a pool of candidate posts, in what order should they actually appear? Recency alone (the chronological fallback) ignores that a week-old post from a close friend is often more relevant than a stranger's post from five minutes ago.

1. From EdgeRank to Modern Ranking

Facebook's original public ranking formula, EdgeRank, scored each candidate post ("edge") as:

score(edge) = affinity(viewer, author) × weight(edge_type) × time_decay(edge)

  affinity    — how much the viewer historically interacts with this author
                (likes, comments, profile visits, message frequency)
  weight      — a static per-type weight (comment > share > like > view,
                photo/video > plain text, tunable per content type)
  time_decay  — score shrinks as post age increases, e.g. 1 / (age_hours + 2)

EdgeRank is simple, explainable, and cheap to compute — a good baseline and still a useful mental model. Production systems replace the hand-tuned weight/decay terms with a learned model, but the three-factor shape (relationship strength × content signal × recency) still holds.

2. Two-Stage Retrieval + Ranking

Scoring every candidate post with a full ML model is too expensive to run over hundreds of candidates per feed load at 350K reads/sec peak. Production ranking splits into two stages:

StageGoalCost
Retrieval (candidate generation)Cheaply narrow thousands of possible posts down to ~200-500 candidates (recent posts from friends/pages, celebrity fan-in merge from Lesson 3)Cheap heuristics/light model — must run in single-digit ms
RankingScore the smaller candidate set with a full model using rich features, return top N for the requested pageMore expensive per item, but bounded by the small candidate count
💡 Interview signal: Naming this as a two-stage funnel (cheap retrieval → expensive ranking on a small set) is the standard answer to "how would you rank without scoring every post in the system" — the same pattern shows up in search and recommendation systems generally.

3. Ranking Features & Feature Store

  • Viewer-author affinity — interaction history, precomputed and refreshed periodically, not recomputed per request
  • Content features — post type, has-media, early engagement velocity (likes/comments in the first N minutes)
  • Context features — time of day, device, viewer's recent session behavior
Ranking Service ──▶ Feature Store (low-latency KV lookup)
                        keys: (viewerId, authorId) → affinity features
                              (postId) → content + engagement-velocity features
                        // Precomputed offline/streaming, served online read-only —
                        // ranking-time work is feature lookup + model inference,
                        // not feature computation.

4. Real-Time vs. Batch Re-Ranking

ApproachTradeoff
Batch (precomputed ranking, refreshed periodically)Cheaper, but stale — misses a post that suddenly goes viral in the last few minutes
Real-time (rank at request time using freshest features)Captures viral/trending shifts immediately, but adds inference latency to every getFeed() call
Hybrid (used in practice)Batch-rank the bulk of candidates; blend in a small set of real-time signals (e.g., engagement velocity in the last 10 min) at request time

5. Latency Budget

Target: getFeed() p99 < 200ms (from Lesson 1's NFRs)

  Candidate retrieval (cache + celebrity fan-in merge)   ~20-40ms
  Feature store lookups (batched, parallel)              ~30-50ms
  Model inference on ~200-500 candidates                 ~50-80ms
  Serialization / network                                ~20-30ms
  ────────────────────────────────────────────────────────────────
  Total                                                  ~150-200ms  // fits the budget

// If inference cost grows, the retrieval stage's candidate count is the
// first lever to pull — fewer candidates into ranking, not a slower model.

Key Takeaways

  • EdgeRank's affinity × weight × time-decay shape is still the right mental model, even though production systems replace it with a learned model
  • Split ranking into cheap retrieval (narrow the candidate pool) and expensive ranking (score the small pool) — never full-model-score every post
  • Precompute features into a low-latency feature store; ranking time should be lookup + inference, not feature computation
  • Hybrid batch + real-time re-ranking captures viral content without paying real-time cost for every feature
  • When latency is tight, shrink the retrieval stage's candidate count before reaching for a faster/smaller ranking model

Interview Tips

  • Start from EdgeRank's three factors — it's a concrete, memorable baseline before you pivot to "in practice, this becomes a learned model"
  • Always propose the two-stage retrieval/ranking split — interviewers expect it as soon as candidate counts get large
  • Walk through a latency budget with rough per-stage numbers — it shows you're designing to the p99 target, not hand-waving "it's fast"
  • When asked "what if ranking gets too slow," reach for reducing candidates first, then model simplification — in that order
