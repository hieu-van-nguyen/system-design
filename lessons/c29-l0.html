Requirements & Estimations

Uber's backend matches riders requesting a trip with nearby available drivers, in real time, while both sides are constantly moving. Unlike Chapter 28's static-place search, the defining constraint here isn't read volume — it's that every active driver is continuously writing its location, and the system must match, price, and dispatch within seconds.

1. Clarifying Questions

QuestionWhy it matters
Ride-hailing only, or also deliveries (Uber Eats)?Scope to ride-hailing; deliveries share the dispatch pattern but add a different matching unit (orders, not passengers)
How often does a driver's app report its location?Directly sets the location-write rate — the dominant load on the system (computed below)
Do we need the globally-optimal driver match, or a "good enough, fast" match?Optimal matching (e.g., minimizing total wait time across all riders) doesn't scale to sub-second dispatch; assume nearest-available with a few candidates considered
Must the system prevent a driver from being double-booked?Strong consistency requirement on the "accept ride" step, even though location updates are eventually consistent (detailed in Lesson 3)
Is dynamic (surge) pricing in scope?Adds a real-time demand/supply pipeline (Lesson 4); assume yes

For this design: ride-hailing only, drivers report location every ~4 seconds, matching is "nearest available, fast" rather than globally optimal, ride acceptance must be strongly consistent (no double-booking), and surge pricing is in scope.

2. Functional Requirements

  • Riders can request a ride given a pickup and drop-off location and see an ETA/fare estimate
  • The system matches a ride request to a nearby available driver and dispatches an offer
  • Drivers continuously report their location while online/on-trip
  • Riders can track their assigned driver's location in real time during pickup and the trip
  • Fares reflect real-time supply/demand (surge multiplier) at request time
  • Both parties can cancel; the system re-matches or refunds appropriately

3. Non-Functional Requirements

AttributeTarget
LatencyMatch + dispatch within a few seconds of a ride request; location updates visible within ~1-2s
ConsistencyStrong consistency for ride acceptance (exactly one driver per ride); eventual consistency for location data
AvailabilityFavor availability for location ingestion — dropping a stale ping is fine, refusing to accept pings is not
ScalabilitySustain continuous location writes from millions of drivers plus bursty, geographically-concentrated ride-request spikes (surge events)
DurabilityTrip records (fare, route, timestamps) must be durable for billing/receipts; raw location pings do not need long-term durability
💡 Interview signal: Call out that consistency requirements differ within the same system — strongly consistent ride acceptance, eventually consistent location. Treating the whole system as one consistency level is a common shortcut that misses the double-booking requirement.

4. Traffic Estimation

Assumptions:
  Active drivers (online at once) = 1,000,000  (1M)
  Rider DAU                       = 100,000,000  (100M)
  Rides/day                       = 10,000,000  (10M)
  Driver location ping interval   = every 4 seconds while online

Ride requests/sec = 10M / 86,400              ≈ 116 rides/sec (avg)
Ride requests peak ≈ 116 * 3 (commute/event surge) ≈ 350 rides/sec (peak)

Driver location writes/sec = 1,000,000 drivers / 4 sec  = 250,000 writes/sec
  // This dwarfs ride-request traffic by ~700-2,000×. The system's write
  // path is dominated by location ingestion, not by ride requests — this
  // is the number that shapes the ingest architecture in Lesson 2.

5. Storage Estimation

Trip record (rider_id, driver_id, pickup, dropoff, fare, surge_multiplier,
             timestamps, route summary): ~1 KB/trip
  10M rides/day * 1 KB                 = 10 GB/day
  Over 5 years: 10 GB * 365 * 5         ≈ 18 TB (durable, for billing/receipts/disputes)

Driver location pings: NOT stored durably per-ping — only the latest
position per driver is kept (in the geospatial index from Ch.28's
geohash + Redis approach), overwritten every ~4 seconds.
  Live location footprint: 1M drivers * ~50 bytes (id + lat/lng + ts) ≈ 50 MB
  // Tiny and entirely in-memory — confirms location state is a cache,
  // not a database table, reinforcing the eventual-consistency NFR above.
💡 Interview signal: Explicitly stating that raw pings are not durably stored (only trip summaries are) heads off a common interviewer trap: "so you're writing 250K location records/sec to your database?" — the answer is no, and explaining why shows real design judgment.

6. Interfaces (Internal)

APIPurpose
requestRide(riderId, pickup, dropoff) → rideId, estimatedFareKicks off matching (Lesson 3); fare includes current surge multiplier (Lesson 4)
updateDriverLocation(driverId, lat, lng)High-frequency write (~250K/sec system-wide) into the live location index
getNearbyDrivers(lat, lng, radius) → driverIds[]Reuses the geospatial index pattern from Chapter 28, adapted for moving entities
acceptRide(driverId, rideId)Strongly consistent — must guarantee exactly one driver is assigned (Lesson 3)

Key Takeaways

  • Driver location writes (~250K/sec) dominate the system's load by three orders of magnitude over ride requests (~116-350/sec) — design the ingest path first
  • Consistency requirements are not uniform: ride acceptance must be strongly consistent (no double-booking), location data is eventually consistent
  • Raw location pings are ephemeral, in-memory, and overwritten — only trip summaries need durable, long-term storage
  • This system reuses the geospatial indexing idea from location-based search, but for moving entities rather than static places

Interview Tips

  • Lead with the location-write rate, not the ride-request rate — it's the number that dominates the architecture
  • Explicitly split consistency requirements by data type (booking vs. location) rather than picking one model for the whole system
  • State that raw pings aren't durably persisted before an interviewer asks — it preempts a common storage-sizing trap
  • If you covered Chapter 28, reference it directly: "same nearby-search problem, but now the points move" reframes it as a known pattern, not a new one
