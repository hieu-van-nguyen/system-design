Deep Dive — Metadata DB & Sync Service

lesson
⏱ 10 min
📖 Chapter 19, Lesson 4

🎯 Learning Objectives

  • Design the 5-table metadata schema (files, file_versions, shares, change_journal, folder_permissions) and explain the sharding strategy for 5T file records
  • Architect the Sync Service for 20M concurrent WebSocket connections — memory math, server count, and the cursor-based long-poll fallback
  • Explain file versioning as ordered chunk-hash snapshots (not full copies) and calculate the storage savings vs. naive full-file versioning
  • Design the GDPR erasure pipeline with reference-counted chunk GC, and the Elasticsearch permission-aware search query

1. Metadata Database Schema

The metadata layer is the brain of the system. It must handle conflict detection (strong consistency), folder trees (hierarchical queries), sharing/permissions (security boundary), and a complete change history for sync (cursor-based pagination).

-- ─── FILES (current state of each file/folder) ──────────────────────────────
CREATE TABLE files (
    id                  BIGINT       PRIMARY KEY,      -- Snowflake ID (time-ordered)
    owner_user_id       BIGINT       NOT NULL,
    parent_folder_id    BIGINT       REFERENCES files(id) ON DELETE CASCADE,
    name                TEXT         NOT NULL,
    is_folder           BOOLEAN      DEFAULT FALSE,
    current_version_id  BIGINT,                        -- FK to file_versions
    is_deleted          BOOLEAN      DEFAULT FALSE,    -- soft-delete (30-day recovery)
    created_at          TIMESTAMPTZ  DEFAULT NOW(),
    updated_at          TIMESTAMPTZ  DEFAULT NOW(),
    -- Shard key: owner_user_id (all files for one user on same shard)
    CONSTRAINT unique_name_in_folder UNIQUE (parent_folder_id, name, owner_user_id)
);
CREATE INDEX idx_files_owner_parent ON files(owner_user_id, parent_folder_id)
    WHERE is_deleted = FALSE;

-- ─── FILE VERSIONS (immutable history; one row per commit) ──────────────────
CREATE TABLE file_versions (
    id              BIGINT       PRIMARY KEY,      -- Snowflake ID
    file_id         BIGINT       NOT NULL REFERENCES files(id),
    version_number  INTEGER      NOT NULL,
    size_bytes      BIGINT,
    created_by      BIGINT       NOT NULL,         -- user_id
    created_at      TIMESTAMPTZ  DEFAULT NOW(),
    is_tombstone    BOOLEAN      DEFAULT FALSE,     -- for GDPR soft-delete
    UNIQUE (file_id, version_number)
);
-- file_chunks join table (defined in Block Storage lesson) links versions to SHA-256 hashes

-- ─── SHARING / PERMISSIONS ──────────────────────────────────────────────────
CREATE TABLE shares (
    id                  BIGINT       PRIMARY KEY,
    file_id             BIGINT       NOT NULL REFERENCES files(id) ON DELETE CASCADE,
    shared_with_user_id BIGINT,                    -- NULL = public link
    share_token         CHAR(32)     UNIQUE,       -- random token for link shares
    permission          TEXT         NOT NULL
        CHECK (permission IN ('view', 'edit', 'owner')),
    expires_at          TIMESTAMPTZ,               -- NULL = never
    created_at          TIMESTAMPTZ  DEFAULT NOW()
);
CREATE INDEX idx_shares_file ON shares(file_id);
CREATE INDEX idx_shares_user ON shares(shared_with_user_id) WHERE shared_with_user_id IS NOT NULL;

-- ─── CHANGE JOURNAL (append-only, drives cursor-based sync) ─────────────────
CREATE TABLE change_journal (
    id              BIGINT       PRIMARY KEY,      -- monotonically increasing (global sequence)
    user_id         BIGINT       NOT NULL,         -- user whose view is affected
    file_id         BIGINT       NOT NULL,
    change_type     TEXT         NOT NULL
        CHECK (change_type IN ('created','modified','deleted','renamed','shared','unshared')),
    version_id      BIGINT       REFERENCES file_versions(id),
    created_at      TIMESTAMPTZ  DEFAULT NOW()
);
-- Critical index: cursor-based "give me changes since ID X for user Y"
CREATE INDEX idx_change_journal_user_cursor ON change_journal(user_id, id);
-- Why NOT created_at for cursor? Clock skew between servers; monotonic ID is reliable.

Sharding Strategy

5 trillion file records won't fit on one PostgreSQL instance.

Shard key: owner_user_id
  - All files owned by user X live on shard X % N
  - Folder tree queries = same shard (single user's tree)
  - Sharing queries: file appears on owner's shard; share record also on owner's shard
  - Cross-shard problem: "files shared with me" → scatter-gather OR materialized shared-files table

Shard count:
  5T records × 200 bytes = 1 PB metadata
  1 PostgreSQL shard: 10 TB practical limit (SSD, 2TB NVME × 4 RAID)
  Shards needed: 1 PB ÷ 10 TB = 100 shards

Snowflake ID encodes shard:
  Bit layout: [41-bit timestamp][10-bit shard_id][12-bit sequence]
  file_id & 0x3FF000 >> 12 = shard_id → O(1) routing without directory lookup

2. File Versioning — Chunk-Hash Snapshots

Version history stores ordered lists of chunk hashes — NOT full file copies. This is the critical optimization that makes 180-version history affordable.

Example: report.pdf, 40 MB = 10 chunks of 4 MB each

Version 1 (original):
  file_versions(id=v1, file_id=f123, version_number=1)
  file_chunks: [(v1,0,sha_A),(v1,1,sha_B),(v1,2,sha_C),(v1,3,sha_D),...,(v1,9,sha_J)]

Version 2 (edit chunk 2 only):
  file_versions(id=v2, file_id=f123, version_number=2)
  file_chunks: [(v2,0,sha_A),(v2,1,sha_B),(v2,2,sha_NEW),(v2,3,sha_D),...,(v2,9,sha_J)]
  → sha_A, sha_B, sha_D...sha_J are SHARED with v1 (same physical S3 objects)
  → Only sha_NEW is new: stored once in S3

Storage comparison for 180 versions:
  Naive (full copies):      180 × 40 MB = 7.2 GB per file
  Chunk snapshots:          40 MB (v1) + 179 × 4 MB (avg 1 chunk changed per edit)
                          = 40 + 716 = 756 MB per file
  Saving:                  7.2 GB - 756 MB = 6.5 GB = 9.5× reduction

To restore version 6:
  SELECT seq, sha256 FROM file_chunks WHERE file_version_id = v6 ORDER BY seq
  → Returns: [(0,sha_A),(1,sha_B),(2,sha_C_v6),...]
  → Client downloads only chunks that differ from current version (delta restore)

3. Sync Service — WebSocket at 20M Concurrent Connections

Connection Capacity Math

Total concurrent WebSocket connections: 20M
  (50M DAU × 2 devices × 20% online at peak)

Memory per connection (Linux kernel):
  TCP socket buffer:   4 KB (send) + 4 KB (recv) = 8 KB
  WebSocket state:     2 KB (headers, frame parser, user_id mapping)
  Total per conn:      ~10 KB

Total RAM needed:  20M × 10 KB = 200 GB

Sync server sizing:
  Server: 32-core, 64 GB RAM (leave 10 GB for OS + app)
  Connections per server: 54 GB ÷ 10 KB = 5.4M connections
  Servers needed:          20M ÷ 5.4M ≈ 4 servers (with replication: 12 servers, 3 AZs)
  Practical number: 200 servers (for geographic distribution + headroom)

Connection Registry

Problem: when file f123 changes, which WebSocket server holds the connections
         for users A, B, C who have access to f123?

Solution: Redis connection registry (pub/sub + hash)
  On connect:    HSET ws:user:{user_id} server_id {ws_server_id}
                 EXPIRE ws:user:{user_id} 30  # refresh on heartbeat
  On disconnect: HDEL ws:user:{user_id} server_id

Fan-out on file change:
  Kafka consumer (per Sync Server) reads file-changes topic.
  For file f123:
    1. Get all users with access: SELECT user_id FROM shares WHERE file_id = f123
       UNION SELECT owner_user_id FROM files WHERE id = f123
    2. For each user: HGET ws:user:{user_id} → returns server_id
    3. If server_id = this server: push directly to local WebSocket conn
    4. If server_id = other server: pub/sub via Redis channel ws:server:{other_id}

Long-Poll Fallback (for firewalls that block WebSocket)

GET /v1/changes?cursor=892345&timeout=30

Server behavior:
  1. Query: SELECT * FROM change_journal
            WHERE user_id = $user AND id > $cursor
            ORDER BY id LIMIT 100
  2. If results: return immediately (100 changes max per response)
  3. If empty: hold connection 30 seconds (server-side sleep with early-wake on Kafka event)
  4. After 30s: return empty array with same cursor (client retries)

Client behavior:
  while true:
    result = GET /changes?cursor={last_id}&timeout=30
    for change in result.changes:
      process_change(change)
      last_id = change.id
    # No sleep needed: server held connection 30s

4. Search — Elasticsearch with Permission-Aware Filtering

Indexing Pipeline

Kafka consumer (Search Indexer) reads file-changes topic:

On file commit:
  1. Fetch file metadata (name, folder path, owner, shared_with[])
  2. If text file (txt, md, py, js):   read content from S3, index as-is
     If PDF/DOCX/PPTX:                 extract text via Apache Tika (100ms)
     If image/video/binary:            index filename only (no content)
  3. Upsert Elasticsearch document:
     {
       "file_id": "f123",
       "name": "quarterly_report.pdf",
       "folder_path": "/Finance/2024/Q3",
       "content": "Revenue grew 23% year-over-year...",  // extracted text
       "accessible_by_user_ids": [42, 91, 1337],          // owner + all share recipients
       "owner_user_id": 42,
       "updated_at": "2024-08-28T10:00:00Z",
       "size_bytes": 2097152,
       "file_type": "pdf"
     }

On file delete:
  DELETE /files_index/_doc/{file_id}

On permission change:
  UPDATE accessible_by_user_ids (add or remove user_id)

Search Query — Permission-Aware

{
  "query": {
    "bool": {
      "must": [
        {
          "multi_match": {
            "query": "quarterly report revenue",
            "fields": ["name^3", "content", "folder_path^2"],
            "type": "best_fields",
            "fuzziness": "AUTO"
          }
        }
      ],
      "filter": [
        { "term": { "accessible_by_user_ids": 42 } }
      ]
    }
  },
  "highlight": {
    "fields": { "content": { "fragment_size": 150, "number_of_fragments": 3 } }
  },
  "sort": [
    { "_score": "desc" },
    { "updated_at": "desc" }
  ]
}
Security guarantee: the filter on accessible_by_user_ids runs at the Elasticsearch shard level — documents not containing the requesting user's ID are never scored, never returned, never even touched by the query execution plan. This is not application-level filtering; it's enforced in the search engine itself.

5. GDPR Erasure Pipeline

User submits DELETE /v1/account request:

Phase 1 — Immediate (synchronous, < 1 second):
  1. Revoke all auth tokens (invalidate JWT JTI in Redis deny-list)
  2. Soft-delete user account: users.deleted_at = NOW()
  3. Return 200 OK to user

Phase 2 — Grace Period (30 days, recoverable):
  - Files remain in storage with is_deleted = TRUE
  - User can contact support to restore account within 30 days
  - Files not accessible (auth revoked)

Phase 3 — Hard Erasure (Kafka scheduled job at T+30 days):
  1. PostgreSQL: DELETE FROM files WHERE owner_user_id = $user
     → CASCADE deletes file_versions, file_chunks (via FK)
  2. Reference counting: for each deleted file_chunk row:
     UPDATE chunks SET ref_count = ref_count - 1 WHERE sha256 = $sha256
  3. Chunk GC: DELETE FROM chunks WHERE ref_count = 0
     → For each deleted chunk: S3.delete_object(sha256_key)
     Note: shared chunks (ref_count > 0) are NOT deleted — other users still reference them
  4. Elasticsearch: DELETE BY QUERY { term: { owner_user_id: $user } }
     → Also UPDATE accessible_by_user_ids: remove $user from all shared file docs
  5. change_journal: DELETE FROM change_journal WHERE user_id = $user
  6. shares: DELETE FROM shares WHERE shared_with_user_id = $user

Phase 4 — Audit Log (permanent, immutable):
  - Erasure event recorded in append-only audit table (cannot be erased — regulatory requirement)
  - Log: { user_id_hash: SHA256(user_id), erased_at, file_count, byte_count, requestor_ip }
  - user_id stored as hash only — not raw PII

SLA: Complete erasure within 30 days of request (GDPR Article 17 requirement).
     Typically completes in < 1 hour via Kafka pipeline.

6. Consistency Model

OperationConsistencyMechanismAcceptable Staleness
File metadata write (commit)StrongPostgreSQL serializable transaction; parent_version_id check prevents lost updates0 — conflict detection requires linearizability
Sharing permissions readStrongPostgreSQL read from primary; security boundary must not grant stale access0 — stale permission = security bug
Folder listingEventualRedis cache (60s TTL); read from replica for read-scaling60s — directory listing lag is imperceptible
Cross-device sync propagationEventualKafka → Sync Service WebSocket push; 1–30s propagation30s — clearly documented in product SLA
Search indexEventualKafka → ES indexer async; 10–30s indexing lag30s — new file appears in search within 30s
Chunk deduplicationStrongPostgreSQL UNIQUE ON CONFLICT DO NOTHING; prevents double-store race0 — idempotent upsert; correctness required
Virus scan statusEventualAsync SQS → ClamAV; 1–10s scan latency10s — quarantine applied async after upload
Version history readStrongRead file_versions from PostgreSQL primary0 — version history used for conflict detection ancestry
GDPR erasure completionEventualKafka job; completes within 1 hour; committed within 30 days30 days (GDPR SLA)
Two-tier consistency insight: Dropbox has two distinct consistency domains:
  1. Security domain (permissions, conflict detection) — must be strongly consistent. A stale permission read grants unauthorized access; a stale version read causes silent data loss.
  2. Sync domain (propagation to devices, search indexing) — can be eventually consistent. 30-second sync lag is acceptable; users expect it.
Design the system by assigning each operation to one of these domains first, then choose the database accordingly.

Key Takeaways

  • Shard metadata by user_id: 5T file records require 100 PostgreSQL shards; Snowflake ID encodes shard for O(1) routing
  • Version = chunk-hash list, not full copy: 180 versions × 1 new chunk/edit = 756 MB vs. 7.2 GB naive — 9.5× storage reduction
  • Change journal + monotonic ID = reliable cursor: use cursor (integer ID), not timestamp (clock skew risk); index on (user_id, id) for O(log n) polling
  • Permission filter in Elasticsearch, not application: term filter on accessible_by_user_ids enforced at shard level — never leaks data regardless of application bugs
  • GDPR erasure needs reference counting: shared chunks (ref_count > 0) must not be deleted when one user is erased — other users still own them
  • Two consistency domains: security (strong) vs. sync propagation (eventual) — assign each operation to a domain first, choose DB second

Interview Tips

  • When asked "how do you handle 20M WebSocket connections?" — answer with memory math first: 20M × 10 KB = 200 GB → 200 servers; interviewers want numbers
  • The change_journal cursor pattern comes up constantly: "why not use timestamp as cursor?" → clock skew between servers makes timestamps unreliable; monotonic integer IDs are safe
  • For GDPR, proactively mention the reference-counting problem: "deleting one user's data must not delete chunks still owned by other users — we use ref_count and decrement atomically"
  • Search permission filter is a security interviewer probe: "what prevents user A from seeing user B's files in search?" → the ES filter is enforced server-side, not in the application layer
  • Version restore optimization: "restoring version v6 only downloads chunks that differ from the current version — same delta sync algorithm in reverse"
