Requirements & Estimations

The Facebook Newsfeed shows each user a personalized, continuously-updating stream of posts from friends, followed Pages, and Groups. The hard part isn't rendering a list of posts — it's deciding whose posts to fan out, when to compute the feed, and in what order to rank them, at a scale where a single celebrity account can have 100M+ followers and users expect a fresh feed within seconds of opening the app.

1. Clarifying Questions

QuestionWhy it matters
Ranked feed or reverse-chronological?Ranked feed needs an ML scoring pipeline (Lesson 4); chronological only needs a merge of timelines
What content types appear — text, photo, video, shared links?Media-heavy posts push storage/CDN into the design; assume all types, media stored separately from post metadata
Do we design for friends only, or also Pages/Groups the user follows?Increases the fan-out graph beyond a symmetric friend graph to include one-directional follows
How fresh must the feed be after a friend posts?Assume "seconds," which rules out fully-batch/offline feed generation
Do we need infinite scroll / pagination that's stable while new posts arrive?Drives cursor-based pagination instead of offset-based (Lesson 2)
Read-heavy or write-heavy system?Feed reads vastly outnumber post writes — this ratio drives the pull vs. push decision in Lesson 2

For this design: ranked feed (with a chronological fallback), all content types, friends + Pages/Groups, feed updates visible within seconds, and stable cursor-based pagination.

2. Functional Requirements

  • Users can create posts (text, photo, video, link) visible to their friends/followers
  • Users can fetch their personalized feed, paginated, ordered by rank (or recency as fallback)
  • New posts from friends/Pages should appear in the feed within seconds
  • Users can like, comment, and share posts, and those signals feed back into ranking
  • The feed excludes posts the user has already seen or hidden, and respects blocks/privacy settings
  • The system supports both a "top follower count" celebrity account and an average user with ~300 friends

3. Non-Functional Requirements

AttributeTarget
AvailabilityFavor availability over strict consistency — a slightly stale feed is fine, a feed that fails to load is not
LatencyFeed load p99 < 200ms; new-post-to-friend's-feed visibility within a few seconds
ScalabilitySupport 1B+ DAU, with feed reads outnumbering post writes by roughly 20:1
ConsistencyEventual consistency for feed content; read-your-own-writes for a user's own post
DurabilityPosts and social graph edges must never be lost; the feed cache itself is disposable/rebuildable
💡 Interview signal: Explicitly say "the feed cache is a derived, rebuildable view — the source of truth is the post store and the social graph." This tells the interviewer you understand which data must be durable and which can be treated as an optimization.

4. Traffic Estimation

Assumptions:
  DAU                        = 1,000,000,000  (1B)
  Avg friends/follows per user = 300
  Posts created per user/day = 0.5            // most users read far more than they post
  Feed reads per user/day    = 10              // opening the app / scrolling, refreshes included

Post writes/day  = 1B * 0.5                = 500,000,000 posts/day
Post writes/sec  = 500M / 86,400            ≈ 5,800 writes/sec (avg)

Feed reads/day   = 1B * 10                 = 10,000,000,000 reads/day (10B)
Feed reads/sec   = 10B / 86,400             ≈ 116,000 reads/sec (avg)
Feed reads peak  ≈ 116K * 3 (evening peak)  ≈ 350,000 reads/sec (peak)

Read : Write ratio ≈ 116,000 : 5,800  ≈  20 : 1
  // Feed reads dominate — this is why we cache aggressively and
  // precompute feed content instead of joining across the social graph on every read.

Fan-out amplification (if every post were pushed to every follower's feed):
  Fan-out writes/day = 500M posts * 300 avg friends = 150,000,000,000 (150B)
  Fan-out writes/sec = 150B / 86,400          ≈ 1,700,000 writes/sec (1.7M/sec)
  // 1.7M/sec of fan-out work is what makes "push to everyone, always" infeasible
  // for celebrity accounts — this single number motivates the hybrid model in Lesson 3.

5. Storage Estimation

Post metadata (author_id, timestamp, privacy, media refs, counters): ~300 bytes/post
  500M posts/day * 300 bytes           = 150 GB/day of post metadata
  Over 5 years: 150 GB * 365 * 5       ≈ 274 TB (metadata only, excluding media blobs)

Media (photo/video), stored in blob storage + CDN, referenced by URL from post metadata:
  ~60% of posts include media, avg 200 KB (after compression/thumbnailing)
  500M * 0.6 * 200 KB                 = 60 TB/day of new media

Social graph (friend edges, follow edges): ~1B users * 300 edges * 16 bytes ≈ 4.8 TB total
  // Small compared to posts/media — but read on every fan-out decision, so it lives
  // in a low-latency store (Lesson 2), not scanned from a cold data warehouse.

Precomputed feed cache (push model), per active user:
  Top 500 post IDs + score, 8 bytes each  = 4 KB/user
  1B DAU * 4 KB                        ≈ 4 TB of hot cache footprint (e.g., in Redis)
💡 Interview signal: Separating "post metadata" from "media bytes" and "feed cache" into three distinct storage estimates shows the interviewer you're not treating this as one monolithic database — each has different durability, size, and access-pattern requirements.

6. Interfaces (Internal)

APIPurpose
createPost(userId, content, mediaRefs, privacy) → postIdPublish a new post; triggers fan-out (Lesson 3)
getFeed(userId, cursor, pageSize) → posts[], nextCursorFetch a page of the user's ranked feed (Lesson 2 covers cursor design)
getSocialGraph(userId) → friendIds[], followedIds[]Used by the fan-out worker to determine who receives a post
recordEngagement(userId, postId, type)Feeds like/comment/share signals into the ranking feature store (Lesson 4)

Key Takeaways

  • Feed reads (~116K/sec avg, ~350K/sec peak) outnumber post writes (~5,800/sec) by ~20:1 — design for reads first
  • The 1.7M writes/sec full fan-out number is a red flag, not a target — it's the reason a pure push model can't work for celebrity accounts
  • Treat post metadata, media blobs, the social graph, and the feed cache as four separately-sized, separately-durable stores
  • The feed cache is a derived, rebuildable view; the post store and social graph are the durable sources of truth
  • Availability and low latency matter more than strict consistency — a few-second-stale feed is an acceptable tradeoff

Interview Tips

  • Lead with the read:write ratio — it's the single number that justifies every caching/fan-out decision that follows
  • Call out the celebrity-account edge case early; interviewers use it to test whether you'll blindly push-fan-out everything
  • Separate your storage estimate into metadata vs. media vs. cache — don't lump them into one "database size" number
  • State explicitly which data must be durable (posts, graph) vs. which can be lossy/rebuildable (feed cache)
