Deep Dive — Deduplication & Storage

Two separate dedup problems hide inside "don't crawl the same thing twice": URL dedup (have we ever seen this exact URL?) and content dedup (is this page's content a duplicate of one we already have, even under a different URL — mirrors, tracking params, syndicated articles)? They need different data structures.

1. URL Normalization

Before any dedup check, canonicalize the URL — otherwise cosmetic differences masquerade as new pages:

RuleExample
Lowercase scheme + hostHTTP://Example.com → http://example.com
Strip default portexample.com:80/ → example.com/
Remove fragment/page#section2 → /page
Strip known tracking params?utm_source=x&id=5 → ?id=5
Sort remaining query params?b=2&a=1 → ?a=1&b=2
Resolve relative → absolute against base URL../img.png on site.com/a/b → site.com/img.png
Normalize trailing slash consistently/page/ ≡ /page (pick one convention)

2. URL-Seen Dedup: Bloom Filter

Per Lesson 1, the discovered-URL universe is ~10B entries — far too large to hold in a hash set with reasonable memory. A Bloom filter trades a small, tunable false-positive rate for massive space savings, and its one-sided error is exactly the direction we can tolerate: a false positive means we skip a genuinely new URL (rare, acceptable data loss); a Bloom filter never produces a false negative, so we never accidentally re-crawl-loop on something it swears is new.

Bloom filter sizing for n = 10,000,000,000 URLs, target false-positive rate p = 0.1%

  m (bits) = -(n × ln(p)) / (ln 2)²
           = -(10e9 × ln(0.001)) / (0.6931)²
           = -(10e9 × -6.9078) / 0.4805
           ≈ 143,776,000,000 bits
           ≈ 17.97 GB   (~18 GB bit array)

  k (hash functions) = (m / n) × ln 2
           = (143.776e9 / 10e9) × 0.6931
           ≈ 9.97 ≈ 10 hash functions

→ An ~18 GB bit array with 10 hash functions comfortably fits in memory
  on a handful of sharded nodes (shard by a prefix of the URL hash so
  each node owns a slice of the bit space).
💡 Interview signal: stating the one-sided-error property out loud ("false positives only cost us a missed page, never a correctness bug") is what shows you understand why a Bloom filter is safe here, not just that it's space-efficient.

3. Content Dedup: Exact and Near-Duplicate

TypeTechniqueCatches
Exact duplicateSHA-1/MD5 hash of normalized page content; O(1) lookup against stored hashesByte-identical content served at a different URL (mirrors, re-hosted copies)
Near-duplicateSimHash fingerprint: shingle the content into overlapping n-grams, hash and combine into a fixed-length (e.g., 64-bit) fingerprint where similar documents land close in Hamming distanceBoilerplate template pages, syndicated articles with a different header/footer/ad block, minor edits
 
// Near-duplicate check: is this fingerprint within Hamming distance 3
// of any fingerprint we've already stored?
//
// Can't brute-force compare against 1B+ stored fingerprints per page.
// Standard trick: split the 64-bit fingerprint into k bands, build an
// index per band, and only compare candidates that match on at least
// one band exactly — narrows millions of candidates down to a handful
// before doing the expensive Hamming-distance comparison.

isNearDuplicate(fp) = existsIndexedFingerprint(fp, maxHammingDistance=3)

4. Page Store Schema

PageRecord {
  urlHash          // partition/shard key — consistent hashing across storage nodes
  normalizedUrl
  fetchTimestamp
  httpStatus
  contentHash      // exact-dup key
  simhashFingerprint
  rawContentRef    // pointer into blob storage (cold tier), not inline
  outboundLinks[]
  crawlPriority
  nextCrawlTime    // adaptive recrawl scheduling
}

Sharding by urlHash (consistent hashing) spreads load evenly regardless of host popularity skew, since the shard key is independent of host. Per Lesson 1's estimate: 500 TB raw HTML/month × 3× replication ≈ 1.5 PB/month physical storage, plus ~500 GB of metadata that fits comfortably in a wide-column store.

5. Adaptive Recrawl Scheduling

nextCrawlTime isn't fixed at 30 days for every page — pages observed to change frequently (content hash differs on successive crawls) get a shorter interval; static pages get progressively longer intervals, similar to exponential backoff run in reverse. This keeps the 386 pages/sec average budget spent where it matters instead of uniformly re-fetching pages that never change.

Key Takeaways

  • URL dedup and content dedup are different problems needing different structures — normalize first, then Bloom-filter the URL, then fingerprint the content
  • A Bloom filter's one-sided error (false positives only, never false negatives) is exactly the tradeoff a crawler can safely accept
  • ~18 GB / 10 hash functions covers a 10B-URL universe at a 0.1% false-positive rate — small enough to shard across a handful of nodes
  • SimHash + banded indexing catches near-duplicates that exact hashing misses, without brute-force comparing every page pair
  • Shard the page store by URL hash (not by host) to avoid hot-spotting on popular domains

Interview Tips

  • Always separate "have we seen this URL" from "have we seen this content" — interviewers frequently ask this as a direct follow-up
  • Walk through the Bloom filter math rather than citing the ~18 GB result — the derivation is the signal
  • If asked to reduce false positives further, discuss the direct cost tradeoff: halving p roughly adds another ~10 bits/element, not a free win
  • Mention adaptive recrawl scheduling — it shows you're optimizing the crawl budget, not just executing it uniformly
