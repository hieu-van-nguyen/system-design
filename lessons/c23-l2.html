🎯 Learning Objectives

  • Design the end-to-end offline pipeline: query log → Kafka → Flink 7-day window → Trie Builder → Redis

  • Apply multi-language isolation, profanity filtering, and trending injection to a production typeahead system

Deep Dive — Distributed Trie & Ranking

1. Trie Sharding by Prefix Range

A single Redis instance can't handle 4M QPS. A single trie (even compressed at ~20 GB) fits in memory, but throughput is the constraint. The solution: shard the trie by the first letter(s) of the prefix.


// 3-shard prefix range split (balanced by query frequency):
Shard 1 (a–h):  handles "apple", "google", "how to", "facebook", ...
Shard 2 (i–p):  handles "instagram", "nike", "netflix", "python", ...
Shard 3 (q–z):  handles "reddit", "twitter", "youtube", "walmart", ...

// Routing logic in Suggestion Service:
String prefix = query.toLowerCase();
int shardId = getShardForPrefix(prefix);
String result = redisShards[shardId].hget("trie:en", prefix);
⚠️ The Hot Prefix Problem: Single-character prefixes (a, b, c... s, t, w) receive all traffic for their letter. "w" alone handles queries for "walmart", "weather", "wikipedia", "wordle" — potentially 500K QPS from a single character. A single Redis shard for "w" becomes a bottleneck.

1.1 Mitigation: Read Replicas for Hot Prefixes


// For 1-char and 2-char prefixes: use read replicas
// The "w" prefix is served by 10 Redis replicas (round-robin):
shardW_replicas = [redis-w-1, redis-w-2, ..., redis-w-10]

// Consistent hashing routes request to replica:
replicaIdx = hash(requestId) % 10
result = shardW_replicas[replicaIdx].hget("trie:en", "w")

// All replicas are updated atomically by Trie Builder:
for replica in shardW_replicas:
    replica.hset("trie:en:staging", "w", top5_json)
RENAME trie:en:staging trie:en  // on each replica in sequence
Prefix LengthUnique PrefixesQPS Per Prefix (avg)Strategy
1 char (a–z)26150K QPS/prefix10 read replicas per letter
2 chars (aa–zz)6765.7K QPS/prefixCDN edge cache (TTL 5 min)
3+ chars17,576+< 250 QPS/prefixSingle Redis shard — no special handling needed
💡 CDN for 2-char Prefixes: There are only 676 two-character prefixes (26 × 26). These account for a large fraction of traffic but their results are shared across all users (not personalized at this stage). A CDN can cache all 676 at the edge with a 5-minute TTL, reducing origin load by ~30%. This is distinct from personalized suggestions which can't be CDN-cached.

2. Offline Build Pipeline

The entire trie is rebuilt every 15 minutes from aggregated query logs. This offline pipeline is the backbone of the system's freshness guarantee.


// End-to-end pipeline:

// Step 1: Query log collection (per query completion)
{
  "query": "weather forecast",
  "selected_suggestion": "weather forecast los angeles",
  "user_id": "u_abc123",
  "session_id": "sess_xyz",
  "timestamp": 1725000000000,
  "lang": "en"
}
→ Kafka topic: "query-completions" (2,000 partitions, key=lang+first_char)

// Step 2: Flink 7-day sliding window with 15-min hop
DataStream<QueryCount> queryStream = env
    .addSource(new KafkaSource("query-completions"))
    .keyBy(event -> event.query)
    .window(SlidingEventTimeWindows.of(Time.days(7), Time.minutes(15)))
    .aggregate(new CountAggregator())
    // Output: (query="weather forecast", count=2,847,293, window_end=T)

// Step 3: Apply recency decay and score
score = count × exp(-λ × days_since_window_start)  // λ=0.1

// Step 4: Trie Builder reads scored stream, builds Patricia trie in-memory
// → Traverse all queries, insert with score, update top-K at each ancestor node
// Build time for 1B queries: ~8 minutes on 32-core machine

// Step 5: Serialize trie to Redis staging key
// → HSET trie:en:staging for each reachable prefix
// → RENAME trie:en:staging trie:en (atomic hot-swap)

// Total pipeline latency: 15-min window hop + 8-min build + 1-min Redis write ≈ 24 min
// → Effective lag: up to 24 minutes for a brand-new trending query to surface

2.1 Count-Min Sketch for Frequency Estimation

Flink can't store exact counts for all 1B unique queries in memory. Instead it uses Count-Min Sketch to estimate frequencies with bounded error.


// Count-Min Sketch (same technique as Twitter trending — Chapter 21):
// d=5 hash functions × w=100,000 counters per row
// Memory: 5 × 100,000 × 4 bytes = 2 MB per Flink task
// vs. exact HashMap: ~1B entries × 50 bytes = 50 GB — impossible in memory

// Error bound: P(|estimate - true| > ε × N) < δ
//   where ε = e/w = 2.718/100,000 ≈ 0.003% (0.003% of total queries)
//   and   δ = e^(-d) = e^(-5) ≈ 0.7%

// For a query with true count 1,000,000: estimate error ≤ 0.003% × 42.5B = 1.275M
// → Not suitable for exact counts, but fine for ranking (order of magnitude correct)
// → Use Count-Min Sketch for filtering candidates; exact counts from Kafka compacted topic for final build

3. Personalization

Global trie suggestions rank by population-wide frequency. Personalization blends in the user's own query history for a dramatically better experience.

3.1 Personal History Store


// Redis per-user sorted set (TTL: 90 days)
// Key: "personal:{user_id}"
// Score: timestamp of last search
// Member: query string

ZADD personal:u_abc123 1725000000 "weather forecast"
ZADD personal:u_abc123 1724990000 "weather los angeles"
ZADD personal:u_abc123 1724900000 "weather radar"

// Get user's recent queries matching prefix "wea":
ZRANGEBYSCORE personal:u_abc123 -inf +inf  // all queries
→ filter client-side for prefix match "wea"
→ ["weather forecast", "weather los angeles", "weather radar"]

3.2 Blending at Serve Time


// Suggestion Service blending logic:
function getSuggestions(prefix, userId, lang):
    // Parallel fetch:
    globalTop5  = redis.hget("trie:" + lang, prefix)      // ~0.5ms
    personalHits = personalStore.getMatchingPrefix(userId, prefix)  // ~0.5ms

    // Blend: 90% global score + 10% personal score
    merged = {}
    for suggestion in globalTop5:
        merged[suggestion.query] = suggestion.score × 0.9

    for personalQuery in personalHits:
        if personalQuery in merged:
            merged[personalQuery] += personalBoost(personalQuery) × 0.1
        else:
            merged[personalQuery] = personalBoost(personalQuery) × 0.1

    // personalBoost = 1M × recency_score (recent = higher)
    // recency_score = exp(-hours_since_last_search / 24)

    return sorted(merged, by_score, desc)[:5]
💡 Why 90/10 Split? A pure personal model creates a filter bubble — the user only sees what they've searched before. A pure global model ignores personal context. The 90/10 split ensures the most globally relevant results (shared knowledge) dominate, while personal queries get a meaningful boost when they match. Google uses a similar blend that leans heavily global for short prefixes (1–3 chars) and more personal for longer prefixes.

4. Content Filtering Pipeline

Suggestions must be safe before reaching users. Filtering happens at multiple stages:

Profanity blocklistAho-Corasick automaton over blocklist (~100K terms); O(L) scan of each suggestionBuild time (excluded from trie) + serve time (defense-in-depth)
SafeSearch filterClassifier labels queries as safe/explicit. Explicit queries excluded from default trie; served only if user opts into SafeSearch-off mode.Build time, applied to top-K selection
Legal blocklistCourt orders, DMCA requests, country-specific bans (e.g., Germany bans certain political terms)Build time; country-specific trie variant

5. Multi-Language Support


// One trie per language, stored as separate Redis hash:
trie:en   → English trie
trie:es   → Spanish trie
trie:zh   → Chinese trie (character-based, not alphabetic — uses n-gram prefix model)
trie:ar   → Arabic trie (right-to-left, stored left-to-right internally)
trie:hi   → Hindi trie (Devanagari script — Unicode code points as trie keys)

// Language detection from request:
1. HTTP Accept-Language header: "es-MX,es;q=0.9,en;q=0.8" → "es"
2. User profile language preference (overrides header if set)
3. Fallback: "en" if detection fails

// Routing:
lang = detectLanguage(request)
result = redis.hget("trie:" + lang, prefix)
if (result == null && lang != "en"):
    result = redis.hget("trie:en", prefix)  // English fallback

6. Full System Architecture — Deep Dive


REQUEST PATH (4M QPS peak):

User types "wea" (keypress #3)
  │
  ▼ GET /v1/suggest?q=wea&lang=en&uid=u123
CDN Edge Cache
  ├── HIT (2-char prefixes only): return cached JSON, ~5ms
  └── MISS: forward to API Gateway
        │
        ▼
Suggestion Service (stateless, 400 nodes @ 10K QPS/node)
  ├── Profanity pre-filter: is "wea" on blocklist? No → continue
  ├── Parallel fetch:
  │     ├── Redis Shard "w-z" → HGET trie:en "wea" → ["weather","weather forecast",...] ~0.5ms
  │     └── Personal Store → prefix match "wea" in user's history → ["weather radar"] ~0.5ms
  ├── Blend: 90% global + 10% personal
  ├── Post-filter: remove any profanity from blended results
  ├── Trending injection: check Trending Redis hash for "wea" boost
  └── Return top-5 JSON → ~3ms total server time → <50ms round-trip ✅

WRITE PATH (async, ~98K writes/sec):
Query completion logged → Kafka "query-completions"
  │
  ▼ (15-min Flink window)
Flink Aggregation Jobs
  ├── Count-Min Sketch frequency estimation
  ├── Recency decay scoring
  └── Emit (query, score) → "scored-queries" Kafka topic
        │
        ▼ (triggered every 15 min)
Trie Builder (one builder per language, 32 cores)
  ├── Read scored queries from Kafka (7-day window)
  ├── Build Patricia trie in-memory (~8 min for 1B queries)
  ├── Pre-compute top-K at every node
  ├── Apply profanity + SafeSearch filters
  └── Serialize to Redis trie:en:staging → RENAME → trie:en (~1 min)

TOTAL BUILD CYCLE: ~24 minutes wall-clock
EFFECTIVE FRESHNESS: ~24-min lag for brand-new trending queries

7. Consistency Model

DomainStrategyConsistencyWhy
Global trie suggestionsOffline rebuild every 15 min → Redis RENAMEEventual (~24 min lag)No user notices 24-min stale suggestions; avoids distributed locking on hot nodes
Personal historyWrite-through: every query completion → Redis ZADD immediatelyStrong (for own history)User expects to see their own recent searches reflected immediately
Trending injectionTrending service pushes to Redis hash every 1 minNear-real-time (1 min lag)Breaking news surfaces quickly; separate from main trie to avoid expensive rebuild
Profanity blocklistIn-memory, reloaded every 5 min from DBNear-real-timeNew blocklist entries (legal orders) take effect within 5 min across all nodes
Multi-regionTrie Builder runs per-region; no cross-region syncRegional consistencyUS and EU queries have different trending topics; separate regional tries are more relevant
💡 Two-Domain Insight: Typeahead has two distinct write domains with different consistency requirements. Global suggestions tolerate 24-minute lag (distributed Kafka+Flink pipeline). Personal history requires immediate consistency (user's own searches must appear instantly). Mixing them into a single pipeline would either make global updates too slow or personal updates too complex. Separate stores with separate consistency models is the right separation of concerns.

Key Takeaways

  • Shard by prefix range; replicate hot prefixes: 1-char prefixes need 10× read replicas; 2-char prefixes are CDN-cached; 3+ char prefixes need no special treatment.
  • Offline Kafka → Flink → Trie Builder pipeline: 7-day sliding window gives stable frequency counts; 15-min hop gives acceptable freshness; Count-Min Sketch fits aggregation state in 2 MB per Flink task.
  • Atomic RENAME for zero-downtime trie swap: Build to staging key, RENAME atomically — no user ever sees partial trie state.
  • 90/10 personalization blend: Global relevance dominates; personal history gets a meaningful boost without creating a filter bubble.
  • Trending injection is separate from trie: Main trie rebuilds every 15 min; trending topics injected to a separate Redis hash every 1 min. Serves breaking news without continuous expensive rebuilds.
  • Per-language tries are mandatory: Chinese, Arabic, and Hindi require fundamentally different prefix models. A universal Unicode trie cannot accommodate all three.

Interview Tips

  • Lead with the pipeline diagram: Draw: Query Log → Kafka → Flink → Trie Builder → Redis. This immediately shows you understand the end-to-end freshness cycle, not just the serving layer.
  • Quantify the hot prefix problem: "The 'w' node receives ~500K QPS. A single Redis instance at 1M QPS is at 50% capacity — borderline. I'd use 10 read replicas to give each replica 50K QPS and 10× headroom." Numbers make the problem concrete.
  • Distinguish trending from trie updates: When asked "how do you surface breaking news?", the answer is not "rebuild the trie immediately." It's: separate Trending Redis hash, updated every 1 minute, merged at serve time. This shows architectural sophistication.
  • Personalization = two Redis calls in parallel: Don't make it complex. One call to the global trie shard (~0.5ms), one call to the personal history store (~0.5ms), both in parallel, merged in-memory. Total additional latency: ~0.5ms (parallel execution).
  • Build time math: "1 billion queries × 10 prefix nodes per query = 10B node updates. At 100M updates/sec on a 32-core machine, build takes 100 seconds = ~1.7 minutes." Knowing this lets you reason about the rebuild cycle and how many CPUs the Trie Builder needs.
