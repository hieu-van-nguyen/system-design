Deep Dive — Block Storage & Chunking

lesson
⏱ 12 min
📖 Chapter 19, Lesson 3

🎯 Learning Objectives

  • Explain why content-defined chunking (Rabin fingerprinting) achieves 30–50% storage dedup while fixed-size chunking fails on edits
  • Design the chunk database schema (content-addressed chunks table + file_chunks join table) and explain why SHA-256 is the primary key
  • Trace the presigned S3 upload flow and quantify why only uploading new chunks saves 90%+ bandwidth on typical edits
  • Describe conflict detection using parent_version_id and why "conflict copy" is the correct resolution policy over last-write-wins

1. Why Chunking? — The Core Problem

Naive approach: upload/download the entire file on every change. This fails at scale:

  • User edits 1 sentence in a 40 MB Word document → re-upload 40 MB
  • 50M users × 10 edits/day × 40 MB = 20 PB/day upload bandwidth
  • At $0.08/GB egress: $1.6M/day in unnecessary bandwidth costs

Solution: Split files into chunks. Only upload chunks that changed. This is delta sync.

2. Fixed-Size vs. Content-Defined Chunking

Fixed-Size Chunking (naive — don't recommend this)

File: [A][B][C][D][E]   ← 5 chunks of 8 MB each = 40 MB

User inserts 1 byte at the start of chunk B:
New: [A][B'][C'][D'][E'] ← every chunk from B onward has different content
                           → must re-upload chunks B', C', D', E' = 32 MB

Why it fails: inserting/deleting bytes causes a "boundary shift" —
all downstream chunks get different content even if bytes are unchanged.

Content-Defined Chunking with Rabin Fingerprinting (Dropbox's actual approach)

Algorithm: slide a 48-byte window over the file, compute rolling hash.
           Emit chunk boundary when hash % TARGET_SIZE == MAGIC_VALUE.

Parameters:
  Window:      48 bytes (Rabin polynomial)
  Target size: 4 MB   (avg)
  Min size:    1 MB   (prevent tiny chunks)
  Max size:    8 MB   (prevent huge chunks)

Same edit scenario:
  Original: [A][B][C][D][E]   (natural content boundaries)
  Insert 1 byte at start of B:
  New:      [A][B'][C][D][E]  ← ONLY chunk B' has different hash
                                 C, D, E have IDENTICAL bytes → same SHA-256 → no re-upload

Result: upload 4 MB instead of 32 MB = 87.5% bandwidth saving on this edit

Pseudocode

def rabin_cdc(data: bytes, window=48, min_chunk=1*MB, max_chunk=8*MB) -> list[bytes]:
    PRIME = 3  # Rabin polynomial base
    MOD   = 4 * MB  # target chunk size = avg boundary frequency
    MAGIC = 1       # boundary when hash % MOD == MAGIC

    hash_val, start = 0, 0
    chunks = []
    window_buf = collections.deque(maxlen=window)

    for i, byte in enumerate(data):
        # Roll hash forward: add new byte, remove oldest
        hash_val = (hash_val * PRIME + byte) % MOD
        if len(window_buf) == window:
            hash_val = (hash_val - (window_buf[0] * PRIME**window)) % MOD
        window_buf.append(byte)

        chunk_len = i - start + 1
        # Emit boundary if: hash matches AND min size met, OR max size reached
        if (hash_val == MAGIC and chunk_len >= min_chunk) or chunk_len >= max_chunk:
            chunks.append(data[start:i+1])
            start = i + 1

    if start < len(data):
        chunks.append(data[start:])  # final chunk
    return chunks

3. Global Deduplication via SHA-256 Content Addressing

Each chunk is identified by its SHA-256 hash — its content IS its identity. This enables global deduplication across all users:

Examples of globally shared chunks (same SHA-256 across millions of users):
  - node_modules/lodash/lodash.js   → thousands of JS developers share identical chunk
  - macOS system library dylibs     → millions of Mac users back up identical files
  - blank pages in Word templates   → common document templates deduplicate
  - Common header chunks (PDF, ZIP) → file format boilerplate deduplicates

Dedup math:
  Raw uploads/day:     500M ops × 4 MB avg           = 2 PB/day raw
  After cross-user dedup (30%): 2 PB × 0.70          = 1.4 PB/day unique
  After same-user dedup (delta sync, 20%): × 0.80     = 1.12 PB/day stored
  Annual savings at $0.023/GB (S3): 880 TB/day × 365 × $0.023/GB = $7.4B/year
  (At Dropbox scale; actual savings proportional to their storage cost)

4. Database Schema — Block Storage Layer

-- Global chunk registry (content-addressed, shared across all users)
CREATE TABLE chunks (
    sha256      CHAR(64)     PRIMARY KEY,        -- SHA-256 hex = content identity
    s3_key      TEXT         NOT NULL,           -- s3://dropbox-chunks/ab/cd/sha256
    size_bytes  INTEGER      NOT NULL,
    ref_count   INTEGER      DEFAULT 0,          -- for GDPR erasure GC
    virus_scan  TEXT         DEFAULT 'pending'   -- 'pending','clean','quarantined'
        CHECK (virus_scan IN ('pending','clean','quarantined')),
    created_at  TIMESTAMPTZ  DEFAULT NOW()
);
-- Partition by sha256 prefix for even distribution (256 partitions = sha256[0:2])

-- File version → chunk sequence (join table, immutable after commit)
CREATE TABLE file_chunks (
    file_version_id  BIGINT     NOT NULL REFERENCES file_versions(id) ON DELETE CASCADE,
    seq              SMALLINT   NOT NULL,   -- chunk order within file (0, 1, 2, ...)
    sha256           CHAR(64)   NOT NULL REFERENCES chunks(sha256),
    PRIMARY KEY (file_version_id, seq)
);
-- Index for "what versions reference this chunk?" (used by GDPR erasure GC)
CREATE INDEX idx_file_chunks_sha256 ON file_chunks(sha256);

-- S3 key convention: two-level prefix for S3 key namespace performance
-- s3://dropbox-chunks/{sha256[0:2]}/{sha256[2:4]}/{sha256}
-- Example: sha256 = "a3f7..." → s3://dropbox-chunks/a3/f7/a3f7...
-- Why: S3 performance degrades with sequential prefixes; hex prefix = even distribution

5. Presigned Upload Flow — Dedup Integration

Client → POST /v1/files/init-upload
Body: {
  "file_id": "f123",
  "parent_version_id": "v6",          ← for conflict detection
  "chunk_hashes": [
    "sha256_A", "sha256_B", "sha256_NEW", "sha256_D"
  ]
}

Server logic:
  1. Verify parent_version_id == current_version_id for file f123
     → If mismatch: return 409 Conflict (another device committed first)

  2. Dedup check:
     SELECT sha256 FROM chunks WHERE sha256 = ANY($chunk_hashes) AND virus_scan = 'clean'
     → Returns: {"sha256_A", "sha256_B", "sha256_D"}  (3 of 4 already exist)
     → New chunks: {"sha256_NEW"}

  3. Generate presigned S3 PUT URL for each new chunk:
     URL = s3.generate_presigned_url(
       'put_object',
       Params={'Bucket': 'dropbox-chunks', 'Key': 'a3/f7/sha256_NEW',
               'ContentLength': 4194304},
       ExpiresIn=900  # 15 minutes
     )

  4. Insert chunk placeholders (status=pending):
     INSERT INTO chunks(sha256, s3_key, size_bytes, virus_scan)
     VALUES ('sha256_NEW', 'a3/f7/sha256_NEW', 4194304, 'pending')
     ON CONFLICT DO NOTHING

  5. Return to client:
     {
       "upload_id": "u789",
       "presigned_urls": {
         "sha256_NEW": "https://dropbox-chunks.s3.amazonaws.com/a3/f7/sha256_NEW?X-Amz-..."
       }
       // sha256_A, B, D not included — client skips uploading them
     }

6. Virus Scanning — Non-Blocking Async Pipeline

Upload completes → S3 triggers EventBridge rule → SQS queue → ClamAV worker pool

ClamAV Worker:
  1. Read chunk from S3 (stream, don't download entire chunk before scanning)
  2. Scan stream with ClamAV engine (libclamav)
  3. If CLEAN:    UPDATE chunks SET virus_scan='clean' WHERE sha256=?
     If THREAT:   UPDATE chunks SET virus_scan='quarantined' WHERE sha256=?
                  → Notify user: "File blocked: malware detected"
                  → Do NOT delete chunk (forensics; soft-block only)

Timing:
  ClamAV throughput: ~200 MB/sec per worker
  4 MB chunk scan time: 4 MB ÷ 200 MB/s = 20ms
  Queue-to-scan latency: typically 1–5 seconds
  Impact on upload path: ZERO (file commit proceeds; quarantine invalidates async)

Edge case: what if user downloads a file before scan completes?
  → Download permitted (99.9% are clean)
  → If scan later returns THREAT: file blocked, user notified, file marked unavailable
  → Acceptable: same policy as Gmail attachment scanning

7. Conflict Detection & Resolution

Conflict scenario:
  Device A (laptop) and Device B (phone) both edit report.pdf while phone is offline.
  Device A commits → file version = v7.
  Device B comes online → attempts to commit its version.

Conflict detection (server-side, on commit):
  Client B sends: { parent_version_id: "v6", chunk_hashes: [...] }
  Server checks:  SELECT current_version_id FROM files WHERE id = 'f123'
  Result:         current = "v7" ≠ parent "v6" → CONFLICT

Resolution policy — why NOT last-write-wins:
  Last-write-wins silently discards Device A's changes.
  User has no way to recover lost edits.
  Catastrophic for a product whose value proposition IS data safety.

Correct policy — Conflict Copy:
  Server creates new file entry:
    name: "report (conflicted copy by Bob, 2024-08-28).pdf"
    chunk_hashes: [Device B's chunk_hashes]
    version: v1 (new file, not a version of the original)

  Original file (v7, Device A's version) remains untouched.
  Both versions appear in the shared folder.
  User sees both, merges manually, deletes the conflict copy.

Client UX:
  Sync notification: "Conflict detected in report.pdf. A conflict copy was created."
  Both files visible in folder with clear naming.

8. Large File Resumable Upload

Problem: 50 GB file = 12,500 chunks × 4 MB each.
         If upload fails at chunk 10,000 → must restart from chunk 0.

Solution: client tracks upload state in local SQLite:
  chunks(sha256, uploaded=FALSE, created_at)

On resume:
  1. Client reads SQLite: which chunks have uploaded=FALSE?
  2. Re-query server: POST /init-upload with remaining chunk hashes
     (server already knows which are new vs. existing — dedup still works)
  3. Upload only remaining new chunks
  4. Commit only after ALL chunks confirmed

S3 multipart upload:
  Each chunk maps to one S3 part.
  S3 multipart allows individual part retry without restarting.
  Parts persist for 7 days; client can resume across reboots.

Client pseudocode:
  for chunk in file_chunks:
      if not local_sqlite.is_uploaded(chunk.sha256):
          presigned_url = server.get_presigned_url(chunk.sha256)
          s3.put(presigned_url, chunk.data)
          local_sqlite.mark_uploaded(chunk.sha256)
  server.commit(file_id, all_chunk_hashes)

Key Takeaways

  • CDC vs. fixed-size: Rabin fingerprinting finds natural content boundaries → insert/delete doesn't shift downstream chunks → dedup works across edits
  • SHA-256 = identity: content-addressed storage means dedup is automatic — no separate dedup logic needed; just check if the key exists
  • Only upload new chunks: for typical edits, 1 of 10 chunks changes → 90% bandwidth saving vs. full file upload
  • Virus scan is async: blocking the upload path on AV scan adds 1–5 second latency to 99.9% clean uploads — not acceptable
  • Conflict copy beats last-write-wins: "conflict copy" preserves both versions; last-write-wins silently destroys data — the opposite of what a storage product should do
  • S3 key prefix matters: use sha256[0:4] as two-level prefix; avoid sequential prefixes that create S3 hot partitions

Interview Tips

  • When asked "how does delta sync work?" draw the Rabin CDC diagram showing chunk boundaries surviving an edit — this visual wins points
  • Interviewers often probe: "what's wrong with MD5?" → collision risk for a global dedup store; SHA-256 = 2^256 collision space → safe
  • If asked about compression: "we compress before hashing; gzip -6 on text files; images/video already compressed (JPEG, H.264) — don't double-compress"
  • The ref_count column is the GDPR hook: decrement on version delete; when count reaches 0, delete chunk from S3 — explain this proactively
  • Conflict copy is a talking point: mention Dropbox's actual UX behavior — interviewers who use Dropbox will recognize it and be impressed
