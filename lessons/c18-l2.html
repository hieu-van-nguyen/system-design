Database Schema & Photo Uploads

lesson
⏱ 10 min
📖 Chapter 18, Lesson 3

🎯 Learning Objectives

  • Design the presigned S3 URL upload pipeline and explain why direct-to-S3 is mandatory at scale
  • Describe the async media processing worker pipeline (transcoding, content mod, dedup)
  • Write production-quality schemas for posts, users, media, follow graph, and likes
  • Explain perceptual hash (pHash) deduplication and why it catches re-uploads that SHA-256 misses

Photo Upload Pipeline

The upload pipeline has one non-negotiable constraint: raw media bytes must never transit your API servers. At 7,200 uploads/sec × 2 MB = 14.4 GB/s, routing through app servers would require a $30M+/year transit infrastructure. The solution is S3 presigned URLs.

Presigned URL Flow (Step by Step)

Step 1 — Client requests upload permission:
  POST /api/v1/media/upload/init
  Body: { file_size_bytes: 5242880, content_type: "image/jpeg" }

Step 2 — Upload Service generates presigned URL:
  media_id = Snowflake.generate()  // time-ordered 64-bit ID
  presigned_url = S3.generate_presigned_put(
      bucket = "instagram-raw-media",
      key = f"raw/{media_id}.original",
      expires_in = 3600,              // 1-hour window
      content_type = "image/jpeg",
      content_length_range = (1, 52428800)  // 1B to 50MB max
  )
  INSERT INTO media (media_id, status='pending', s3_raw_key, uploader_id, created_at)
  RETURN { media_id, presigned_url }

Step 3 — Client uploads DIRECTLY to S3 (no Instagram server in data path):
  PUT {presigned_url}
  Headers: Content-Type: image/jpeg
  Body: [5 MB photo bytes]
  → S3 validates content-type and size against the presigned constraints
  → No Instagram server handles these bytes

Step 4 — S3 triggers event notification:
  S3 → EventBridge → Kafka topic "media.uploaded"
  Event: { media_id, user_id, s3_raw_key, file_size_bytes, timestamp }

Step 5 — Media Processing Worker consumes event (async):
  [see Media Processing section below]

Step 6 — Client creates post after media is ready:
  POST /api/v1/posts
  Body: { caption: "...", media_ids: ["abc123"], hashtags: ["#travel"], location_id: 42 }
  → Post Service validates media status='ready' for all media_ids
  → INSERT into posts table, publish Kafka "post.created"
  RETURN { post_id, permalink }
Why validate media_ids at post creation? If you allow a post to reference a media_id that's still "processing" or "failed", users see broken images in feeds. Always enforce the contract: post creation requires media status = 'ready'.

Media Processing Workers

These are Kafka consumers running as Kubernetes pods with GPU access. They operate entirely asynchronously — the user's post goes live while these workers run.

Photo Processing Pipeline

Input: JPEG/HEIC/PNG from S3 raw bucket

Step 1 — Decode & Validate:
  Parse container headers (MIME magic bytes, not file extension)
  Strip EXIF metadata (privacy: GPS coordinates, device serial number)
  Reject: corrupt files, >50 MP resolution (decompression bomb risk),
          MIME type mismatch

Step 2 — Content Moderation (mandatory, runs before any storage):
  PhotoDNA hash → compare against NCMEC CSAM database
    Match → immediate reject, legal reporting workflow
  ML nudity/violence classifier (Google Vision API or internal model)
    Score > 0.90 → hold for human review, notify uploader
    Score 0.70–0.90 → allow but flag for periodic audit

Step 3 — Perceptual Hash Deduplication:
  Compute pHash (DCT-based 64-bit fingerprint)
  SELECT post_id, user_id FROM phash_index
    WHERE hamming_distance(phash, {computed_phash}) < 10
  If match found:
    Option A: Link to same S3 object (storage dedup — saves bytes)
    Option B: Store separately, apply "repost" signal in Explore ranking
    Instagram uses Option B: store separate, demote in discovery

Step 4 — Resize & Compress:
  Generate 4 variants (all as WebP — 30-40% smaller than JPEG):
    150×150  crop-center thumbnail  (WebP quality 80)
    640w     medium (feed timeline) (WebP quality 85)
    1080w    full (full-screen view) (WebP quality 90)
    1440w    HiDPI (Retina displays) (WebP quality 90)
  Archive original JPEG to S3 Glacier (for download / legal hold, never served)

Step 5 — Store to S3 & Update Metadata:
  For each variant:
    s3://instagram-media/{shard}/{media_id}/{variant}.webp
    Cache-Control: public, max-age=31536000, immutable
  UPDATE media SET status='ready', variants=['150x150','640w','1080w','1440w']
  CDN warm request for popular content (proactive pre-caching)

Video Upload (Reels) — Chunked Multipart

Videos can be 200 MB+ — standard HTTP POST fails on network interruption.
Solution: resumable chunked upload protocol.

1. Client: POST /api/v1/media/upload/init?type=video
   Response: { upload_id, chunk_size: 5242880 }  // 5 MB chunks

2. Client splits video into 5 MB chunks, uploads sequentially:
   PUT /api/v1/media/upload/{upload_id}/chunk/{n}
   Body: [5 MB chunk bytes]
   Response: { bytes_received, next_offset }

3. On network failure: client queries current offset:
   GET /api/v1/media/upload/{upload_id}/status
   Response: { offset: 52428800 }  // resume from byte 50MB

4. After all chunks: POST /api/v1/media/upload/{upload_id}/complete
   → Server: S3 compose API merges all chunks into single object atomically
   → Kafka "video.uploaded" → GPU transcoding workers

GPU Transcoding (FFmpeg + NVIDIA A100):
  Output profiles:
    360p  H.264 (800 Kbps) + AAC 128k  → HLS segments (2s)
    720p  H.264 (2.5 Mbps) + AAC 128k  → HLS segments (2s)
    1080p H.264 (5 Mbps)   + AAC 192k  → HLS segments (2s)
    720p  H.265/HEVC (1.2 Mbps)         → 40% smaller for newer devices

  Auto-caption (ASR): audio → Whisper → WebVTT with word timestamps
  Thumbnail: ML picks most visually interesting frame from 0s/1s/2s

Data Models

Post

-- Cassandra: primary post store (high write throughput, time-ordered)
CREATE TABLE posts (
    post_id       BIGINT    PRIMARY KEY,   -- Snowflake (encodes created_at)
    user_id       BIGINT    NOT NULL,
    caption       TEXT,
    media_ids     LIST<TEXT>,              -- ordered list of media_id refs
    post_type     TEXT,                   -- 'photo', 'video', 'carousel', 'reel'
    hashtags      LIST<TEXT>,
    location_id   BIGINT,
    like_count    BIGINT    DEFAULT 0,
    comment_count BIGINT    DEFAULT 0,
    is_deleted    BOOLEAN   DEFAULT false,
    created_at    TIMESTAMP
);

-- User's post timeline (for profile grid — partition by user, cluster by post)
CREATE TABLE user_posts (
    user_id  BIGINT,
    post_id  BIGINT,
    PRIMARY KEY (user_id, post_id)
) WITH CLUSTERING ORDER BY (post_id DESC);  -- newest first

Media Object

-- PostgreSQL: media metadata (small, rich queries, moderate scale)
CREATE TABLE media (
    media_id          BIGINT         PRIMARY KEY,  -- Snowflake
    uploader_id       BIGINT         NOT NULL,
    media_type        VARCHAR(10)    NOT NULL,     -- 'photo', 'video'
    status            VARCHAR(20)    DEFAULT 'pending',
                                    -- 'pending'|'processing'|'ready'|'failed'
    s3_raw_key        TEXT           NOT NULL,
    width_px          INTEGER,
    height_px         INTEGER,
    duration_s        FLOAT,                       -- video only
    file_size_bytes   BIGINT,
    phash             BIGINT,                      -- perceptual hash (dedup)
    created_at        TIMESTAMPTZ    DEFAULT NOW()
);

-- GiST index for Hamming distance queries on pHash:
CREATE INDEX idx_media_phash ON media USING GIST (phash gist_int8_ops);

User

-- PostgreSQL: structured, uniqueness constraints, moderate scale
CREATE TABLE users (
    user_id          BIGINT        PRIMARY KEY,  -- Snowflake
    username         VARCHAR(30)   UNIQUE NOT NULL,
    display_name     VARCHAR(60),
    bio              VARCHAR(150),
    profile_pic_id   BIGINT,           -- FK to media
    is_private       BOOLEAN       DEFAULT false,
    is_verified      BOOLEAN       DEFAULT false,
    follower_count   INTEGER       DEFAULT 0,
    following_count  INTEGER       DEFAULT 0,
    post_count       INTEGER       DEFAULT 0,
    created_at       TIMESTAMPTZ   DEFAULT NOW()
);
-- Case-insensitive username uniqueness:
CREATE UNIQUE INDEX idx_users_username_ci ON users (LOWER(username));

Follow Graph (Dual-Table)

-- Cassandra shard A: "who do I follow?" — sharded by follower_id
CREATE TABLE following (
    follower_id  BIGINT,
    followee_id  BIGINT,
    created_at   TIMESTAMP,
    PRIMARY KEY  (follower_id, followee_id)
) WITH CLUSTERING ORDER BY (followee_id ASC);

-- Cassandra shard B: "who follows me?" — sharded by followee_id
CREATE TABLE followers (
    followee_id  BIGINT,
    follower_id  BIGINT,
    created_at   TIMESTAMP,
    PRIMARY KEY  (followee_id, follower_id)
) WITH CLUSTERING ORDER BY (follower_id ASC);

-- BOTH tables updated on every follow/unfollow (dual Cassandra BATCH write)
-- Rationale: single-table would require scatter-gather across 1,000 shards
--            to answer "who follows Ronaldo?" (600M followers)
--            Dual table: O(1) for both traversal directions

-- Pending follow requests (private accounts):
CREATE TABLE follow_requests (
    followee_id  BIGINT,
    follower_id  BIGINT,
    created_at   TIMESTAMP,
    PRIMARY KEY  (followee_id, follower_id)
);

Likes

-- Cassandra: high write volume (48,600 likes/sec)
CREATE TABLE likes (
    post_id     BIGINT,
    user_id     BIGINT,
    created_at  TIMESTAMP,
    PRIMARY KEY (post_id, user_id)   -- deduplication built-in
);

-- For "posts liked by user" (profile Liked tab):
CREATE TABLE user_likes (
    user_id     BIGINT,
    post_id     BIGINT,
    created_at  TIMESTAMP,
    PRIMARY KEY (user_id, post_id)
) WITH CLUSTERING ORDER BY (post_id DESC);

-- Redis for hot-path counts (flushed to Cassandra every 60s):
-- INCR post:{post_id}:like_count  → atomic, 48,600/sec, O(1)
-- SADD post_likers:{post_id} {user_id}  → for "did I like this?"

Key Takeaways

  • S3 presigned URLs are the only viable upload architecture at 14.4 GB/s — never route media bytes through app servers
  • pHash catches re-uploads that SHA-256 misses: same photo with different JPEG compression quality → different SHA-256 hash, same pHash
  • The dual follow-graph table (FOLLOWING + FOLLOWERS) is the standard pattern for any social graph at scale — accept 2× write amplification for O(1) both-direction reads
  • Always use Snowflake IDs for posts and media: they embed a timestamp (no separate column needed) and enable the Cassandra clustering order to work for time-ordered reads
  • Content moderation (PhotoDNA, ML classifier) must run before content is stored or served — not as a background cleanup job
