Requirements & High-Level Design

1. Clarifying Questions

2. Functional Requirements

  • Suggestion API: Given a prefix string, return top-5 search suggestions ranked by global popularity + personal relevance.
  • Fast response: Every keypress triggers a request; response must arrive before the next keypress (~150ms human typing cadence).
  • Near-real-time updates: Trending queries (e.g., breaking news) surface within 15 minutes of becoming popular.
  • Personalization: A user who frequently searches "machine learning" sees ML-related suggestions boosted for prefixes like "ma".
  • Content filtering: No profanity, hate speech, or NSFW suggestions returned.
  • Analytics: Log every query completion for offline trie rebuilds and A/B testing.

4. Back-of-Envelope Estimations

4.1 QPS Sizing

💡 The Keypress Multiplier: The most common mistake is sizing for 98K QPS (raw queries). The actual load is 5× that because every keypress triggers a suggestion request. At peak, the suggestion service handles nearly 4M requests/sec — this is why Google pre-computes and caches suggestions in Redis rather than querying a database per keystroke.

7. API Design

EndpointMethodParamsResponse
/v1/suggestGETq=wea&lang=en&limit=5&uid=u123{ "suggestions": ["weather", "wearable tech", "weather forecast", "weather today", "wearable devices"] }
/v1/query-logPOST (async){ prefix, selected, uid, session_id }{ "logged": true }
⚠️ GET vs POST for Suggest: Use GET — it's cacheable at the CDN/reverse proxy layer. A CDN can serve GET /suggest?q=the from edge cache, eliminating origin load for the most popular prefixes. POST requests are not cached. Short prefixes (1–3 chars) can have cache TTL of 5 minutes; longer prefixes are too numerous to cache effectively.

8. Why Trie Over Elasticsearch / SQL LIKE?

ApproachPrefix Lookup ComplexityProblem
SQL LIKE 'wea%'O(N) full table scan without index; O(log N) with B-tree prefix indexB-tree prefix index works but can't cache top-K at node level; requires post-sort
ElasticsearchO(L × log N) via inverted index + prefix queryOverkill for pure prefix matching; 100ms+ for cold queries at 4M QPS
Hash map prefix → resultsO(1) lookupStores every possible prefix; memory proportional to total prefix space (too large)
Trie + top-K at each nodeO(L) traversal, then O(1) — return pre-cached top-5None — optimal for this use case

The key insight: by pre-computing and caching the top-5 suggestions at every node in the trie, a prefix lookup becomes a single trie traversal (O(L) where L = prefix length) with no further computation. After the traversal, the answer is already there — no ranking, no scanning leaves.

Key Takeaways

  • 5× keypress multiplier: Size the suggestion service at 5× the query QPS — every keypress is a request. At Google scale this is ~4M QPS peak.
  • Read:write = 10,000:1: Optimize entirely for reads; write path (trie update) is offline and asynchronous.
  • Trie with top-K at each node: Pre-computation turns O(N log K) ranking at query time into O(L) traversal + O(1) return.
  • Redis trie cache: 100 GB fits in 10 Redis shards at 10 GB each; O(1) lookup per keypress via hash GET.
  • Offline pipeline freshness: 15-minute rebuild cycle with Flink 7-day sliding window balances trending freshness vs rebuild cost.
  • Personalization blend: 90% global frequency + 10% personal history avoids cold-start while surfacing user preferences.

Interview Tips

  • Anchor on latency first: The <100ms constraint drives every storage decision — it's why you use Redis, not Elasticsearch.
  • Explain the 5× multiplier unprompted: Most candidates size for query QPS only. Identifying the keypress multiplier signals you've thought about real production behavior.
  • Trie vs. hash map tradeoff: A flat hash map of prefix→results works but stores redundant data. A trie shares node prefixes, making memory proportional to the unique prefix space, not total data.
  • Hot-swap trie atomically: When discussing trie rebuilds, mention Redis RENAME to atomically swap the old trie key with the new one — zero-downtime update.
  • CDN caching for top prefixes: Short prefixes (1–3 chars) are shared across all users; a CDN edge cache can absorb the top 676 (26×26) two-char prefix queries entirely, eliminating origin load.
