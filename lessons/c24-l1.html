2. Redis Key Design

Key structure encodes all rate-limiting dimensions:


// Key format: ratelimit:{dimension}:{identifier}:{window_bucket}
// Examples:

// Per user, per minute (Sliding Window Counter needs 2 keys):
ratelimit:user:u_abc123:1725000060   // current window (minute bucket)
ratelimit:user:u_abc123:1725000000   // previous window

// Per API key, per endpoint, per minute:
ratelimit:apikey:key_xyz:POST_v1_messages:1725000060

// Per IP (for unauthenticated requests):
ratelimit:ip:203.0.113.42:1725000060

// Global (entire API):
ratelimit:global:1725000060

// Multi-dimension check: all 3 keys checked in parallel per request
// If ANY exceeds its limit → REJECT

3. Redis Implementation per Algorithm

3.1 Fixed Window — INCR + EXPIRE


-- Lua script (atomic): fixed window counter
-- KEYS[1] = rate limit key, ARGV[1] = limit, ARGV[2] = window_secs

local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[2])  -- set TTL only on first increment
end
if count > tonumber(ARGV[1]) then
    return {0, count}  -- REJECTED, current count
else
    return {1, count}  -- ALLOWED, current count
end

-- Why Lua? INCR and EXPIRE are not atomic together. Without Lua:
-- Thread A: INCR → count=1
-- Thread A: [context switch before EXPIRE]
-- Thread B: INCR → count=2 (key now has NO expiry → leaks forever!)
-- With Lua: INCR + conditional EXPIRE execute atomically on Redis server

3.2 Sliding Window Counter — Lua Script


-- Lua script (atomic): sliding window counter
-- KEYS[1]=current key, KEYS[2]=prev key, ARGV[1]=limit, ARGV[2]=window_secs, ARGV[3]=elapsed_fraction

local cur_count  = tonumber(redis.call('GET', KEYS[1])) or 0
local prev_count = tonumber(redis.call('GET', KEYS[2])) or 0
local elapsed    = tonumber(ARGV[3])  -- fraction through current window: 0.0→1.0

-- Weighted estimate of requests in rolling window
local weighted = cur_count + prev_count * (1 - elapsed)

if weighted < tonumber(ARGV[1]) then
    local new_count = redis.call('INCR', KEYS[1])
    if new_count == 1 then
        redis.call('EXPIRE', KEYS[1], ARGV[2] * 2)  -- 2× TTL: survives as "prev" key
    end
    -- Return: allowed=1, current=new_count, remaining=limit-weighted
    return {1, new_count, tonumber(ARGV[1]) - weighted - 1}
else
    return {0, cur_count, 0}  -- rejected, at limit
end

-- All 5 operations in a single Redis round-trip (Lua executes server-side)
-- Latency: 0.1–0.5ms typical on Redis Cluster

3.3 Token Bucket — Redis Hash


-- Token Bucket state stored as Redis Hash:
HSET ratelimit:token:u_abc123  tokens 100  last_refill 1725000000000

-- Lua script: check and consume token
local key = KEYS[1]
local capacity    = tonumber(ARGV[1])   -- max tokens
local refill_rate = tonumber(ARGV[2])   -- tokens per millisecond
local now         = tonumber(ARGV[3])   -- current time in ms

local state = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens      = tonumber(state[1]) or capacity
local last_refill = tonumber(state[2]) or now

-- Refill tokens based on elapsed time
local elapsed = now - last_refill
local new_tokens = math.min(capacity, tokens + elapsed * refill_rate)

if new_tokens >= 1 then
    redis.call('HMSET', key, 'tokens', new_tokens - 1, 'last_refill', now)
    redis.call('EXPIRE', key, 3600)  -- cleanup idle users after 1 hour
    return {1, math.floor(new_tokens - 1)}  -- allowed, remaining tokens
else
    return {0, 0}  -- rejected
end

3.4 Sliding Window Log — Sorted Set


-- Sliding Window Log: sorted set, score=timestamp
-- Used for critical low-traffic endpoints where exact counts matter

-- Lua script: log-based sliding window
local key       = KEYS[1]
local now       = tonumber(ARGV[1])   -- current timestamp in ms
local window_ms = tonumber(ARGV[2])   -- window duration in ms
local limit     = tonumber(ARGV[3])

-- Remove expired entries
redis.call('ZREMRANGEBYSCORE', key, '-inf', now - window_ms)

-- Count remaining entries in window
local count = redis.call('ZCARD', key)

if count < limit then
    -- Add current request (score=member=timestamp for uniqueness, append seq if needed)
    redis.call('ZADD', key, now, now .. ':' .. math.random(100000))
    redis.call('EXPIRE', key, math.ceil(window_ms / 1000) + 1)
    return {1, limit - count - 1}  -- allowed, remaining
else
    return {0, 0}  -- rejected
end

4. Rate Limit Response Headers

Every API response must include these headers so clients can implement smart retry logic:

HeaderValue ExamplePurpose
X-RateLimit-Limit1000Total requests allowed per window
X-RateLimit-Remaining347Requests remaining in current window
X-RateLimit-Reset1725000120Unix timestamp when window resets (clients can sleep until then)
Retry-After47Seconds until next request is allowed (on 429 response only)
X-RateLimit-Policy1000;w=60;burst=200Machine-readable policy string (IETF draft standard)
 

// HTTP 429 response:
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1725000120
Retry-After: 47
X-RateLimit-Policy: 1000;w=60

{
  "error": {
    "code": "rate_limit_exceeded",
    "message": "You have exceeded your rate limit of 1000 requests per minute.",
    "documentation_url": "https://docs.example.com/rate-limits"
  }
}

5. Rule Configuration System

Limits must be dynamically configurable — changing a limit shouldn't require a deployment.


// PostgreSQL: rate_limit_rules table
CREATE TABLE rate_limit_rules (
    id          SERIAL PRIMARY KEY,
    scope       VARCHAR(20) NOT NULL,  -- 'user', 'api_key', 'ip', 'global', 'endpoint'
    tier        VARCHAR(20),           -- 'free', 'basic', 'enterprise', NULL=all
    endpoint    VARCHAR(200),          -- '/v1/messages', NULL=all endpoints
    limit_value INT NOT NULL,          -- max requests
    window_secs INT NOT NULL,          -- window duration
    algorithm   VARCHAR(30) NOT NULL,  -- 'sliding_window_counter', 'token_bucket'
    burst_size  INT,                   -- token bucket capacity (NULL if not token bucket)
    enabled     BOOLEAN DEFAULT TRUE,
    updated_at  TIMESTAMP DEFAULT NOW()
);

// Example rules:
INSERT INTO rate_limit_rules VALUES
  (1, 'api_key', 'free',       NULL,              100,   60, 'sliding_window_counter', NULL),
  (2, 'api_key', 'basic',      NULL,             1000,   60, 'sliding_window_counter', NULL),
  (3, 'api_key', 'enterprise', NULL,            10000,   60, 'token_bucket',           20000),
  (4, 'endpoint', NULL,        'POST /payment',     10,   60, 'sliding_window_log',     NULL),
  (5, 'ip',       NULL,        NULL,              1000, 3600, 'sliding_window_counter', NULL),
  (6, 'global',   NULL,        NULL,           1000000,   60, 'sliding_window_counter', NULL);
      

// 3-layer rule caching:
// Layer 1: PostgreSQL (source of truth, updated by ops team dashboard)
// Layer 2: Redis (shared cache across all Rate Limiter nodes, 60s TTL)
// Layer 3: Local in-memory (per-node, 30s TTL — avoids Redis lookup on every request)

// Rule lookup at request time (~0ms for hot path):
rule = localMemoryCache.get(user_tier + endpoint)
if not rule:
    rule = redisCache.get("rule:" + user_tier + endpoint)   // ~0.5ms
    if not rule:
        rule = postgres.query("SELECT ... WHERE tier=? AND endpoint=?")  // ~5ms
        redisCache.setex("rule:...", 60, rule)
    localMemoryCache.set(rule, ttl=30s)

6. Technology Choices

ComponentTechnologyRationale
Counter storeRedis Cluster (10 nodes)Single-digit millisecond latency; INCR atomic; Lua scripts for complex operations; 1M ops/sec per node
Rate limiter placementAPI Gateway (Kong/Envoy) + in-process middlewareAPI Gateway for external traffic (centralized); in-process middleware for internal service-to-service calls
Rule storagePostgreSQL → Redis → in-memory3-layer cache: Postgres = durable; Redis = shared; in-memory = zero-latency hot path
AtomicityRedis Lua scriptsLua executes atomically on Redis server — no MULTI/EXEC overhead, no race conditions
Audit loggingKafka → ClickHouseRate limit rejections logged async (never in hot path); ClickHouse for analytics queries on rejection patterns
MonitoringPrometheus + GrafanaTrack: rejection rate per endpoint, Redis latency p99, rule cache hit rate

Key Takeaways

  • Lua scripts for atomicity: INCR + EXPIRE are not atomic together in Redis. A Lua script executes all operations as a single atomic unit on the Redis server — no race conditions, no round-trips.
  • Multi-dimension checks in parallel: User + endpoint + IP limits are checked simultaneously via Redis pipeline — one network round-trip for all three checks.
  • 3-layer rule cache: DB (30s-stale) → Redis (30s TTL) → in-memory (30s TTL). Hot path = in-memory, zero added latency. Emergency updates propagate within 30 seconds.
  • 5 response headers are mandatory: Clients need Limit, Remaining, Reset, Retry-After, and Policy to implement exponential backoff correctly. Missing headers force clients to use trial-and-error.
  • Async audit logging: Never write the rejection audit log synchronously in the request path. Fire-and-forget to Kafka; consume asynchronously to ClickHouse for analytics.
  • Sliding Window Counter in Lua: Two GETs + weighted math + conditional INCR + conditional EXPIRE — all in one Lua script = one Redis round-trip = 0.5ms typical.

Interview Tips

  • Draw the placement in the stack: Rate limiter sits between the API Gateway and the upstream service. Show this explicitly — "every request goes through Rate Limiter before hitting the business logic."
  • Always mention Lua for atomicity: When an interviewer asks "what if two requests arrive simultaneously?" the answer is "I use a Lua script which executes atomically on the Redis server — no distributed locking needed." This is a senior-level answer.
  • 3 Redis operations per request is the baseline: GET(prev) + GET(cur) + INCR(cur) via Lua = 1 network round-trip to Redis. Add this to your latency budget calculation.
  • Explain the response headers proactively: Most candidates implement the rejection but forget the headers. Mentioning all 5 headers (especially Retry-After) shows you've thought about the client experience.
  • Multi-tier limits are the realistic scenario: "Free users get 100/min, paid get 1,000/min, enterprise get 10,000/min — all stored in a rule table, no code change needed to adjust limits." This shows operational maturity.
