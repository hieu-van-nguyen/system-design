Deep Dive — Timeline Generation (Fan-out)

lesson
⏱ 14 min
📖 Chapter 21, Lesson 3

🎯 Learning Objectives

  • Implement the hybrid fan-out algorithm: write fan-out for < 1M followers with Kafka pipeline, read-time celebrity merge at the Timeline Service
  • Design the Redis sorted-set timeline cache — score = Snowflake tweet_id, ZREMRANGEBYRANK trim to 800, ZREVRANGE for O(log N + k) reads
  • Trace a complete home timeline read for a user following both normal users and Katy Perry — including the 5-source merge and hydration step
  • Explain the Count-Min Sketch data structure for trending: d×w hash table, 4 MB vs 128 MB exact, 0.003% error — and how Flink drives it with a sliding window

1. The Three Fan-Out Strategies

StrategyHow it worksWrite costRead costVerdict
Write fan-out (push model)On every tweet, ZADD to each follower's timeline cache immediatelyHigh: followers × 1 ZADDLow: O(log N + k) Redis read✅ Normal users (< 1M followers)
Read fan-out (pull model)On timeline read, fetch followed users' recent tweets and mergeZero at write timeHigh: followings × Cassandra read + merge sort❌ Too slow at 200M users × 69K reads/sec
HybridWrite fan-out for normal users; read-time merge only for celebritiesLow: skip celebrities (≥ 1M followers)Low: Redis read + small celebrity merge (most users follow < 5 celebrities)✅ Twitter's actual approach

2. Write Fan-Out Pipeline (Normal Users)

Trigger: Kafka consumer reads tweet-event { tweet_id: 8675309, user_id: alice, follower_count: 5000 }

Fan-out Worker (1 of N parallel workers):

  Phase 1 — Fetch follower list (paginated):
    page_token = null
    all_followers = []
    while True:
      rows = SELECT follower_id, last_login FROM followers
             WHERE followee_id = alice
             AND   follower_id > page_token
             LIMIT 5000
      all_followers += rows
      if len(rows) < 5000: break
      page_token = rows[-1].follower_id

  Phase 2 — Zombie filter:
    active = [f for f in all_followers if f.last_login > 90_days_ago]
    # Removes ~30% of followers (inactive accounts, bots)
    # For alice (5K followers): 5K × 0.70 = 3,500 active followers to fan-out to

  Phase 3 — Redis pipeline (100 commands per round-trip):
    pipeline = redis.pipeline()
    for i, follower_id in enumerate(active):
      pipeline.zadd(f'timeline:{follower_id}', {tweet_id: tweet_id})
      pipeline.zremrangebyrank(f'timeline:{follower_id}', 0, -801)  # keep top 800
      if (i + 1) % 100 == 0:
        pipeline.execute()   # flush batch
    pipeline.execute()       # flush remainder

  Throughput math:
    5,787 tweets/sec × avg 500 followers × 70% active = 2.03M ZADD/sec
    Redis cluster at 50K ops/sec/node: 2.03M ÷ 50K = 41 Redis nodes for fan-out
    (In practice: 200+ Redis nodes with sharding for timeline cache + fan-out headroom)

3. Celebrity Handling — Read-Time Merge

Definition: celebrity = user with ≥ 1,000,000 followers
Action on tweet: DO NOT fan-out to followers. Write only to:
  - Own timeline (as always)
  - Celebrity tweet index: ZADD celeb_tweets:{user_id} tweet_id tweet_id (keep last 1,000)

Read-time merge (at Timeline Service):
  When Bob requests his home timeline:
    Bob follows: alice (2K followers), charlie (50K followers), KatyPerry (100M followers)

  Step 1: Fetch Bob's pre-computed timeline from Redis:
    ZREVRANGE timeline:bob 0 49 → [tweet_id_a1, tweet_id_a2, tweet_id_c1, ...]
    (Contains tweets from alice + charlie only — normal users, already fanned-out)

  Step 2: For each celebrity Bob follows, fetch their recent tweets:
    ZREVRANGE celeb_tweets:katyperry 0 19 → [tweet_id_k1, tweet_id_k2, ..., tweet_id_k20]
    (O(1) Redis read — celebrity tweets indexed separately)

  Step 3: Merge and sort:
    combined = normal_tweets + celebrity_tweets  # lists of tweet_ids
    combined.sort(key=lambda t: t, reverse=True)  # sort by Snowflake ID (time-ordered)
    top_50 = combined[:50]

  Step 4: Hydrate (fetch tweet content):
    For each tweet_id in top_50:
      Try: MGET tweet_content:{id}  (Redis tweet cache, 5-minute TTL)
      Miss: SELECT * FROM tweets WHERE tweet_id = id  (Cassandra)
    Return hydrated tweets to client

  Latency breakdown:
    Redis ZREVRANGE (normal timeline):          1ms
    Redis ZREVRANGE (N celebrity followings):   N × 0.5ms (avg user follows 3 celebrities = 1.5ms)
    Merge + sort (50 + 60 = 110 tweet IDs):    < 0.1ms (in-memory)
    Hydration (MGET 50 tweet IDs, 95% cache):  3ms
    Total:                                     ~6ms

4. Redis Sorted Set — Timeline Cache Design

Key design:      timeline:{user_id}
Score:           tweet_id       (Snowflake ID, numerically = time-ordered)
Member:          tweet_id       (same value — we store IDs only, not full tweet content)
Max size:        800 entries    (beyond 800 tweets deep, usage is negligible)

Operations:
  ZADD timeline:{uid} {tweet_id} {tweet_id}              -- O(log N) per insert
  ZREVRANGE timeline:{uid} 0 49                          -- O(log N + 50) = O(1) effectively
  ZREVRANGEBYSCORE timeline:{uid} {cursor} -inf LIMIT 50 -- cursor pagination
  ZREMRANGEBYRANK timeline:{uid} 0 -801                  -- trim to 800 newest entries

Why store tweet_id as both score AND member:
  Score must be a float64 (Redis sorted set spec).
  Snowflake ID fits in float64 without precision loss (53-bit mantissa; Snowflake = 41-bit timestamp + 22 bits = 63 bits total... actually at 63 bits, there IS precision loss in float64!)

  Correct implementation:
    Score: unix_timestamp_ms (41 bits → fits in float64 exactly)
    Member: tweet_id as string (no precision loss as string key)
    → ZADD timeline:{uid} {created_at_ms} {tweet_id_string}

Cache miss handling:
  If timeline:{uid} does not exist (user hasn't logged in for a while):
    Timeline Service: SELECT tweet_id FROM user_tweets
                      WHERE user_id IN (followees of uid)
                      ORDER BY tweet_id DESC LIMIT 800 -- Cassandra scatter-gather
    Rebuild cache from Cassandra → warm Redis → serve

Cache eviction:
  EXPIRE timeline:{uid} 604800   -- 7-day TTL (weekly active users stay warm)
  Cold users: cache expires; rebuilt on next login (acceptable cold-start latency: 200ms)

5. Trending Topics — Count-Min Sketch

Why not exact counting?

Exact approach: HashMap<hashtag, count>
  10M unique hashtags at peak × 8 bytes key + 8 bytes count = 160 MB per time window
  5 concurrent Flink windows (1h sliding, 5 operators) = 800 MB state
  Serialization overhead for distributed state: 2–3× = 2.4 GB across Flink cluster

Count-Min Sketch:
  4 MB total (d=5 rows × w=100,000 cols × 8 bytes each)
  Error bound: ε = e/w = 2.718 / 100,000 = 0.003% overcount
  Probability of exceeding error: δ = e^(-d) = e^(-5) = 0.007 = 0.7%
  → 99.3% of hashtag counts are within 0.003% of true value
  → False "trending" at 0.003% error: acceptable (interviewers won't notice #SportsEvent vs #SportEvent)
  Memory: 4 MB vs 160 MB = 97.5% reduction

Count-Min Sketch internals

Structure: d=5 independent hash functions × w=100,000 counter array each

Insert("#WorldCup"):
  for i in range(5):
    col = hash_i("#WorldCup") % 100_000
    table[i][col] += 1

Query("#WorldCup") → estimated count:
  counts = []
  for i in range(5):
    col = hash_i("#WorldCup") % 100_000
    counts.append(table[i][col])
  return min(counts)   ← minimum across all rows (counters are overestimates due to collisions)

Why minimum:
  Hash collisions cause overcounting (multiple hashtags → same cell → cell sum > any one's true count)
  Minimum across 5 independent rows gives tightest bound (probability all 5 overcount same tag is tiny)

Top-K extraction (top 10 trending):
  Min-heap of size 10, maintained over all hashtags seen in window
  When count(tag) > heap.min: heap.push(tag, count(tag)); heap.pop_min()
  Result: top 10 hashtags by estimated frequency

Flink Sliding Window Pipeline

Kafka topic: tweet-events (5,787 events/sec average)

Flink job:
  source: KafkaSource("tweet-events")
    .map(tweet → extract_hashtags(tweet))       -- ["#WorldCup", "#Messi"]
    .flatMap(hashtags → (tag, 1) pairs)
    .keyBy(tag)                                  -- partition by hashtag
    .window(SlidingEventTimeWindows.of(
        Time.hours(1),                           -- 1-hour window
        Time.minutes(5)                          -- 5-minute slide (new trending every 5min)
    ))
    .aggregate(CountMinSketchAggregator())       -- maintain CMS per window
    .process(TopKExtractor(k=10))                -- extract top 10 from CMS
    .sink(RedisSink("trending:global"))          -- publish to Redis

Redis trending key:
  trending:global = [ {tag: "#WorldCup", count: 2.4M}, {tag: "#Messi", count: 1.8M}, ... ]
  TTL: 310 seconds (slightly longer than slide interval to avoid stale reads)

6. "For You" Algorithmic Timeline — Overview

Two-stage recommendation pipeline (separate from chronological timeline):

Stage 1 — Candidate Generation (offline, every hour):
  Two-tower DNN:
    User tower: embeds user_id, follow graph, interaction history → 256-dim user vector
    Tweet tower: embeds tweet content, author, engagement signals → 256-dim tweet vector
  ANN retrieval: ScaNN (Google's ANN library) over 800M active tweet vectors
    For user u: find top 500 tweets with highest dot-product(user_vec_u, tweet_vec_t)
    → 500 candidate tweet IDs stored in Redis: candidates:{user_id}

Stage 2 — Real-time Ranking (on each timeline request):
  Fetch 500 candidates from Redis
  Score each with lightweight ranking model (< 100ms inference):
    Features: engagement probability, recency, diversity penalty (avoid same author repeatedly)
    Output: score per candidate tweet
  Sort by score → return top 20 for "For You" tab
  Interleave with chronological timeline: alternating or weighted blend

Why separate from chronological:
  Chronological is write-time pre-computed (fan-out model)
  Algorithmic requires real-time feature scoring → can't pre-compute per-user at tweet-post time
  Decoupled pipelines: chronological stays fast even if ML pipeline is slow

Key Takeaways

  • Hybrid fan-out threshold = 1M followers: write fan-out for < 1M (5s acceptable); read-time merge for celebrities (Redis ZREVRANGE = < 1ms per celebrity)
  • Zombie filter saves 30%: 30% of followers are inactive; filtering before ZADD = 30M fewer Redis writes per Katy Perry tweet = major cost reduction
  • Score is unix_timestamp_ms, NOT tweet_id: Snowflake IDs at 63 bits exceed float64 precision — use timestamp as score, tweet_id as string member
  • Count-Min Sketch = 4 MB vs 128 MB exact: 0.003% error at 97.5% memory reduction; d=5 rows to reduce collision probability to 0.7%; min() across rows is the correct estimator
  • Flink 5-minute slide: trending refreshes every 5 minutes; 1-hour window captures sustained trends, not momentary spikes

Interview Tips

  • When describing hybrid fan-out, explicitly state the threshold derivation: "1M = 5s target × 50K ZADDs/sec × 100 Redis nodes; anything above this threshold is a celebrity"
  • Mention the pipeline flush: "batching 100 ZADDs per Redis round-trip reduces latency from 100 × 0.5ms = 50ms to 1 × 0.5ms = 0.5ms per batch"
  • The float64 precision issue with Snowflake IDs is an advanced point: "Snowflake IDs at 63 bits exceed the 53-bit float64 mantissa — we use unix_timestamp_ms as the score and tweet_id as string member"
  • For Count-Min Sketch: "d=5 rows gives error probability of e^(-5) = 0.7%; w=100,000 cols gives error magnitude of e/100,000 = 0.003% — both parameters are independently tunable"
  • Don't forget celebrity cache warming: "when a celebrity logs in and posts, their celeb_tweets:{user_id} sorted set is pre-populated by the fan-out worker; read-time merge is O(1) after that"
