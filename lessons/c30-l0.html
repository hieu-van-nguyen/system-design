  • State non-functional requirements that prioritize correctness (no double-booking) over raw throughput
  • Define the core reservation interfaces used throughout the chapter

Requirements & Estimations

Ticketmaster's hardest problem isn't scale in the usual sense — it's contention on a tiny, fixed dataset. When a popular event goes on sale, hundreds of thousands of requests arrive per second, all competing for a seat inventory as small as 50,000 rows. That ratio — not raw QPS — is what shapes this entire design.

1. Clarifying Questions

QuestionWhy it matters
Is event discovery/search in scope, or just seat selection and checkout?Scope to reservation + checkout; discovery is a separate read-heavy search problem (similar to Chapter 25/26's patterns)
Do we need to handle "flash sale" on-sales (e.g., a stadium tour announcing tickets at a fixed time)?This is the design-defining case — assume yes; it's the reason a waiting room (Lesson 4) exists at all
General admission (just a count) or assigned seats?Assigned seats is harder — assume assigned seats, since general admission is a strict subset (just a counter)
How long does a user get to complete payment after selecting a seat?Sets the "hold" TTL — the seat is provisionally locked, not sold, for a bounded window (Lesson 2)
Must double-booking be impossible, or just rare?Impossible — selling the same seat twice is a correctness failure, not a degraded-UX tradeoff

2. Functional Requirements

  • Users can view a venue's seat map and see real-time seat availability
  • Users can select one or more seats and place a temporary hold while completing payment
  • A hold that isn't confirmed within its TTL automatically releases the seat back to available
  • On successful payment, the seat transitions to permanently booked and is issued as a ticket
  • During a flash on-sale, excess demand is queued rather than allowed to overwhelm the reservation path

3. Non-Functional Requirements

AttributeTarget
CorrectnessZero double-booking under any concurrency scenario — this is non-negotiable, unlike most "eventual consistency is fine" NFRs elsewhere in this course
Availability under overloadDegrade gracefully (queue users, show wait times) rather than error out or crash during a flash sale spike
LatencySeat map should feel real-time (~1s) to browsing users; hold confirmation should be near-instant for a user who reaches the front of any queue
FairnessUnder contention, no user should be able to unfairly cut ahead (e.g., via bot scripts hammering the endpoint) — addressed in Lesson 4
💡 Interview signal: Framing the hard requirement as "zero double-booking, not high throughput" early on tells the interviewer you've correctly identified this as a concurrency-correctness problem rather than a generic scale problem — the two call for very different designs.

4. Traffic Estimation

Assumptions:
  Platform DAU (browsing, normal days)        = 10,000,000
  Hot event seat inventory                    = 50,000 seats
  Interested users hitting the on-sale drop   = 10,000,000
  On-sale burst window                        ≈ 20 seconds

Peak reservation requests/sec = 10,000,000 / 20s  ≈ 500,000 req/sec
Seats available                               = 50,000

Contention ratio = 500,000 req/sec : 50,000 seats  ≈ 200,000 competing
  requests for every 20,000 seats sold per second (at best)
  // ~99%+ of requests in the first seconds of a flash sale MUST fail
  // gracefully (queued or told "sold out") — this is normal, expected
  // behavior, not a system overload to be "fixed" with more servers.

5. Storage Estimation

Seat inventory per event: ~50,000 rows (seat_id, section, row, status, price)
  // Small enough to fit entirely in memory for a single hot event —
  // this is exactly why an in-memory lock (Redis) is viable at all
  // (Lesson 3) — the dataset under contention is tiny, even if the
  // request volume against it is enormous.

Venue/seat map (layout, geometry): ~100 KB per venue, largely static
  // Rarely changes — cacheable at the CDN, separate from live status (Lesson 2)

Booking records (durable): user_id, seat_id, event_id, price, timestamp
  ~1 KB/booking * 50,000 seats/event * 10,000 events/year ≈ 500 MB/year
  // Tiny relative to the request volume — the storage problem here is
  // contention, not capacity.
💡 Interview signal: Pointing out that the seat inventory is small enough to live entirely in a single cache node's memory reframes the whole problem: this isn't a sharding/partitioning challenge, it's a single-hot-key concurrency challenge — a very different (and more interesting) discussion.

6. Interfaces (Internal)

APIPurpose
getSeatMap(eventId) → seats[](status, price)Read path; serves the volatile availability overlay (Lesson 2)
holdSeat(eventId, seatId, userId) → holdId, expiresAtAttempts to reserve a seat for a bounded window; this is the highest-contention write (Lesson 3)
confirmBooking(holdId, paymentToken) → bookingIdFinalizes payment and converts a hold into a permanent booking
releaseHold(holdId)Explicit release (user cancels) or implicit release (TTL expiry)

Key Takeaways

  • The defining constraint is contention, not throughput: ~500K req/sec competing for as few as 50,000 seats during a flash sale
  • Zero double-booking is a hard correctness requirement, not a tunable availability/consistency tradeoff
  • The per-event seat inventory is small enough to fit in memory — this is what makes an in-memory concurrency primitive viable later in the chapter
  • Because most requests during a flash sale cannot succeed, graceful degradation (queueing, clear "sold out" signaling) is itself a functional requirement, not an afterthought

Interview Tips

  • Open by naming the contention ratio (requests vs. seats) — it immediately signals you understand what makes this problem hard
  • Distinguish correctness requirements (no double-booking) from availability requirements (browsing can degrade, booking cannot be wrong)
  • State explicitly that most flash-sale requests are expected to fail — designing as if everyone should get a seat is a common misstep
  • Ask whether assigned seating or general admission is in scope; assigned seating is the harder, more interesting case to design for
