🎯 Learning Objectives

Deep Dive — Politeness & BFS vs DFS

Lesson 2's front-queue/back-queue split gives us the mechanism for ordering and pacing crawls. This lesson covers the policy layered on top: which traversal order to use, and how to enforce politeness without a rogue page structure taking down the whole crawl.

1. BFS vs DFS for Crawl Ordering

DimensionBFS (breadth-first)DFS (depth-first)
CoverageSpreads across many hosts quickly — broad, even coverageExhausts one site's link graph before moving on
High-value pagesPages with high in-degree (many inbound links) tend to be discovered early, near the seedsNo such guarantee — a popular page many hops deep is found late, or never, if a trap intervenes first
Crawler trapsA trap only consumes one host's back-queue slot at a time; other hosts keep progressingA single infinite link chain (e.g., ?page=1,2,3,...) can consume the entire crawl budget for one worker
Politeness fitNaturally pairs with per-host back queues — one URL from host H, then move onRepeatedly wants the next URL from the same host, fighting the politeness delay
Interview verdictDefault choice — used in practice (Mercator, most production crawlers)Rarely used standalone; occasionally combined with a strict per-host depth cap

In practice this is "BFS with priority," not pure FIFO breadth-first: the Prioritizer from Lesson 2 biases which front queue gets drained next, so a high-priority page discovered at depth 5 can still be fetched before a low-priority page at depth 2. The breadth-first property we actually want is host diversity, not literal level-order traversal.

2. Politeness Policy

  • Per-host minimum delay: default (e.g., 1-2 sec) unless robots.txt specifies a longer Crawl-delay — enforced by the ready-time min-heap from Lesson 2, so it holds regardless of overall system load
  • Concurrent-connections-per-host cap: normally 1; a handful for large, high-capacity sites that explicitly signal tolerance (e.g., Crawl-delay: 0 plus a documented partnership)
  • IP-level throttling: many distinct hostnames can resolve to one shared IP (small hosting providers, CDNs fronting multiple tenants) — enforcing politeness by hostname alone can still overwhelm a shared backend. Track delay state by resolved IP in addition to hostname when the reverse-DNS/ASN lookup indicates shared hosting.
function onHostReady(host):
    if robotsCache[host].isExpired():
        robotsCache[host] = fetchAndParseRobotsTxt(host)   // TTL ~24h

    delay = max(DEFAULT_DELAY, robotsCache[host].crawlDelay)
    url = backQueue[host].dequeue()
    result = Fetcher.fetch(url)
    backQueue[host].nextFetchTime = now() + delay
    readyHeap.insert(host, backQueue[host].nextFetchTime)
💡 Interview signal: caching robots.txt with a TTL (rather than fetching it before every single page) is a detail that separates a toy answer from a production-grade one — robots.txt fetches would otherwise double your request volume per host.

3. Crawler Traps and Mitigation

Trap patternMitigation
Infinite calendar pages (/events?date=2024-01-01, ...2024-01-02, ...)Cap max crawl depth per host; flag monotonically incrementing query params
Session-ID / tracking params creating unique URLs per requestURL normalization strips known tracking params before the dedup check (Lesson 4)
Deeply nested auto-generated paginationPer-host page-count budget (e.g., max 100K pages/host/cycle); beyond the cap, deprioritize rather than block entirely
Dynamically generated near-duplicate pages under different pathsContent fingerprinting catches these post-fetch even if the URL looks novel (Lesson 4)

Because politeness already caps how much of the crawl budget any single host can consume per unit time, BFS-with-priority plus a per-host page cap bounds the damage from any one trap to a small, predictable slice of total throughput — it can't starve the rest of the crawl.

Key Takeaways

  • BFS-with-priority is the default because it maximizes host diversity and surfaces high-in-degree pages early — pure DFS risks total capture by a single host or trap
  • Politeness must be enforced independent of system load (the ready-time heap), by host and by resolved IP where hosting is shared
  • Cache robots.txt with a TTL — re-fetching it per page would double request volume
  • Bound crawler-trap damage with per-host depth and page-count caps rather than trying to detect every trap pattern upfront

Interview Tips

  • When asked "BFS or DFS," lead with the host-diversity argument, not just "BFS is simpler"
  • Bring up shared-IP throttling unprompted — it's an easy follow-up question interviewers use to test depth
  • Frame trap mitigation as bounding damage, not eliminating traps entirely — a crawler that tries to detect every trap pattern is over-engineered
  • Tie the politeness delay back to the ready-time heap from Lesson 2 rather than describing a new mechanism
