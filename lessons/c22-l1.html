Video Upload Flow — 7 Steps

Step 1 — Creator initiates upload:
  POST /v1/videos/init
  Body: { title: "My Video", duration_sec: 1800, file_size_bytes: 2147483648, mime_type: "video/mp4" }

  Server:
    a. Generate video_id (UUID v4)
    b. INSERT INTO videos (video_id, uploader_id, title, status='UPLOADING', created_at)
    c. Generate S3 multipart upload ID: s3.create_multipart_upload(bucket='raw', key=video_id)
    d. Return { video_id, upload_id, chunk_size_bytes: 10_000_000 }  ← 10 MB chunks

Step 2 — Client uploads chunks directly to S3 (presigned):
  For each 10 MB chunk:
    GET /v1/videos/{video_id}/upload-url?part_number={N}
    Server: presigned_url = s3.generate_presigned_url('upload_part', {Bucket, Key, UploadId, PartNumber})
    Client: PUT {presigned_url} [raw bytes]
    Response: { ETag: "abc123" }  ← client stores ETag per part

  Concurrency: upload 5 parts simultaneously (parallel streams)
  2 GB file ÷ 10 MB/part = 200 parts
  Upload time at 100 Mbps: 2 GB ÷ (100 Mbps ÷ 8) = 160 seconds
  With 5 parallel streams: 160 ÷ 5 = 32 seconds upload time

Step 3 — Client completes multipart upload:
  POST /v1/videos/{video_id}/upload-complete
  Body: { parts: [{part_number: 1, etag: "abc..."}, {part_number: 2, etag: "def..."}] }
  Server: s3.complete_multipart_upload(Parts=[...]) → S3 assembles full file
  UPDATE videos SET status='PROCESSING' WHERE video_id = ?

Step 4 — S3 EventBridge triggers transcoding:
  S3 ObjectCreated event → EventBridge rule → SQS → Transcoding Coordinator
  Coordinator: INSERT INTO transcoding_jobs (video_id, raw_s3_key, status='QUEUED')

Step 5 — DAG Coordinator builds task graph:
  a. Fetch video metadata: duration=30min → 180 10-second segments
  b. Create DAG: segment_extraction → [transcode(seg_i, quality_j) for all i, j] → manifest_assembly
  c. Dispatch: 180 segments × 21 versions = 3,780 encode tasks to GPU worker pool via SQS

Step 6 — GPU Workers transcode in parallel:
  Each worker:
    1. Download 10-second raw segment from S3
    2. Encode: ffmpeg -i input.mp4 -c:v libx264 -preset fast -crf 23 -t 10 output_720p.mp4
       (or libvpx-vp9, libaom-av1)
    3. Force keyframe at segment boundary: -force_key_frames expr:gte(t,0) -g 1
    4. Upload to s3://transcoded/{video_id}/{quality}/{segment_N}.mp4
    5. Report completion to Coordinator

  Parallelism: all 3,780 tasks simultaneously (GPU cluster has 200 GPUs × 10 tasks/GPU = 2,000 concurrent)
  Wall clock: time to complete 1 task ≈ 15 seconds (GPU-accelerated 10s segment encode)
  Total pipeline time: ~15s transcode + 5s assembly = 20 seconds for 30-min video

Step 7 — Manifest Assembly + Publish:
  Coordinator: all tasks complete → generate manifests:
    DASH: .mpd (Media Presentation Description) listing all qualities + segment paths
    HLS:  .m3u8 master playlist + per-quality playlists
  Upload manifests to s3://transcoded/{video_id}/manifest.mpd
  UPDATE videos SET status='PUBLISHED', manifest_url='...', duration=1800
  Push manifest URL to CDN: CDN pre-warms popular thumbnails and first few segments
  Search indexer: index video_id, title, description, tags → Elasticsearch

Video Playback Initiation — 5 Steps

Step 1 — Client requests video page:
  GET /v1/videos/{video_id}
  Response: { title, description, manifest_url, thumbnail_url, duration, like_count, ... }

Step 2 — Client fetches manifest:
  GET https://cdn.youtube.com/{video_id}/manifest.mpd
  CDN edge: 95%+ cache hit (manifest cached max-age=60s — short TTL because like_count embeds here)
  Response: DASH manifest listing available qualities (144p, 240p, 360p, 480p, 720p, 1080p, 2160p)
            with URLs for each 10-second segment

Step 3 — Client selects initial quality:
  ABR (Adaptive Bitrate) algorithm:
    Measure current network throughput: bandwidth_estimate = bytes_received / time
    Select highest quality where: bitrate × 1.5 buffer_safety < bandwidth_estimate
    Example: bandwidth = 12 Mbps → select 1080p (5 Mbps H.264) → leaves 7 Mbps headroom

Step 4 — Client pre-buffers first 3 segments:
  Fetch segments 0, 1, 2 (0–30 seconds of video) in parallel
  GET https://cdn.youtube.com/{video_id}/1080p/segment_0.mp4   → 30 MB
  GET https://cdn.youtube.com/{video_id}/1080p/segment_1.mp4   → 30 MB
  GET https://cdn.youtube.com/{video_id}/1080p/segment_2.mp4   → 30 MB
  Buffer health: 30 seconds buffered before first frame displayed
  First frame: displayed as soon as segment_0 fully downloaded ≈ 0.5–2s depending on network

Step 5 — Continuous ABR adaptation:
  Every segment fetch: measure download time → update bandwidth estimate
  If bandwidth drops: request next segment at lower quality (e.g. 720p instead of 1080p)
  If bandwidth improves: request at higher quality
  Player goal: keep buffer 15–30 seconds ahead (rebuffer if buffer drops to 0)

Technology Choices

ComponentChoiceOne-sentence rationale
Raw video storageS3 (raw bucket)Unlimited scale; multipart upload native; EventBridge trigger for pipeline
Transcoded segmentsS3 (transcoded bucket, content-addressed)Immutable segments → max-age=1 year CDN caching; SHA-256 key prefix ensures even distribution
Transcoding pipelineGPU cluster + DAG coordinator (SQS + worker pool)DAG parallelism reduces 30-min video wall-clock from 6+ hours to 20 seconds
Video manifestMPEG-DASH (.mpd) + HLS (.m3u8)DASH: industry standard; HLS: required for Safari/iOS (Apple mandate)
CDNGGC (YouTube) / Open Connect (Netflix)ISP co-location eliminates internet backbone egress for popular content
Video metadataPostgreSQL (sharded by video_id)ACID for status transitions (uploading → processing → published); rich query for search
Watch historyBigtable (YouTube) / Cassandra (Netflix)Wide-row: row key = user_id + reverse_timestamp → O(1) "last 50 watched"
Like countsRedis INCR + 60s Cassandra flushSame pattern as Twitter: rate exceeds PostgreSQL by orders of magnitude
CommentsCassandra (video_id partition, comment_id DESC)Write-heavy append; O(1) paginated reads per video; no JOIN needed
SearchElasticsearchFull-text + tag search; transcript indexing via async speech-to-text pipeline
RecommendationTwo-tower DNN + ScaNN ANNCandidate generation over 800M video embeddings; watch-time regression not CTR
Creator analyticsClickHouse (OLAP) + Flink (streaming)ClickHouse columnar OLAP for fast aggregation; Flink for real-time view count windows

Key Takeaways

  • Upload and playback paths are completely separate: upload goes raw S3 → DAG transcoder → transcoded S3; playback goes client → CDN edge → origin shield → transcoded S3. They never share infrastructure.
  • Status transitions are the serialization point: UPLOADING → PROCESSING → PUBLISHED in PostgreSQL; enables idempotent retry and observability of the pipeline
  • Manifest TTL vs segment TTL: manifest is dynamic (max-age=60s, embeds metadata) while segments are immutable (max-age=1 year) — different TTLs for different content types
  • 5 parallel chunk streams: multipart upload with 5 concurrent 10 MB parts reduces 2 GB upload from 160s to 32s on a 100 Mbps connection
  • Both DASH and HLS are required: DASH for Android/desktop Chrome; HLS mandatory for iOS/Safari; same segments, different manifest format

Interview Tips

  • The "presigned multipart upload" insight is critical: "the 2 GB raw video never passes through API servers — it goes directly to S3 at the creator's full upload speed"
  • Mention the EventBridge → SQS → Coordinator pattern: "S3 event is the pipeline trigger; SQS provides durability so a coordinator crash doesn't lose the job"
  • When asked "what if transcoding fails mid-way?": "each segment task is independent and idempotent — a failed segment is retried by re-fetching from raw S3 and re-encoding; the coordinator tracks completion per segment"
  • Status machine insight: "UPLOADING → PROCESSING → PUBLISHED with FAILED as a terminal state; creators see 'Processing' on their video until all 21 versions complete (or lowest quality done first)"
