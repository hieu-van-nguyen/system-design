lesson
⏱ 12 min
📖 Chapter 26, Lesson 1

🎯 Learning Objectives

  • Scope a web crawler with clarifying questions (crawl breadth, freshness, content types, politeness)
  • Derive crawl throughput and storage needs from a 1B-pages/month target
  • Size the URL universe your dedup layer must track (discovered vs. crawled)
  • Justify a BFS-first, eventually-consistent design over strict per-page freshness

Requirements & Estimations

A web crawler (Googlebot, Bingbot) systematically discovers and downloads pages by following hyperlinks, starting from a set of seed URLs. The hard part isn't fetching one page — it's fetching billions of pages without hammering any single site, getting stuck in infinite link structures, or re-downloading content you already have.

1. Clarifying Questions

QuestionWhy it matters
General-purpose crawl or a focused/vertical crawl (e.g., only news sites)?Determines seed set size, prioritization strategy, and whether we need topic classifiers
How fresh must content be? (recrawl every day / week / month?)Drives crawl throughput and whether we need adaptive per-page recrawl scheduling
Do we need to render JavaScript (SPA pages) or is raw HTML enough?Headless-browser rendering is 10-100× more expensive per page than a raw HTTP GET
Must we respect robots.txt and Crawl-delay?Legal/ethical requirement for any production crawler — assume yes
What do we store — raw HTML, extracted text, or both?Directly changes storage estimate; assume raw HTML + extracted metadata
Do we need near-duplicate detection across mirrors/syndicated content?Adds a content-fingerprinting stage (covered in Lesson 4)

For this design: general-purpose crawl, monthly full-refresh freshness target, raw-HTML-only fetch (no JS rendering), strict robots.txt compliance, and near-duplicate detection in scope.

2. Functional Requirements

  • Given a set of seed URLs, discover and fetch new pages by following extracted links
  • Respect each site's robots.txt and any Crawl-delay directive
  • Avoid fetching a URL — or content — more than once (URL dedup + content dedup)
  • Re-crawl pages periodically based on an observed/estimated change frequency
  • Extract and store page content, metadata, and outbound links for downstream indexing
  • Handle malformed HTML, redirects, timeouts, and non-HTML content types gracefully

3. Non-Functional Requirements

AttributeTarget
ScalabilitySustain a crawl of 1B+ pages/month; horizontally scale fetcher fleet
PolitenessNever overload a single host — enforce a min per-host delay independent of overall system load
RobustnessTolerate malformed pages, dead links, crawler traps, and slow/unresponsive servers without stalling the pipeline
ExtensibilityNew content types (PDF, sitemap XML) and new prioritization signals pluggable without a redesign
ConsistencyAP-leaning — a page being briefly stale or a URL being fetched twice under a race is acceptable; losing track of the frontier is not

4. Traffic Estimation

Target: full refresh of 1,000,000,000 (1B) pages every 30 days

Average crawl rate:
  1,000,000,000 pages / (30 days × 86,400 s/day)
  = 1,000,000,000 / 2,592,000 s
  ≈ 386 pages/sec (avg)

Peak crawl rate (3× avg — crawler fleet ramps during off-peak windows,
bursts against freshly-discovered link batches):
  386 × 3 ≈ 1,157 pages/sec (peak)

Link discovery rate (avg ~30 outbound links/page, ~90% already-seen):
  386 pages/sec × 30 links/page × 10% new ≈ 1,158 new URLs/sec
  → discovered-URL universe grows far faster than the crawled-page count;
    over time the crawler will have SEEN ~10B+ distinct URLs even though
    it only actively crawls ~1B/month
💡 Interview signal: stating explicitly that "discovered URLs" ≫ "crawled pages" is what leads into designing a URL-seen filter (Bloom filter, Lesson 4) sized for 10B+ entries, not 1B.

5. Storage Estimation

Assume average page size (HTML only, no embedded media): 500 KB

Raw HTML per crawl cycle (30 days):
  1,000,000,000 pages × 500 KB ≈ 500,000,000,000 KB
  = 500 TB / month

With 3× replication for durability:
  500 TB × 3 = 1.5 PB / month of physical storage

Metadata per page (~500 bytes: URL, fetch timestamp, content hash,
HTTP status, outbound link list pointer, next-crawl-time):
  1B pages × 500 bytes = 500 GB metadata (fits a distributed KV/wide-column store)

URL frontier + seen-set working set (avg URL ~100 bytes):
  10B discovered URLs × 100 bytes = 1 TB just for raw URL strings
  (compressed further once hashed — see Lesson 4's Bloom filter sizing)
TierContentsStore
HotIn-flight frontier, per-host queues, robots.txt cacheIn-memory (Redis/custom), sharded by host

6. Interfaces (Internal)

A crawler has no public API — its "interface" is the contract between internal components. Sketching this early signals you're thinking in terms of a pipeline, not a monolith:

URLFrontier.enqueue(url: string, priority: int) -> void
URLFrontier.dequeue() -> url: string          // returns only a URL whose host is "ready" (politeness)

Fetcher.fetch(url: string) -> {status, headers, body, fetchTimeMs}

Parser.extract(html: string, baseUrl: string) -> {text, outboundLinks[], contentHash}

URLFilter.shouldCrawl(url: string) -> bool     // dedup + robots.txt + depth/host caps

Key Takeaways

  • Always separate "discovered URL" volume from "crawled page" volume — the frontier and dedup layer must be sized for the larger number
  • 1B pages/month at 500 KB average yields ~386 pages/sec average, ~1,157 peak, and ~1.5 PB/month replicated storage
  • Politeness is a hard non-functional requirement, not an optimization — it shapes the URL Frontier design in Lesson 2
  • AP-leaning consistency is the right call: a crawler tolerates staleness and occasional duplicate fetches far better than it tolerates losing frontier state

Interview Tips

  • Anchor every later design decision (BFS vs DFS, Bloom filter size, queue sharding) back to the numbers you derive here
  • Explicitly separate "URLs we've seen" from "pages we've fetched" early — interviewers probe this distinction
  • State your assumptions (page size, refresh window, link fan-out) out loud before computing — the number matters less than the method
  • Bring up robots.txt/politeness unprompted; it signals real-world crawler experience
