Requirements & Estimations

lesson
⏱ 8 min
📖 Chapter 20, Lesson 1

🎯 Learning Objectives

  • Ask the 6 clarifying questions that transform "design a chat app" into a scoped, solvable problem with clear boundaries
  • Derive the 3 numbers interviewers care most about: 231K messages/sec throughput, 450M concurrent WebSocket connections, and 3.2 TB/day message storage
  • Explain why 69 GB/s media upload bandwidth forces presigned S3 URLs — same architectural insight as Instagram and Dropbox
  • Identify the two hard problems unique to messaging: message ordering across distributed servers, and fan-out to offline devices

Step 1 — Clarifying Questions

Facebook Messenger is a broad system. Scope it aggressively in the first 2 minutes or you'll spend 45 minutes designing everything and demonstrating nothing deeply.

Do we need end-to-end encryption?E2E (Signal Protocol: X3DH + Double Ratchet) is a separate lesson. Mention it, then scope out.No E2E for this session — mention it as a follow-up
What message types must be supported?Media (images/video) changes the upload path; reactions, replies, and threads each add components.Text + images/video; reactions + replies; no threads
Do we need message history / search?Persistent history requires durable storage; search adds Elasticsearch indexing.Yes — permanent history; no full-text search (scope out)
Do we need read receipts and delivery status?3-state status (sent → delivered → read) requires receipt fan-back to sender; aggregation for groups.Yes — single-tick (sent), double-tick (delivered), blue (read)

Step 4 — Back-of-Envelope Estimation

Message Throughput

MAU:                          1B
DAU:                         500M   (50% activation)
Messages sent per user/day:   40    (mix of 1:1 text, group, media)
Total messages/day:            500M × 40        = 20B messages/day
Peak multiplier:               5×    (global events, time zones)

Average msg/sec:               20B ÷ 86,400     = 231K messages/sec
Peak msg/sec:                  231K × 5         = 1.16M messages/sec

Fan-out delivery events:
  Average group size:          10 members
  Delivery events/sec:         231K × 10        = 2.31M delivery writes/sec
  (includes status updates: sent + delivered + read × 10 members)

WebSocket Connections

DAU:                         500M
Average devices per user:      3    (phone, tablet, desktop)
Total devices:                1.5B
Fraction online at peak:      30%

Concurrent connections:       1.5B × 0.30       = 450M concurrent WebSockets
Memory per connection:         10 KB (TCP buffers + WebSocket state)
Total connection memory:       450M × 10 KB     = 4.5 TB RAM

Chat servers (practical):     10,000 servers × 45K connections each
  → 45K conn/server × 10 KB = 450 MB for connections per server (leaves headroom for msg processing)

Storage

Message type mix:
  85% text:   average 100 bytes  → 20B × 0.85 × 100B = 1.7 TB/day
  15% media:  message row = 500 bytes (URL + metadata, not raw media)
              → 20B × 0.15 × 500B = 1.5 TB/day
  Total message rows: 3.2 TB/day

5-year message storage:    3.2 TB × 365 × 5  = 5.84 PB
After 3× Cassandra repl:  5.84 × 3          = 17.5 PB physical

Status events (sent/delivered/read per message × avg 10 recipients):
  231K msg/sec × 3 states × 10 recipients = 6.93M status writes/sec
  Status row: 30 bytes
  Status storage: 6.93M × 30B × 86,400    = 18 TB/day (requires separate fast-GC store)
  → Status rows expire after 30 days (only recent delivery state matters)

Media Upload Bandwidth

Media messages:      20B/day × 15%             = 3B media messages/day
Average media size:  2 MB (image=200KB, video=5MB avg)
Total media bytes:   3B × 2 MB                 = 6 PB/day
Aggregate bandwidth: 6 PB ÷ 86,400             = 69 GB/sec
Key insight: 69 GB/s media bandwidth cannot route through chat servers. Chat servers run in kernel-bypass mode (io_uring) optimized for tiny message frames — they're not designed for multi-megabyte media streaming. The solution is presigned S3 URLs: clients upload media directly to S3, then send the CDN URL as the message payload. This is the same architectural necessity as Instagram (36 GB/s) and Dropbox (11.6 GB/s).

The Two Hard Problems

Every interviewer probes at least one of these. Have crisp answers ready:

  1. Message ordering across distributed chat servers:
    Multiple servers may receive messages for the same conversation concurrently. Without coordination, server A's message might arrive after server B's message even if sent first. Solution: Snowflake IDs as message_id (41-bit timestamp + server_id + sequence) → time-ordered within a server; conversation-level sequence number via atomic counter for global ordering within a conversation.
  2. Delivery to offline users:
    When the recipient's WebSocket is disconnected, the chat server has nowhere to deliver. Solution: chat server checks presence; if offline → publish to Kafka → notification service → FCM/APNs push → app wakes, opens WebSocket, fetches missed messages from Cassandra.

Key Takeaways

  • 231K messages/sec average, 1.16M/sec peak — the throughput numbers that size Cassandra write capacity
  • 450M concurrent WebSockets = 10,000 chat servers at 45K connections each; 4.5 TB RAM for connection state
  • 3.2 TB/day message row storage; 5.84 PB over 5 years (before replication)
  • 69 GB/s media → presigned S3 URLs; chat servers handle only tiny message frames
  • 6.93M status writes/sec for delivery/read receipts — these need their own storage tier with 30-day TTL

Interview Tips

  • Open by asking "1:1 only or group chat too?" — this single answer changes 40% of the design
  • When asked about message ordering, say "causal ordering within a conversation" not "global total ordering" — total ordering is unnecessarily strong and expensive
  • The "69 GB/s media insight" is a high-signal answer that shows systems thinking — lead with it when media comes up
  • Mention delivery receipts as a non-trivial problem: "sent/delivered/read × 10 group members = 30 status writes per message — at 231K msg/sec that's 6.93M writes/sec for status alone"
  • Presence is commonly underestimated: "500M users × heartbeat every 5s = 100M writes/sec — we need a batched sampling approach, not naive per-user Redis writes"
