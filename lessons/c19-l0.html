Requirements & Estimations

lesson
⏱ 7 min
📖 Chapter 19, Lesson 1

🎯 Learning Objectives

  • Elicit the 7 functional requirements and 4 explicit out-of-scope boundaries that define a file-sync system vs. a document editor
  • Derive upload QPS, chunk throughput, and storage growth numbers that justify a content-defined chunking architecture
  • Explain why 11.6 GB/s aggregate upload bandwidth forces presigned S3 URLs — identical reasoning to Instagram's 36 GB/s insight
  • Calculate the deduplication savings (30–50% storage reduction) and delta-sync savings (90%+ bandwidth on edits) that interviewers expect you to quantify

Step 1 — Clarifying Questions

Always open by scoping the problem. Dropbox and Google Drive are architecturally identical; the interviewer wants to see you isolate the hard parts.

Step 4 — Back-of-Envelope Estimation

Users & Operations

Registered users:        500M
DAU:                      50M   (10% activation rate)
File operations/user/day:  10   (creates, edits, deletes, renames)
Total file ops/day:       500M
Peak multiplier:           8×   (business hours, multi-timezone)

File ops/sec (average):   500M ÷ 86,400          =  5,787 ops/sec
File ops/sec (peak):      5,787 × 8              = 46,296 ops/sec

Chunk Throughput (the critical number)

Average file size:          4 MB  (documents, code, PDFs — not media)
Average chunk size:         4 MB  (Rabin CDC target)
Chunks per file op:         1     (most edits touch 1–2 chunks via delta sync)

Chunk uploads/sec (avg):   5,787 × 1             =  5,787 chunks/sec
Chunk uploads/sec (peak):  46,296                = 46,296 chunks/sec

NEW chunks after dedup:    5,787 × 50%           =  2,894 new chunks/sec
Aggregate upload BW:       2,894 × 4 MB          = 11.6 GB/sec
Key insight: 11.6 GB/s aggregate bandwidth cannot pass through API servers — each API server at 10 Gbps NIC would need 9+ servers just for data transfer, adding zero value as pure pipes. The solution is presigned S3 URLs: clients upload chunks directly to S3, bypassing API servers entirely. This is the same insight as Instagram's 36 GB/s photo upload problem.

Storage Math

Raw data per user:               500 MB average utilized storage
Total raw:                       500M × 500 MB    = 250 PB
After chunk-level dedup (30%):   250 PB × 0.70    = 175 PB unique chunks
After S3 3× replication:         175 PB × 3       = 525 PB physical storage

5-year growth (40% CAGR):
  Year 1: 175 PB → Year 5: 175 × (1.4)^4        ≈ 944 PB ≈ ~1 EB unique chunks

Version history overhead:
  180 versions × average delta = 1 chunk (4 MB) per version
  Full-copy alternative:       180 × 40 MB = 7.2 GB per file
  Chunk-snapshot approach:     40 MB base + 179 × 4 MB delta = 756 MB per file
  Savings:                     7.2 GB → 756 MB = 9.5× reduction

Metadata Storage

Files per user:              10,000 files average
Total files:                 500M × 10,000         = 5 trillion file records
File metadata row size:      ~200 bytes
Total metadata:              5T × 200B              = 1 PB (requires sharded PostgreSQL)

Implication: shard metadata DB by user_id from day one.
             Current-version metadata → PostgreSQL (sharded)
             Full version history     → Cassandra (append-optimized)

Sync Connections

DAU:                          50M
Devices per active user:       2 (laptop + phone)
Concurrent connections (20%):  50M × 2 × 0.20     = 20M concurrent WebSockets
Memory per connection:         2 KB
Total connection state:        20M × 2 KB           = 40 GB RAM
Sync servers needed:           200 servers × 100K connections + 200 MB RAM each

Key Takeaways

  • 11.6 GB/s upload bandwidth → presigned S3 URLs are non-negotiable; API servers cannot be in the data path
  • 30–50% dedup from content-defined chunking (SHA-256 content-addressed storage) saves ~75 PB
  • Delta sync: editing 1 byte in a 40 MB file uploads 4 MB (1 chunk), not 40 MB — 90% bandwidth saving
  • Version history: chunk-hash snapshots store 180 versions at 9.5× less cost than full copies
  • Metadata sharding: 5 trillion file records require sharded PostgreSQL by user_id from the start
  • 20M concurrent WebSockets fit on 200 sync servers at 100K connections each (40 GB total state)

Interview Tips

  • Lead with the "presigned URL" insight early — it shows you've thought about data path, not just control path
  • Distinguish Dropbox from Google Docs explicitly: file sync = eventual consistency + conflict copies; collaborative editing = OT/CRDT + strong consistency
  • The dedup math (30–50%) and delta-sync math (90% BW saving) are interviewer-expected numbers — memorize them
  • Version history as chunk-hash snapshots (not full copies) is the key storage optimization — explain it as "a version is just an ordered list of chunk hashes"
  • When asked about conflicts: "last-write-wins loses data; we create a conflict copy and let the user resolve" — Dropbox's actual policy
