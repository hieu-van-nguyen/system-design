🎯 Learning Objectives

  • Implement a trie that stores top-K suggestions at every node, eliminating runtime ranking
  • Explain Patricia trie (radix tree) compression and why it reduces memory 3–5× over a standard trie
  • Design a safe offline trie update strategy using double-buffering to avoid serving stale data during rebuilds
  • Serialize a trie to Redis as a flat hash map (prefix → JSON[top5]) for O(1) lookup at 4M QPS

Deep Dive — Trie Data Structure

1. Trie Node Structure

A trie (prefix tree) is the foundational data structure for typeahead. Each node represents a character; a path from the root to any node spells a prefix. The naive implementation has two problems at 4M QPS:

  1. Slow ranking: To find the top-5 suggestions for prefix "wea", you must traverse all leaf descendants and rank them — O(N log K) where N = number of queries with that prefix.
  2. Deep traversal: A 10-character prefix requires 10 pointer dereferences, each potentially a cache miss.

The solution: pre-compute and cache top-K at every node.


// Trie node with pre-cached top-K suggestions
class TrieNode {
    Map<Character, TrieNode> children;  // 'a'→node, 'b'→node, ...
    boolean isEnd;                        // true if this node is a complete query
    long frequency;                       // how many times this query was searched
    List<Suggestion> topK;              // ← PRE-COMPUTED: top-5 suggestions for this prefix

    TrieNode() {
        this.children = new HashMap<>();
        this.topK = new ArrayList<>();
    }
}

class Suggestion {
    String query;     // "weather forecast"
    double score;     // blended ranking score
}

With top-K pre-cached at each node, a lookup for prefix "wea" is:

  1. Traverse: root → 'w' → 'e' → 'a' (3 pointer dereferences)
  2. Return: node.topK — already ranked, zero computation at query time

Time complexity: O(L) where L = prefix length. Typically L ≤ 10 characters.

2. Ranking Score

Each suggestion at a node is ranked by a blended score:


// score = frequency × recency_decay × quality_boost
score(query) = frequency(query, 7d_window)
             × exp(-λ × days_since_last_searched)   // λ = 0.1 for 7-day half-life
             × quality_multiplier                    // 1.0 for most; 0.5 for low-quality; 1.2 for promoted

// Examples at prefix "wea":
// "weather"          : frequency=8,500,000 × decay=1.0  × quality=1.0  → score=8,500,000
// "wearable"         : frequency=1,200,000 × decay=0.98 × quality=1.0  → score=1,176,000
// "weather forecast" : frequency=2,800,000 × decay=1.0  × quality=1.0  → score=2,800,000
// "weapons"          : frequency=400,000   × decay=0.95 × quality=0.5  → score=190,000
💡 Why Not Pure Frequency? A query searched 10M times 18 months ago should rank below one searched 500K times last week. The recency decay (exponential with 7-day half-life) ensures trending queries surface quickly while old queries fade naturally — without requiring a separate "trending" computation.

3. Top-K Update Algorithm

When inserting a new query into the trie, you must update the top-K list at every ancestor node along the path:


// Update trie with query "weather" (score=8,500,000)
void insert(TrieNode root, String query, double score) {
    TrieNode node = root;
    for (char c : query.toCharArray()) {
        node.children.putIfAbsent(c, new TrieNode());
        node = node.children.get(c);
        updateTopK(node, query, score);  // update at EVERY ancestor
    }
    node.isEnd = true;
    node.frequency = score;
}

void updateTopK(TrieNode node, String query, double score) {
    // Min-heap of size K for O(log K) insertion
    if (node.topK.size() < K) {
        node.topK.add(new Suggestion(query, score));
    } else if (score > node.topK.peek().score) {
        node.topK.poll();  // remove lowest
        node.topK.add(new Suggestion(query, score));
    }
    // Sort descending so topK[0] is highest ranked
    // (in practice: use a sorted structure or sort once at build time)
}

4. Patricia Trie (Compressed Trie)

A standard trie wastes memory on single-child chains. For example, "weather", "weathered", "weathering" share the prefix "weather" — storing 7 separate nodes for w-e-a-t-h-e-r is wasteful when no branching occurs until the 8th character.


// Standard trie (7 nodes for "weather"):
root → w → e → a → t → h → e → r[END, topK]

// Patricia trie (1 compressed node):
root → "weather"[END, topK]
       ├── "ed"[END]
       └── "ing"[END]

// Memory savings: 3–5× for typical English query datasets
AspectStandard TriePatricia Trie
Memory (1B queries)~100 GB~20–30 GB
Lookup timeO(L) character stepsO(L) character comparisons (same asymptotically)
Insert complexityO(L)O(L) + possible node split
Cache localityPoor (one pointer per character)Better (compressed node reads sequentially)
Use caseSimple implementation, small datasetsProduction (Google, Bing) — memory matters at scale

5. Serialization to Redis

An in-memory trie object is not directly shareable across 100+ Suggestion Service nodes. The solution: serialize the trie to a flat Redis hash map during the offline build phase.


// Trie serialized as Redis hash:
// Key: "trie:en" (one hash per language)
// Field: prefix string
// Value: JSON array of top-5 suggestions

HSET trie:en "w"   '[{"q":"walmart","s":9200000},{"q":"weather","s":8500000},{"q":"wikipedia","s":7800000},{"q":"walmart+","s":6100000},{"q":"wordle","s":5400000}]'
HSET trie:en "we"  '[{"q":"weather","s":8500000},{"q":"weather forecast","s":2800000},{"q":"wearable","s":1200000},{"q":"webmd","s":980000},{"q":"weather today","s":870000}]'
HSET trie:en "wea" '[{"q":"weather","s":8500000},{"q":"weather forecast","s":2800000},{"q":"weather today","s":870000},{"q":"wearable","s":1200000},{"q":"wearable tech","s":410000}]'

// Lookup at query time (O(1)):
suggestions = HGET trie:en "wea"
→ parse JSON → return top-5
⚠️ Prefix Space Explosion: You don't store ALL possible prefixes. A query "machine learning" has 16 prefixes (m, ma, mac, ..., machine learning). With 1B queries × avg 10 prefixes each = 10B Redis fields — too large. Solution: store only prefixes where at least one popular query exists. Using a trie during build ensures you only serialize reachable nodes, not the full prefix space.

6. Online vs. Offline Updates

A common candidate mistake: "Update the trie in real-time for every query." This breaks at scale:

StrategyWrite PathProblem
Online (real-time) updateEach query completion → update trie node + all ancestorsLock contention on hot nodes (e.g., "w" is updated 98K times/sec). Distributed locking adds 10–50ms latency.
Offline batch rebuildKafka log → Flink 7-day aggregation → full trie rebuild every 15 min → atomic Redis RENAME15-minute lag for new trending queries. Acceptable for typeahead.
Hybrid (online + offline)Online updates to a separate "trending" Redis hash (top-50 trending queries); offline trie for historicalAdded complexity; merge at serve time. Used at Twitter/Google for breaking news.

Double-buffer pattern for safe trie swaps:


// Trie Builder publishes to "trie:en:staging" (not live key)
HSET trie:en:staging "w"   '[...]'
HSET trie:en:staging "we"  '[...]'
// ... write all 10B prefixes to staging key ...

// Atomic hot-swap — zero downtime, no locks needed:
RENAME trie:en:staging trie:en
// Old key is atomically replaced; next HGET "trie:en" reads new data

Key Takeaways

  • Top-K pre-computation is the core optimization: Without it, every query requires O(N) leaf traversal. With it, lookup is O(L) — the length of the prefix.
  • Patricia trie saves 3–5× memory: Collapsing single-child chains from 100 GB to ~20 GB makes the difference between needing 10 Redis nodes vs. 2.
  • Score = frequency × recency decay: Pure frequency rewards stale queries; the exponential decay (λ=0.1, 7-day half-life) surfaces trending content without a separate trending system.
  • Offline batch updates with RENAME: Never update the live trie under lock. Build to a staging key, then atomic RENAME for zero-downtime swap.
  • Serialization to Redis flat hash: The in-memory trie is for building; the serving layer uses a flat hash (prefix → JSON). This decouples build complexity from serve latency.
  • Top-K update requires touching every ancestor: Inserting "weather forecast" updates nodes for "w", "we", "wea", "weat", ..., "weather forecast" — O(L × log K) per insertion during build.

Interview Tips

  • Draw the trie node with topK field: Most candidates draw a trie without the cached top-K. Adding this field is the key insight that unlocks O(1) serving — draw it explicitly and explain why it's there.
  • Explain why online updates don't work: The "w" node is the parent of every query starting with 'w'. At 98K writes/sec, this single node becomes a distributed lock bottleneck. Offline batch rebuilds sidestep the problem entirely.
  • Mention Patricia trie proactively: Even if you don't go deep, saying "in production we'd use a compressed Patricia trie to reduce memory 3–5×" signals familiarity with real-world tradeoffs.
  • Distinguish build-time trie from serve-time Redis hash: The in-memory trie object is used during the 15-minute build; the Redis flat hash is what the Suggestion Service actually queries at 4M QPS. Conflating the two is a common mistake.
  • The RENAME pattern prevents thundering herds: If you updated individual Redis keys one-by-one, requests during the update window see partial data. RENAME makes the entire swap atomic.
