Deep Dive — Message Storage & Ordering

lesson
⏱ 10 min
📖 Chapter 20, Lesson 3

🎯 Learning Objectives

  • Design the Cassandra schema for messages using conversation_id as partition key and Snowflake message_id as clustering column — and explain why this enables O(1) pagination
  • Explain the 3-state message status lifecycle (SENT → DELIVERED → READ) and how receipt fan-back works without creating a hot partition
  • Justify Cassandra over PostgreSQL for 231K writes/sec using LSM-tree write amplification math
  • Design idempotent message send using client_msg_id dedup and explain what happens on retry after a network drop

1. Why Cassandra for Message Storage

The write throughput problem

Message writes:      231K messages/sec
Status writes:       231K × 3 states × 10 avg recipients = 6.93M status writes/sec
Total writes:        ~7.2M rows/sec

PostgreSQL limits:
  Single node:       ~5K writes/sec (MVCC + WAL + B-tree update overhead)
  To reach 7.2M/sec: 7.2M ÷ 5K = 1,440 PostgreSQL instances — operationally impossible

Cassandra limits:
  Single node:       ~50K writes/sec (LSM-tree: sequential write to MemTable → SSTable flush)
  To reach 7.2M/sec: 7.2M ÷ 50K = 144 Cassandra nodes — manageable (Messenger uses ~thousands)

Why Cassandra's LSM-tree wins for chat

B-tree (PostgreSQL/MySQL):
  Write path: find B-tree leaf page → random I/O → update in place → WAL
  Random I/O kills throughput for write-heavy workloads
  Compaction: immediate B-tree rebalance on every write

LSM-tree (Cassandra/HBase):
  Write path: append to in-memory MemTable → sorted → flush to SSTable (sequential write)
  Sequential I/O: disk throughput 500 MB/s vs. ~1 MB/s random IOPS
  Background compaction: merges SSTables offline, not blocking writes
  Result: Cassandra achieves 400× more writes/sec per node than PostgreSQL

Access pattern fit

Message reads: "load last 50 messages in conversation c789"
  Query: SELECT * FROM messages WHERE conv_id = 'c789' ORDER BY message_id DESC LIMIT 50

Cassandra wide-row model:
  Partition key: conv_id → all messages for one conversation on same node
  Clustering key: message_id DESC → pre-sorted; LIMIT 50 = read 50 contiguous rows = O(1)
  No index needed; no full table scan; no JOIN

PostgreSQL equivalent:
  INDEX(conv_id, message_id DESC) helps, but:
  - B-tree index lookup → random I/O across pages
  - At 20B messages: index itself = 20B × 16 bytes = 320 GB index just for messages table
  - Hot conversations = hot B-tree pages = lock contention

2. Cassandra Schema — Messages

-- Primary messages table
CREATE TABLE messages (
    conv_id         UUID,            -- conversation identifier (partition key)
    message_id      BIGINT,          -- Snowflake ID (41-bit ts + 10-bit server + 12-bit seq)
    sender_id       BIGINT,
    msg_type        TEXT,            -- 'text', 'image', 'video', 'voice', 'reaction', 'system'
    content         TEXT,            -- text content OR null for media
    media_url       TEXT,            -- CDN URL for media messages
    media_type      TEXT,            -- 'image/jpeg', 'video/mp4', etc.
    thumbnail_b64   TEXT,            -- inline thumbnail (50×50px JPEG, base64)
    reply_to_id     BIGINT,          -- message_id of parent (for replies)
    client_msg_id   UUID,            -- client-generated dedup key
    created_at      TIMESTAMP,
    is_deleted      BOOLEAN DEFAULT FALSE,    -- soft-delete (message "unsend")
    PRIMARY KEY (conv_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC)  -- newest first for pagination
  AND compaction = { 'class': 'TimeWindowCompactionStrategy',
                     'compaction_window_unit': 'DAYS',
                     'compaction_window_size': 1 }
  -- TWCS: compacts messages within same day together → efficient TTL expiry
  AND default_time_to_live = 0;   -- no TTL on messages (permanent history)

-- Dedup table: prevents duplicate messages on client retry
CREATE TABLE message_dedup (
    client_msg_id   UUID    PRIMARY KEY,
    message_id      BIGINT,
    created_at      TIMESTAMP
) WITH default_time_to_live = 86400;   -- 24h TTL (retries only happen within minutes)

-- Message status (delivery + read receipts)
CREATE TABLE message_status (
    conv_id         UUID,
    message_id      BIGINT,
    user_id         BIGINT,          -- recipient user_id
    status          TEXT,            -- 'DELIVERED', 'READ'
    updated_at      TIMESTAMP,
    PRIMARY KEY ((conv_id, message_id), user_id)
) WITH default_time_to_live = 2592000;  -- 30 days TTL (status older than 30d irrelevant)

3. Message ID — Snowflake for Ordering

Problem: multiple chat servers receive messages for the same conversation concurrently.
         Server S1 processes message A, Server S2 processes message B simultaneously.
         How do we guarantee A appears before B if A was sent first?

Snowflake ID structure (64 bits):
  [63..22] = 41 bits = milliseconds since epoch (Jan 1, 2020)
              → unique for 69 years
  [21..12] = 10 bits = server_id (1024 possible chat servers)
  [11..0]  = 12 bits = per-server sequence (4096 messages per ms per server)

Why Snowflake preserves causal ordering:
  - Messages from the same client arrive at the same server (L4 sticky routing)
  - Same server: sequence monotonically increases → A.id < B.id if A sent before B
  - Same millisecond, same server: sequence bits differentiate → still ordered
  - Cross-server, same millisecond: server_id breaks ties (not causally significant)
    → acceptable: two users sending simultaneously have no causal relationship

Ordering guarantee: strict causal ordering within a single conversation, per sender.

Why NOT UUIDs (UUID v4):
  - Random → no temporal ordering
  - Cassandra sorts clustering column → random UUIDs scatter across SSTable = terrible read performance
  - 128 bits vs 64 bits = 2× storage

Why NOT database sequences:
  - Requires round-trip to sequence generator on every message
  - Generator becomes bottleneck at 231K msg/sec
  - Snowflake: generated locally on chat server, zero coordination needed

4. Message Read Flow — Pagination

Client: "Load conversation c789, last 50 messages"

Initial load:
  GET /v1/conversations/c789/messages?limit=50

  Cassandra query:
    SELECT * FROM messages
    WHERE conv_id = 'c789'
    ORDER BY message_id DESC
    LIMIT 50
  → Returns: messages 50 to 1 (most recent first)
  → Response includes: messages[], next_cursor: message_id[50]

Scroll up (load older messages):
  GET /v1/conversations/c789/messages?limit=50&before=8675000

  Cassandra query:
    SELECT * FROM messages
    WHERE conv_id = 'c789'
      AND message_id < 8675000
    ORDER BY message_id DESC
    LIMIT 50
  → Fetches next 50 older messages in O(1) (no offset, no count(*))

Why cursor over offset:
  OFFSET 50 in SQL = scan and discard first 50 rows on every page request
  At page 100 of a chat: OFFSET 5000 = scan 5000 rows to discard them
  Cursor (message_id < X): always reads exactly 50 rows regardless of depth

5. Delivery Receipt System

3-state lifecycle:
  ┌─────────┐         ┌───────────┐         ┌──────┐
  │  SENT   │────────▶│ DELIVERED │────────▶│ READ │
  │  (✓)    │         │  (✓✓)     │         │ (🔵) │
  └─────────┘         └───────────┘         └──────┘
  Server has msg      Recipient app          Recipient opened chat
  in Kafka/Cassandra  received over WS       and viewed message

Receipt write path (DELIVERED):
  Bob's device receives message via WebSocket
  Bob's app: POST /v1/receipts { message_id: 8675309, status: "DELIVERED" }
    (or: send WebSocket frame { type:"receipt", ... })
  Chat server: INSERT INTO message_status (conv_id, msg_id, user_id, status='DELIVERED', updated_at)
  Chat server: route receipt to Alice via connection registry → Alice sees ✓✓

Receipt write path (READ):
  Bob opens the conversation in the app (not just receives message)
  Bob's app: POST /v1/receipts { conv_id: "c789", up_to_message_id: 8675309, status: "READ" }
  Batch receipt: marks all messages up to 8675309 as READ for Bob
  Cassandra: UPDATE message_status SET status='READ' WHERE conv_id=? AND message_id <= ? AND user_id=?
  Alice sees: 🔵 (blue tick) on all messages up to 8675309

Hot partition problem:
  If Alice sends 1,000 messages and 500M people receive (viral post scenario — not relevant for chat)
  For chat (bounded group, ≤ 500 members): max 500 status rows per message → not a hot partition
  For broadcast scenarios: use aggregated counters instead of per-user rows

6. Idempotent Message Send — Client Dedup

Failure scenario:
  1. Alice sends message; frame arrives at chat server
  2. Chat server publishes to Kafka, ACKs back to Alice
  3. ACK lost in transit (network drop)
  4. Alice's app sees timeout → retries with SAME frame + same client_msg_id

Without dedup: Bob receives "Hey Bob" twice

With client_msg_id dedup:
  1. Chat server receives frame with client_msg_id = "abc-uuid"
  2. Check: SELECT message_id FROM message_dedup WHERE client_msg_id = 'abc-uuid'
     → Hit: return existing message_id, skip re-processing
     → Miss: process normally, INSERT INTO message_dedup (24h TTL)

Client generates client_msg_id:
  UUID v4 (random) generated at send time
  Same UUID retried across reconnections
  UUID stored in client SQLite until ACK received

Cassandra LWT (Lightweight Transaction) alternative:
  INSERT INTO message_dedup ... IF NOT EXISTS
  → Paxos-based atomic check-and-insert; correct but 3× slower than regular INSERT
  → Use for critical dedup; regular INSERT + read for lower-latency paths

7. Message "Unsend" (Soft Delete)

Facebook Messenger and WhatsApp allow deleting sent messages within a time window.

Implementation:
  1. Sender: DELETE /v1/messages/{message_id}  (within 10 minutes of send)
  2. Server: UPDATE messages SET is_deleted=TRUE WHERE conv_id=? AND message_id=?
  3. Publish deletion event to Kafka: { type:"delete", message_id, conv_id }
  4. All recipients' clients receive deletion event via WebSocket
  5. Recipients' UI: replace message content with "Message was deleted" placeholder
  6. Message content cleared from Cassandra (tombstone)

Tombstone vs. actual delete:
  Cassandra DELETE creates a tombstone marker.
  Tombstone GC happens during compaction (gc_grace_seconds = 10 days).
  During gc_grace window: tombstone is returned as "no content" to reads.
  After gc_grace: tombstone purged; row truly gone.

Time window enforcement:
  Server checks: message.created_at > NOW() - INTERVAL '10 minutes'
  If outside window: return 403 Forbidden

Key Takeaways

  • Cassandra is the only viable choice for message storage at 231K writes/sec + 6.93M status writes/sec — PostgreSQL would need 1,440 instances
  • Snowflake ID = implicit ordering: time-ordered 64-bit IDs eliminate the need for a separate sort column and enable efficient range scans on the clustering key
  • Cursor pagination is O(1) regardless of depth: `WHERE message_id < cursor LIMIT 50` always reads exactly 50 rows; OFFSET reads cursor+50 rows
  • client_msg_id is the idempotency key: 24h TTL in Cassandra dedup table prevents duplicates on retry without LWT overhead
  • Status rows expire in 30 days: delivery state older than 30 days is irrelevant; TTL GC is automatic in Cassandra (TWCS compaction strategy)

Interview Tips

  • When asked "why not MySQL/PostgreSQL?" — give the write throughput math: 7.2M writes/sec ÷ 5K per PostgreSQL = 1,440 nodes; Cassandra = 144 nodes
  • Mention TWCS (TimeWindowCompactionStrategy) for messages: "messages are append-only and time-ordered; TWCS compacts messages within same day, making TTL expiry and old message archival cheap"
  • When asked about message ordering across servers: "Snowflake IDs have server_id bits; within a client-server pair, ordering is strict; cross-server on same ms is a tie-break by server_id — no causal relationship to violate"
  • For "unsend": proactively mention the gc_grace window — "tombstones persist for gc_grace_seconds (10 days); truly gone after compaction, which satisfies GDPR Article 17 within 30 days"
  • Read receipt aggregation for groups: "for a 500-member group, we store 500 status rows per message; we don't do this for 1:1 — the schema handles both because message_status has user_id as clustering column"
