Requirements & Location-Based Search

A "find nearby places" system (Yelp-style search for restaurants/shops) answers a deceptively simple question — which of millions of static points on a map fall within a radius of the user? — at a scale where scanning every place's coordinates on every query is a non-starter. The design hinges on building a spatial index that turns "search a radius" into a handful of lookups instead of a full table scan.

1. Clarifying Questions

QuestionWhy it matters
Are places static (restaurants, shops) or moving (people, vehicles)?Static places support a periodically-rebuilt spatial index; moving entities need a different structure (contrasted in Lesson 3)
What's the typical search radius — a few blocks or a whole city?Drives how coarse/fine the spatial index's leaf granularity should be
How are results ranked — pure distance, rating, or a blend?Determines whether the index alone can answer the query or a ranking pass is needed after retrieval (Lesson 3)
How often do places get added/updated (new business, hours change)?Low write rate relative to reads means we can favor a read-optimized index over one built for fast writes
Do we need category/filter support (only show "coffee shops")?Adds a filtering dimension on top of pure spatial retrieval

For this design: static places, radius searches from ~1km to ~50km, ranking blends distance with rating, place updates are infrequent relative to searches, and category filters are supported.

2. Functional Requirements

  • Given a lat/lng and radius, return nearby places ranked by relevance (distance + rating)
  • Support category/keyword filters on top of the spatial radius search
  • Add, update, and remove place records (name, category, coordinates, rating, hours)
  • Return results with pagination as the user pans/zooms the map

3. Non-Functional Requirements

AttributeTarget
LatencySearch p99 < 100-200ms — users expect the map to populate near-instantly while panning
ScalabilitySupport hundreds of millions of places and tens of thousands of searches/sec
ConsistencyEventual consistency is fine — a new restaurant appearing in search a minute late is acceptable
AvailabilityFavor availability; a stale index beats a search that fails to return results
💡 Interview signal: Say explicitly "this is a read-heavy, write-light, eventually-consistent problem" up front — it justifies favoring a read-optimized spatial index that's periodically rebuilt rather than one engineered for real-time writes.

4. Traffic Estimation

Assumptions:
  Total places        = 200,000,000  (200M)
  DAU                 = 500,000,000  (500M)
  Searches/user/day    = 5

Searches/day  = 500M * 5                = 2,500,000,000 (2.5B)
Searches/sec  = 2.5B / 86,400            ≈ 29,000 searches/sec (avg)
Searches peak ≈ 29,000 * 3 (meal-time rush) ≈ 90,000 searches/sec (peak)

Place writes are comparatively tiny — new businesses/updates measured in the
thousands/day, not thousands/sec — so this is overwhelmingly a read-scaling problem.

5. Storage Estimation

Place record (name, address, category, hours, rating, description): ~1 KB/place
  200M places * 1 KB                  ≈ 200 GB total place data

Spatial index entry (place_id + lat + lng, the minimum needed to index by location):
  place_id (8 bytes) + lat (8 bytes) + lng (8 bytes) = 24 bytes/place
  200M * 24 bytes                     ≈ 4.8 GB  ≈ 5 GB

// The ~5GB index is the key number: it comfortably fits in memory on a
// handful of hosts. That means sharding the index is driven by *query
// hotspots* (dense cities generating disproportionate traffic), not by
// index size — a distinction that shapes the sharding strategy in Lesson 3.
💡 Interview signal: Computing that the index (~5GB) is orders of magnitude smaller than the full place data (~200GB) is the insight that unlocks "keep the spatial index in memory, fetch full place details from a separate store on a cache/index hit."

6. Interfaces (Internal)

APIPurpose
searchNearby(lat, lng, radiusKm, filters, cursor) → places[], nextCursorPrimary read path — spatial index lookup + ranking (Lessons 2-3)
addPlace(placeData) → placeIdInsert a new place; updates the spatial index (batched/periodic, per NFRs)
updatePlace(placeId, fields)Update mutable fields (hours, rating); coordinate changes are rare and trigger re-indexing

Key Takeaways

  • This is a read-heavy (~29K/sec avg, ~90K/sec peak), write-light, eventually-consistent problem — optimize for read latency
  • Full place data (~200GB) and the spatial index (~5GB) are sized separately — the index is small enough to live entirely in memory
  • Because writes are rare, the spatial index can be a structure optimized for read performance, even if rebuilding it is relatively expensive
  • Static places (this chapter's focus) allow periodic index rebuilds — moving entities would break that assumption (see Lesson 3)

Interview Tips

  • Lead with "static vs. moving entities" as your first clarifying question — it's the single biggest fork in the design
  • Compute the index size separately from the full dataset size — it's the number that justifies an in-memory spatial index
  • State the read:write imbalance explicitly; it's the reasoning behind every caching and indexing decision that follows
  • Don't over-specify ranking here — note that distance + rating are the inputs, and defer the scoring formula to the ranking lesson
