Deep Dive — Ride Matching & Dispatch

Lesson 2 built the live driver-location index (Redis geohash, ~1M drivers, refreshed every ~4s). Matching turns that index into an actual assigned trip: find candidates, rank them, offer the ride, and guarantee exactly one driver ends up assigned — even though many riders and drivers act concurrently on overlapping geo-cells.

1. Candidate Selection

1. Rider requests ride at (lat, lng)
2. GEORADIUS driver_locations lng lat 2km ASC   // reuse Lesson 2's Redis geo-index
   → returns driverIds sorted by straight-line distance, e.g. 15 candidates
3. Filter to status == "available" (from driver:{id}:meta)
4. Keep top ~5 by straight-line distance as an initial shortlist
   // straight-line is cheap and good enough to shortlist; final ranking needs
   // road-network distance, not haversine (below)

Straight-line distance is used only to shortlist — a driver 400m away across a river or highway may be 8 minutes away by road, while one 800m away on a direct street is 3 minutes away. Ranking on haversine distance alone is a common interview mistake.

2. ETA Ranking via Road-Network Routing

ApproachTradeoff
Haversine (straight-line) distanceO(1), no external call — fine for shortlisting, wrong for final ranking (ignores roads, one-ways, traffic)
Road-network routing engine (e.g., precomputed graph + contraction hierarchies)Accurate ETA, but too expensive to run against every online driver — run only against the ~5-driver shortlist

The shortlist (cheap, wide) feeds the routing engine (expensive, narrow): 5 ETA lookups per ride request is affordable at ~350 requests/sec peak; 1M ETA lookups per request would not be.

💡 Interview signal: Explicitly stating "cheap filter first, expensive rank second" — the same funnel shape used in search/recommendation systems — signals you generalize patterns rather than solving each system from scratch.

3. Offer / Accept Dispatch State Machine

REQUESTED → OFFERED(driver_1) → [accept]  → MATCHED → EN_ROUTE → ...
                    │
                    └──[reject/timeout 10s]──► OFFERED(driver_2) → ...
                                                        │
                                          (all shortlist exhausted)
                                                        ▼
                                          EXPAND RADIUS + REQUEUE (below)
Dispatch styleTradeoff
Sequential offer (one driver at a time, 10s timeout)Simple, fair (nearest gets first refusal), but adds latency if several drivers decline in a row — chosen default
Broadcast offer (offer to all 5 shortlisted drivers, first accept wins)Lower worst-case latency, but wastes driver attention (4 of 5 offers are always "too late") and needs the same locking below to resolve the race

4. Preventing Double-Booking

Whichever dispatch style is used, two riders' matching processes could race to assign the same driver at the same instant. Location data is eventually consistent (Lesson 1), but the accept step must not be:

// Atomic compare-and-set on driver status, e.g. via Redis WATCH/MULTI or a Lua script
def accept_ride(driverId, rideId):
    status = GET driver:{driverId}:meta.status
    if status != "available":
        return CONFLICT   // already taken by another ride's accept
    SET driver:{driverId}:meta.status = "assigned" IF status == "available"  // CAS, atomic
    return OK

This is a single-key optimistic CAS, not a distributed lock across services — it stays cheap (sub-millisecond) because the driver's status lives in one Redis key. The rider-facing ride record only transitions to MATCHED after this CAS succeeds, guaranteeing exactly one rider per driver per moment.

💡 Interview signal: Naming this as "strong consistency scoped to a single key" ties directly back to Lesson 1's NFR — you don't need a distributed transaction across the whole system, just an atomic operation on the one piece of shared mutable state (driver status).

5. No Driver Accepts

If the shortlist is exhausted (all 5 declined or timed out), don't fail the ride — expand and retry:

attempt 1: radius = 2km  → shortlist of 5
attempt 2: radius = 5km  → shortlist of 5 (excluding already-declined drivers)
attempt 3: radius = 10km → shortlist of 5
  // Each expansion also relaxes the ETA-quality bar shown to the rider
  // ("your driver is a bit further away") rather than silently failing.
If still no match after N attempts → surface "no drivers available," which
is also a signal into the surge-pricing pipeline (Lesson 4): demand is
exceeding supply in this cell.

Key Takeaways

  • Shortlist cheaply by straight-line distance from the geo-index, then rank the shortlist expensively by road-network ETA — never route every online driver
  • Sequential offer-with-timeout is the simpler default; broadcast offer trades driver attention for lower worst-case latency
  • Double-booking is prevented with a single-key atomic CAS on driver status, not a distributed lock — consistent with location being eventually consistent but assignment being strongly consistent
  • An exhausted shortlist triggers radius expansion and requeue, not failure — and feeds directly into surge-pricing demand signals

Interview Tips

  • Don't rank drivers by haversine distance alone — interviewers listen for the road-network/ETA distinction
  • State explicitly how double-booking is prevented before being asked — it's one of the most probed correctness questions in this design
  • Compare sequential vs. broadcast dispatch with a concrete tradeoff (latency vs. wasted driver attention), not just "broadcast is faster"
  • Always answer "what if no driver accepts?" — radius expansion, not an error, is the expected answer
