Fan-Out Strategies: The Core Design Decision

Feed generation is the hardest problem in Instagram's design. State this explicitly — interviewers expect you to identify it unprompted. There are three approaches:

StrategyWrite CostRead CostProblem
Fan-out on WriteHigh: 1 post × 500K followers = 500K Redis writesO(1) ZREVRANGECelebrity problem: Ronaldo's post → 600M writes
Fan-out on ReadO(1) Cassandra insertO(following): 500 queries per feed load500 queries × 5ms = 2,500ms — catastrophically slow
Hybrid (chosen)Normal users onlyO(1) + O(celebrities) ≈ 10–20msBest of both worlds

Celebrity Threshold Derivation

Celebrity threshold question: at what follower count does fan-out on write become unacceptable?

Cristiano Ronaldo: 600M followers
Fan-out cost: 600M Redis ZADD ops per post
  Single Redis node throughput: ~50,000 ZADDs/sec
  100 Redis nodes in cluster: 5,000,000 ZADDs/sec
  Time to fan-out: 600M / 5,000,000 = 120 seconds = 2 MINUTES

  2 minutes is unacceptable for a post to appear in feeds.

Instagram threshold: 5M followers (vs Twitter's 1M)
  Reasoning: Instagram users post less frequently than Twitter users,
  so the write burst per post is more expensive per unit of content.
  5M × ZADD / (50K × 100 nodes) = 1 second — borderline acceptable.
  Set at 5M to provide headroom.

Zombie optimization (30% write savings):
  Skip fan-out for users inactive > 30 days
  ~30% of Instagram accounts are dormant
  231,400 writes/sec × 70% = 161,980 actual writes/sec
  Cold rebuild on first login: pull from Cassandra, repopulate cache async

Read-Time Celebrity Merge

At feed read time, for each celebrity the viewer follows:
  ZREVRANGE user_posts:{celeb_id} 0 4  → last 5 posts (Redis, ~1ms each)

If user follows 5 celebrities:
  5 × ZREVRANGE = 5ms total
  In-memory k-way merge of 5 + 500 pre-computed posts = 2ms

Total overhead vs no celebrities: ~7ms — within 300ms p99 budget easily

Timeline Cache Design

The feed cache is a Redis Sorted Set per user. The design must support fast writes (fan-out), fast range reads (feed load), and bounded memory (trim to top 500).

Redis Sorted Set per user:
  Key:    feed:{user_id}
  Score:  Unix timestamp (ms) × ranking_boost
          ranking_boost ∈ [0.5, 2.0] — ML affinity multiplier
  Member: post_id (8 bytes, Snowflake ID)

Operations:
  Fan-out write:  ZADD feed:{follower_id} {score} {post_id}    O(log N)
  Trim (async):   ZREMRANGEBYRANK feed:{user_id} 0 -501        O(log N + K)
  Read feed:      ZREVRANGEBYSCORE feed:{user_id} +inf {cursor} LIMIT 0 12
  Pagination:     next cursor = score of last returned post_id

Capacity math:
  Active users (logged in last 7 days): ~200M of 500M total
  Per-user set: 500 post_ids × 8 bytes = 4 KB per user
  Total: 200M × 4 KB = 800 GB
  Redis cluster: 13 nodes × 64 GB = 832 GB  → comfortable fit

Cache cold start (user returns after >7 days):
  Trigger async "feed rebuild" job:
    1. Fetch all followees from Follow Service (paginated)
    2. For each followee: ZREVRANGE user_posts:{id} 0 4  (last 5 posts)
    3. Score with affinity, merge, populate feed:{user_id}
  Until rebuild: serve directly from Cassandra (one-time, slower)
  UX: show spinner or "Updating your feed…" for ~3s
Why not use post_id as score directly? Snowflake IDs are monotonically increasing with time — using them directly as score would work for pure chronological feeds. But for ML-ranked feeds, the score must be timestamp × affinity_multiplier, so we need a float score. This is why we store score and post_id separately.

Feed Ranking: Chronological vs ML-Ranked

Chronological ("Following" Tab)

Score = timestamp (ms)  ← simple, predictable
ZREVRANGE returns newest first
No ML model needed — pure time ordering
Used for "Following" tab (user demand for transparency post-2022)

ML-Ranked ("Home" Tab)

Score = timestamp × affinity_multiplier × content_type_preference

affinity_multiplier: ML-derived float [0.5, 3.0]
  Based on: past likes, comments, profile visits, watch time per author
  Stored in Redis HASH: affinity:{viewer_id} → { author_id: score, ... }
  Updated: hourly Spark job on 30-day engagement history

content_type_preference: user's video/photo/carousel ratio (last 30 days)
  If user watches 80% videos: boost video posts by 1.5×
  Stored per-user in Redis: prefs:{user_id} → { video: 0.8, photo: 0.15, carousel: 0.05 }

Combined ranking score example:
  Post timestamp:       1724800000000 (ms)
  Affinity multiplier:  2.1 (you frequently like this author)
  Content preference:   1.4 (you prefer videos, this is a video)
  Final score:          1724800000000 × 2.1 × 1.4 = 5,068,992,000,000

Cold start (new user with <10 engagements):
  Fallback: popularity-based (top posts in user's detected country + language)
  After 10 engagements: switch to affinity-based ML ranking
  After 50 engagements: full personalization model

Diversity enforcement:
  Max 3 consecutive posts from same author
  Max 40% of 12-post page from any single topic cluster
  Post-ranking filter: reject if diversity rules violated, pull next candidate

Fan-Out Worker Design

Kafka topic: "post.created"
  Partitions: 2,000 (parallelism for fan-out workers)
  Key: user_id (all posts from same user → same partition → ordering)

Fan-out Worker logic (per Kafka partition):
  1. Consume post.created event { post_id, user_id, timestamp }
  2. Check poster's follower count: GET followers_count:{user_id} from Redis
     - If > 5M: skip fan-out (celebrity — pull model at read time)
     - If ≤ 5M: proceed
  3. Fetch follower list (paginated from Social Graph Service, batch 10,000):
     - Cache follower list in worker memory (TTL 30s) — avoid repeat DB hits
  4. Filter: skip followers with last_active > 30 days (inactive users set)
  5. For each batch of 1,000 active followers:
     Redis pipeline (single round trip):
       ZADD feed:{follower_1} {score} {post_id}
       ZADD feed:{follower_2} {score} {post_id}
       ...
       ZREMRANGEBYRANK feed:{follower_1} 0 -501  (trim to 500)
       ZREMRANGEBYRANK feed:{follower_2} 0 -501
  6. Acknowledge Kafka offset after batch complete

Throughput math:
  1,157 photo uploads/sec × 200 avg followers = 231,400 feed writes/sec
  × 70% active = 161,980 actual Redis ZADDs/sec
  With 2,000 partitions × 10 threads each = 20,000 concurrent workers
  Each handles ~8 feed writes/sec — well within capacity

Stories: Ephemeral Content Architecture

Design constraints:
  - Hard 24h TTL (not soft delete — the content must actually disappear)
  - View receipts: poster sees who viewed, for 48h
  - High write volume: 5,787 stories/sec
  - Data loss acceptable: ephemeral content, re-recordable

Redis data structures (all with EXPIRE):
  Story metadata:
    HSET story:{story_id} user_id {uid} media_url {url} created_at {ts}
    EXPIRE story:{story_id} 86400           ← 24-hour hard expiry

  User's active stories:
    ZADD user_stories:{user_id} {timestamp} {story_id}
    EXPIRE user_stories:{user_id} 86400

  View receipts:
    SADD seen:{story_id} {viewer_id}
    EXPIRE seen:{story_id} 172800           ← 48h (poster can check 48h)
    INCR story:{story_id}:view_count

  Close Friends:
    SADD close_friends:{user_id} {friend_id}  ← no TTL, persists

S3 lifecycle rule:
  s3://instagram-stories/{story_id}/{variant}.webp
  S3 lifecycle: delete after 25 hours  ← 1-hour grace beyond Redis TTL
  CDN TTL: max-age=3600 (short — story could be deleted by user early)

Stories feed (home screen rings):
  GET /api/v1/stories/feed:
  1. Fetch following list (cached in Feed Service, TTL 60s)
  2. For each followee: SMEMBERS user_stories:{followee_id} (batch MGET)
  3. Filter expired stories (Redis EXPIRE = story gone automatically)
  4. Check seen: SISMEMBER seen:{story_id} {viewer_id}
  5. Order: unseen first (sorted by poster recency), then seen
  6. Return story rings (one ring per user with active stories)

Why Redis-first (not PostgreSQL)?
  PostgreSQL TTL via background DELETE job: 500M stories/day
  = 5,787 DELETEs/sec → VACUUM overhead → I/O spikes
  Redis EXPIRE: TTL managed by Redis internals, O(1), no I/O spikes
  ✓ Native TTL is the correct tool for ephemeral content

Notification System

Notification types:
  | Event              | In-App | Push | Email |
  | Someone liked post | ✓      | ✓    | No    |
  | Someone retweeted  | ✓      | ✓    | No    |
  | New follower       | ✓      | ✓    | ✓     |
  | @mention           | ✓      | ✓    | ✓     |
  | Reply to comment   | ✓      | ✓    | No    |

Architecture:
  Kafka "notifications.raw"
  Producers: Post Service (like, comment), Follow Service (new follower)

Notification Fan-out Service (Flink consumer):
  1. Read event from Kafka
  2. Deduplication (prevent "you have 200 new like" spam):
     SET notif:{user_id}:{event_type}:{source_id} 1 NX EX 3600
     If key exists → skip (already notified in last hour)
  3. Aggregation (bundling):
     Flink 30s tumbling window per (post_id, event_type)
     "Alice liked your photo" × 47 events in 30s
     → "Alice and 46 others liked your photo"
     (Batch window prevents N individual notifications for viral posts)
  4. Route to channel:
     In-App: LPUSH notif_inbox:{user_id} {json}; LTRIM 0 99 (keep last 100)
     Push:   FCM (Android) / APNs (iOS) — batch up to 500 tokens per FCM call
     Email:  SES (only for follows + mentions; no push for likes)

Consistency Model Summary

ComponentModelJustification
Photo upload (S3 + Cassandra)Strong (write quorum)User's post must not vanish after 201 response
Feed cache (Redis)Eventual (< 30s)Fan-out takes up to 30s; imperceptible to users
Like / comment countsApproximate (±5, 60s lag)48,600 likes/sec; approximate is the right trade-off
Follow / UnfollowStrong (read-your-writes)Unfollow must be immediate — safety / harassment use case
Stories (Redis TTL)Eventual (AOF durability)Story loss on Redis failure (~0.01%/day) acceptable; ephemeral content
CDN mediaImmutableContent-addressed URLs eliminate consistency concern entirely
Private account accessStrong at read timeAccess checked per request — cannot pre-cache private content
NotificationsAt-least-onceDuplicate "Bob liked your photo" is better than missed notification
Key consistency insight: Instagram has two fundamentally different domains. Identity and access (follow state, private account status, block list) require strong consistency — these affect safety. Social metrics and feed (like counts, feed ordering, Explore recommendations) tolerate eventual consistency. Conflating these two in your design is the most common mistake in social system design interviews.

Key Takeaways

  • The celebrity threshold (5M followers) is derived from math, not intuition — be able to show the calculation
  • The hybrid fan-out model combines pre-computed feed (O(1) read) with read-time celebrity merge — neither pure approach works alone
  • Redis sorted sets with float scores enable ML-ranked feeds without changing the data structure — just change how you compute the score
  • Stories' Redis EXPIRE = 86400 is not just a convenience — it eliminates an entire background GC job and the risk of late expiry
  • Notification aggregation (30s Flink window) is essential for viral posts — without it, a post getting 10K likes fires 10K individual push notifications
  • Strong consistency for follow/unfollow is a safety feature, not a performance decision — unblocking someone who was blocked must be immediate
