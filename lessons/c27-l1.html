High-Level Design & Feed Generation

lesson
⏱ 14 min
📖 Chapter 27, Lesson 2

🎯 Learning Objectives

  • Lay out the Post/Feed/Social Graph/Ranking service architecture and how data flows between them
  • Compare pull (fan-out-on-read), push (fan-out-on-write), and hybrid feed generation models
  • Design the feed cache as a bounded, per-user sorted set of post references, not full content
  • Implement cursor-based pagination that stays stable as new posts are continuously inserted

High-Level Design & Feed Generation

Per Lesson 1's numbers: ~5,800 post writes/sec against ~116K feed reads/sec (avg), ~350K at peak. The high-level design has to answer one core question — do we compute each user's feed at read time, or precompute it ahead of time? — and everything else (services, cache shape, pagination) follows from that choice.

  • Post Service — validates and durably writes new posts; publishes a "post created" event to the queue
  • Social Graph Service — fast lookup of a user's friends/follows, and (for the celebrity path) their follower count
  • Feed Service — serves getFeed(); reads from the feed cache, falls back to on-demand generation on a cache miss
  • Ranking Service — scores candidate posts for a user (Lesson 4); called either at fan-out time or at read time depending on the model below

2. Pull vs. Push vs. Hybrid Feed Generation

ModelHow it worksTradeoff
Pull (fan-out-on-read)On getFeed(), fetch the user's friend list, pull their recent posts, merge and rank on the flyCheap writes, but every read does an expensive fan-in across hundreds of friends — read latency scales with friend count, and reads outnumber writes 20:1
Push (fan-out-on-write)On createPost(), immediately write the post ID into every follower's precomputed feed cacheReads become a cheap cache lookup, but a celebrity post triggers millions of fan-out writes (recall: 1.7M writes/sec if applied to every post)
HybridPush for normal users (bounded fan-out); pull-and-merge-at-read-time for celebrity/high-follower accountsBest of both — bounds worst-case write amplification while keeping reads cheap for the common case; adds a merge step at read time (Lesson 3)
💡 Interview signal: Don't just say "hybrid" — explain why: pure push breaks on celebrities because fan-out cost scales with follower count, and pure pull breaks because it re-does the same expensive merge on every single read even though most users' friend lists barely change between requests. Hybrid bounds the worst case of each.

3. Feed Cache Shape

We chose push as the default, so the feed cache is a precomputed, per-user structure — not the full post content, just enough to render and page through:

feed:{userId} → sorted set (Redis ZSET)
  member = postId
  score   = rank_score (or timestamp, for chronological fallback)

  // Bounded to top ~500 entries per user (from Lesson 1: 4KB/user, ~4TB total)
  // Actual post content is fetched separately from the Post DB / a post-content
  // cache, keyed by postId — the feed cache only stores *references + order*.

4. Cursor-Based Pagination

Offset-based pagination (LIMIT 20 OFFSET 40) breaks when new posts are constantly being inserted at the top — a post can shift into a page the user already scrolled past, causing duplicates or skipped posts. Instead, the feed uses a stable cursor:

getFeed(userId, cursor=null, pageSize=20):
  entries = ZREVRANGEBYSCORE feed:{userId}
              max = cursor ?? +inf
              min = -inf
              LIMIT 0 pageSize
  nextCursor = score of the last entry returned
  return entries, nextCursor

// Client passes nextCursor back on the following request.
// Because the cursor is a score (not a row offset), inserting new posts
// above the cursor never shifts or duplicates entries below it.
💡 Interview signal: Naming the offset-pagination failure mode explicitly ("a post can shift into an already-scrolled page") shows you've hit this bug before, not just memorized "use cursors."

5. Cache Miss / Cold Start Path

  • New user or expired cache entry → Feed Service falls back to the pull path: fetch friend list, pull each friend's recent post IDs, merge-sort by score, write the result back into the feed cache
  • This fallback is intentionally the "slow path" — acceptable for rare cold starts, unacceptable as the default for 350K reads/sec at peak

Key Takeaways

  • Pull is cheap to write but expensive to read; push is cheap to read but expensive to write — a hybrid bounds both worst cases
  • The feed cache stores ordered post references (post ID + score), not full content — content is fetched separately
  • Cursor-based pagination (score-based) avoids the duplicate/skip bugs that offset-based pagination causes on a constantly-updating feed
  • A cache miss falls back to the same on-demand merge that the pull model does by default — it's a fallback path, not the primary path
  • Every architectural choice here traces back to the 20:1 read:write ratio established in Lesson 1

Interview Tips

  • Draw the service diagram first — Post/Feed/Social Graph/Ranking services plus the queue — then narrate data flow through it
  • Present pull, push, and hybrid as a genuine tradeoff table, not "hybrid is obviously correct" — show you understand what each gives up
  • Mention that the feed cache is bounded (e.g., top 500 posts) — an unbounded cache defeats the purpose of precomputation
  • Be ready to explain the cold-start/cache-miss path — interviewers often probe "what happens for a brand-new user?"
