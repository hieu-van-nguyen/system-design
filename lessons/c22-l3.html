Deep Dive — CDN & Metadata Management

🎯 Learning Objectives

  • Design the three-tier CDN (Edge PoP → Origin Shield → S3) and explain why content-addressed immutable URLs enable max-age=1 year caching for video segments
  • Contrast YouTube GGC and Netflix Open Connect: ISP co-location economics, cache fill strategy, and how each eliminates internet backbone egress for popular content
  • Design the metadata schema for watch history using Bigtable row key = user_id + reverse_timestamp — and explain why this enables O(50) sequential scan for "last 50 watched"
  • Build the consistency model table and explain the three-tier insight: creator writes (strong), social engagement (eventual), CDN segments (immutable)

1. CDN Architecture — Three Tiers


┌──────────────────────────────────────────────────────────────────────────────────────────────┐
│  TIER 1 — Edge PoP (co-located at ISP, ~1,000 locations globally)                            │
│  YouTube: Google Global Cache (GGC)    Netflix: Open Connect Appliance (OCA)                 │
│  Capacity per PoP: 10 TB SSD + 10 Gbps uplink                                               │
│  Cache hit rate for popular content: 95–99%                                                  │
│  Latency to viewer: 2–5ms (same city)                                                        │
└──────────────────────────────────────────┬───────────────────────────────────────────────────┘
                                           │ cache miss (5% of requests)
                                           ▼
┌──────────────────────────────────────────────────────────────────────────────────────────────┐
│  TIER 2 — Origin Shield (1 per geographic region, ~20 globally)                              │
│  Aggregates cache misses from all edge PoPs in a region                                      │
│  Prevents "thundering herd" when 1,000 ISPs miss the same new video simultaneously           │
│  Without shield: 1,000 PoPs × 1 miss = 1,000 S3 requests at video launch                   │
│  With shield: 1,000 PoP misses → 1 shield fetch → 1 S3 request                             │
│  Cache storage: 100 TB SSD (warm tier — recently popular videos)                             │
└──────────────────────────────────────────┬───────────────────────────────────────────────────┘
                                           │ origin shield miss (rare)
                                           ▼
┌──────────────────────────────────────────────────────────────────────────────────────────────┐
│  TIER 3 — Origin (S3 + internal storage)                                                     │
│  Long-tail videos (viewed < 10 times/day) — not cached at edge or shield                   │
│  Fetched directly from S3 on demand (or origin servers for DRM key delivery)                 │
└──────────────────────────────────────────────────────────────────────────────────────────────┘

2. Content-Addressed Segments — Why max-age=1 Year is Safe

Standard CDN problem:
  URL: https://cdn.example.com/video.mp4?version=3
  If content changes but URL stays same → CDN serves stale cached version
  Solution: short max-age (60s) → frequent origin fetches → high cost

YouTube/Netflix solution: content-addressed immutable URLs
  Segment URL: https://cdn.youtube.com/{video_id}/{quality}/{sha256_of_segment}.mp4
                                                           ↑
                                               SHA-256 hash embedded in URL

  Why this enables max-age=31536000 (1 year):
    If content changes → SHA-256 hash changes → URL changes → old URL never accessed again
    CDN never serves stale content because stale content has a DIFFERENT URL
    CDN can cache with max-age=1 year safely — no coordination with origin needed

  HTTP response headers for segments:
    Cache-Control: public, max-age=31536000, immutable
    ETag: "{sha256}"
    Content-Type: video/mp4

  Manifest URL (dynamic — updated when metadata changes):
    Cache-Control: public, max-age=60
    (shorter TTL: manifest embeds like_count, chapter info — needs periodic refresh)

Storage layout in S3:
  s3://yt-transcoded/{video_id}/{quality}/{sha256[0:4]}/{sha256}.mp4
  Two-level prefix (sha256[0:4]) for S3 partition distribution
  → Even with 800M videos × 21 versions = 16.8B objects, prefix ensures uniform distribution

3. Google GGC vs Netflix Open Connect

AspectYouTube (Google GGC)Netflix (Open Connect)
HardwareGoogle-owned servers at ISP facilitiesNetflix-designed OCA hardware (commodity server + SSDs)
Placement~1,000 ISPs globally; ISP hosts hardware~17,000 OCA deployments; ISP hosts Netflix's hardware
Cache fill strategyOn-demand (client request triggers fill from Google backbone)Proactive nightly fill: Netflix sends top-K videos to each OCA during off-peak hours
Cache hit rate~95% for popular videos~99%+ (proactive fill means most content already present)
Long-tail handlingServed from GGC (still Google infra, lower cache hit)Served from Netflix's own CDN or Akamai fallback
Egress savings~80% of traffic served from GGC (no internet transit)~95% of traffic served from OCA (proactive ensures popular titles always present)
Economic modelGoogle provides GGC free to ISPs; ISP saves bandwidth; Google saves transitNetflix provides OCA free to ISPs; ISP saves transit; Netflix saves CDN fees

Netflix Proactive Fill — Why It Works

Netflix content catalog: ~15,000 titles
Each title: 10 quality levels × HLS segments = 50,000 segments per title
Total content: 15,000 × 50,000 × avg 500 MB/segment = 375 PB — too large for any single OCA

Popularity distribution follows power law (Zipf's law):
  Top 200 titles = 80% of all views
  Top 200 × 10 qualities = 2,000 versions
  Each version: ~4 GB (movie average 2 hours × 5 Mbps avg)
  Top 200 titles' content: 2,000 × 4 GB = 8 TB

OCA storage: 100–200 TB SSD → comfortably fits top 200 titles
Nightly fill: Netflix sends next-day predicted top-200 to all OCAs (based on ML popularity model)
Result: next morning, 99% of demand is already present at the nearest OCA
         → 99% of traffic never touches Netflix's own infrastructure → massive cost savings

4. Metadata Schema — Watch History & Video Catalog

Video Catalog (PostgreSQL)

CREATE TABLE videos (
    video_id        UUID        PRIMARY KEY,
    uploader_id     BIGINT      NOT NULL,
    title           TEXT        NOT NULL,
    description     TEXT,
    duration_sec    INTEGER,
    manifest_url    TEXT,                    -- DASH .mpd URL on CDN
    thumbnail_url   TEXT,
    status          TEXT        NOT NULL     -- UPLOADING, PROCESSING, PUBLISHED, DELETED
        CHECK (status IN ('UPLOADING','PROCESSING','PUBLISHED','DELETED')),
    category        TEXT,
    tags            TEXT[],
    language        CHAR(5),                 -- ISO 639-1 language code
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    published_at    TIMESTAMPTZ,
    view_count      BIGINT      DEFAULT 0,   -- periodically updated from Redis
    like_count      BIGINT      DEFAULT 0,
    -- Sharding: shard by video_id % N_SHARDS
    -- Indexes: (uploader_id, created_at DESC), (status, published_at DESC) for "new videos" query
);

CREATE TABLE video_stats (
    video_id        UUID        PRIMARY KEY,
    view_count      BIGINT      DEFAULT 0,   -- flushed from Redis INCR every 60s
    like_count      BIGINT      DEFAULT 0,
    dislike_count   BIGINT      DEFAULT 0,
    comment_count   BIGINT      DEFAULT 0,
    avg_watch_pct   FLOAT,                   -- average watch fraction (for recommendation)
    updated_at      TIMESTAMPTZ
);

Watch History — Bigtable Schema (YouTube)

Bigtable is a wide-column NoSQL store: rows sorted lexicographically by row key.

Row key design: "{user_id}#{max_int64 - timestamp_ms}"
  Example: "42#9223372036854726207"  (for user 42 at timestamp 1234567890123ms)
  max_int64 = 9223372036854775807
  reverse_timestamp = 9223372036854775807 - 1234567890123 = 9223372036853541684

Why reverse timestamp:
  Bigtable scans are sequential (sorted by row key)
  We want "most recent" first (natural user expectation)
  With forward timestamp: scan gives oldest first → must scan entire history to get recent
  With reverse timestamp: most recent has SMALLEST reverse value → lexicographically FIRST
  Query "last 50 watched by user 42":
    Bigtable.scan(row_range_start="42#0", limit=50)  ← 50 sequential rows = O(50) scan

Column structure per row:
  Column family: watch
    video_id:    "vid_abc123"
    watch_pct:   "0.73"          (fraction of video watched)
    quality:     "1080p"
    device:      "iOS"
    duration:    "1847"          (seconds watched)
    timestamp:   "1234567890123"

Query: "What did user 42 watch recently?"
  scan(prefix="42#", limit=50) → 50 rows = last 50 watch events = O(50)

Query: "Did user 42 watch video_abc?" (for recommendation dedup):
  scan(prefix="42#", filter_column="video_id:vid_abc123") → O(1) if indexed separately
  (In practice: secondary index in a separate lookup table: watches_by_video(user_id, video_id))

View Count — Redis INCR + Flush

YouTube view count scale:
  500M DAU × 4 videos/session × 3 sessions = 6B view events/day = 69,444 views/sec
  Peak: 4× → 277,778 views/sec

Redis INCR:
  INCR view_count:{video_id}
  Atomic, O(1), 1M+ INCR/sec per Redis node

Flush to PostgreSQL (every 60 seconds):
  Flush job: MGET all view_count keys → batch UPDATE video_stats SET view_count=view_count+delta

Hot video problem (viral video at 1M views/min):
  Single Redis key at 16,667 INCR/sec → fine (Redis handles this easily)
  But: 1M views/min displayed on page requires near-real-time count display
  → Redis count is authoritative for display (real-time), PostgreSQL for durability (periodic)
  → Client reads: GET view_count:{video_id} from Redis; falls back to PostgreSQL on Redis eviction

5. Content ID — Copyright Fingerprinting (YouTube)

Problem: 500 hrs/min uploaded → cannot manually review every video for copyright violation
         Need automated copyright detection within seconds of upload

Content ID pipeline:
  At upload time (before publishing):
    1. Extract audio fingerprint: segment audio into 5-second clips → SHA-256 acoustic hash per clip
       (Similar to Shazam: frequency spectrum → normalized hash → O(1) lookup in LSM-tree)
    2. Extract video fingerprint: perceptual hash (pHash) per frame group (every 30 frames)
       pHash: DCT of 32×32 grayscale thumbnail → 64-bit hash → Hamming distance < 10 = match

  Fingerprint database:
    5.76 trillion fingerprints (YouTube's reported number)
    Stored in distributed LSM-tree (like LevelDB/RocksDB) → O(1) lookup per fingerprint
    Indexed by fingerprint → [{rights_holder, asset_id, policy}]

  Match actions (configured by rights holder):
    - Block:      remove video, notify uploader
    - Monetize:   allow video, share ad revenue with rights holder (most common)
    - Track:      allow video, show rights holder view count stats
    - License:    allow if uploader has license

  Scale math:
    1,000 videos/min × 100 audio clips/video = 100,000 audio fingerprint lookups/min
    100,000 × 30 frames/clip ÷ 30 frames/group = 100,000 video fingerprint lookups/min
    Total: 200,000 fingerprint lookups/min = 3,333 lookups/sec
    At O(1) per lookup: trivially handled by a small cluster of LevelDB nodes

6. DRM — Netflix Content Protection

Netflix requires DRM (Digital Rights Management) for all licensed content.

Three DRM systems (device coverage):
  Widevine (Google):  Android, Chrome, Chromecast, Smart TVs
  FairPlay (Apple):   iOS, iPadOS, tvOS, macOS Safari
  PlayReady (Microsoft): Windows 10, Xbox

Encryption:
  Each video segment encrypted with AES-128-CTR
  Key: derived from (master_content_key, segment_id) → unique key per segment
  Key stored in Netflix License Server (not in S3 with the segment)

Playback flow:
  1. Client: decrypt=TRUE, so fetch content_key from License Server
  2. Client → Netflix Auth Service: { user_id, session_token, video_id }
  3. Auth Service: validate subscription active + not in high-piracy region
  4. License Server → Client: { content_key } encrypted with device's hardware key (TEE)
     TEE (Trusted Execution Environment): key never appears in software-accessible memory
  5. Client: decrypt segment using content_key in hardware decoder
  6. Decoded frames: displayed immediately; never written to disk in decrypted form

Why AES-128-CTR (not AES-128-CBC):
  CTR mode: each segment encrypted independently (random access to any position in segment)
  CBC mode: each block depends on previous → cannot decrypt mid-segment without start
  Video segments need random access (seek to frame N within segment) → CTR required

Three-tier consistency insight for video platforms:
  1. Creator domain (strong): Upload status, video availability, copyright decisions — creators and rights holders need accurate, immediate feedback. Eventual consistency here loses creator trust.
  2. Engagement domain (eventual): View counts, likes, comments, watch history — 60-second lag on a number that changes thousands of times per second is imperceptible. Eventual consistency enables enormous write throughput.
  3. CDN segment domain (immutable): Video segments never change after publish. Content-addressing makes this a non-problem — staleness is structurally impossible because stale content has a different URL.

Key Takeaways

  • Origin Shield prevents thundering herd: 1,000 ISP edge PoPs missing a new video simultaneously → 1 origin shield request → 1 S3 read, not 1,000
  • Immutable content-addressed URLs = max-age=1 year: changing content gets a new URL; old URL is forever valid; CDN caches aggressively with zero staleness risk
  • Netflix proactive fill achieves 99% cache hit: nightly ML-predicted top-200 titles pre-loaded to all OCAs → next day's demand is almost entirely served from ISP hardware
  • Bigtable reverse timestamp: row key = user_id + (MAX_INT64 - timestamp) → most recent watch events lexicographically first → "last 50 watched" = O(50) sequential scan
  • Content ID scale: 5.76T fingerprints in LSM-tree → O(1) lookup → 3,333 lookups/sec from 1,000 uploads/min × 3.33 fingerprints/sec/video — easily handled

Interview Tips

  • The Origin Shield insight is commonly missed: "without a shield layer, a viral video launch causes 1,000 concurrent S3 requests — one per edge PoP that hasn't cached it yet — the shield collapses this to 1 request"
  • When asked "how do you keep CDN content fresh?" — the content-addressing answer is elegant: "segments never change, so CDN never needs to check freshness for segments; only the manifest has a short TTL"
  • Netflix proactive fill is a great differentiator from YouTube GGC: "Netflix knows their catalog (15K titles); proactive fill puts tomorrow's top 200 on every OCA tonight — YouTube can't predict which user-generated video will go viral"
  • The Bigtable reverse timestamp trick is a classic interview answer: "Bigtable sorts rows lexicographically; reversing the timestamp makes most recent = lexicographically smallest = first in scan order"
  • For DRM: mention all three (Widevine + FairPlay + PlayReady) and explain the TEE: "the content key is decrypted inside hardware trusted execution environment — it never appears in software-accessible memory, making screen recording produce garbled output"
