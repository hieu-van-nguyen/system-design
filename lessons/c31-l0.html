Design Google Docs (Collaborative Editing)

This is a bonus, standalone design — unlike Chapters 25-30, there's no separate requirements/high-level/deep-dive lesson split. We cover the full problem in one pass: requirements, architecture, and the one deep-dive that actually matters here — how concurrent edits converge to the same document.

1. Clarifying Questions & Scope

QuestionWhy it matters
Real-time character-level sync, or coarser "save and merge"?Character-level sync forces a conflict-resolution algorithm; coarse merge could get away with last-write-wins
Do we need offline editing?Offline-first pushes toward CRDTs; always-online pushes toward a simpler centralized OT server
Do we need version history / "time travel"?Changes the storage model — we'll need an append-only op log, not just current state
How many concurrent editors per document, typically?2-3 is the common case; some docs (shared wikis) spike to 50+ and stress the broadcast fan-out

Scope for this lesson: real-time, character-level collaborative editing (Google Docs' actual behavior), online-first, with version history.

2. Functional & Non-Functional Requirements

TypeRequirement
FunctionalMultiple users edit the same document concurrently; every client converges to the identical final content
FunctionalSee other editors' live cursors and selections
FunctionalBrowse and restore prior versions of a document
Non-functionalLow latency — a keystroke should appear for other editors in well under 100ms on a good connection
Non-functionalConvergence is a hard correctness requirement — like Chapter 30's zero-double-booking, this is not a tunable tradeoff. Every replica must reach the same state.
Non-functionalDurability — no committed keystroke is ever lost, even across reconnects

3. Back-of-the-Envelope Estimation

Assume 500K documents being actively edited at any given moment
Average 3 concurrent editors per active document, each typing ~3 ops/sec while active

Peak aggregate ops = 500,000 docs * 3 editors * 3 ops/sec
                   = ~4.5M ops/sec system-wide (fan-in to be sharded across doc servers)

Each op (insert/delete + position + payload) ~100 bytes
A heavily-edited doc over its lifetime might accumulate millions of ops
  -> replaying the full op log on every load is too slow
  -> need periodic snapshots (e.g. every 500 ops) to bound load time

4. High-Level Architecture

Client A ---\                                    /--- Op Log (durable, per-doc, append-only)
             \--- WebSocket ---> Doc Server ------+
Client B ---/     (bidirectional)  (owns one doc)  \--- Snapshot Store (periodic full-state checkpoints)
             |
             +--- Presence/Cursor broadcast (ephemeral, pub/sub — not persisted)

Doc Server assignment: consistent hash on docId, same sharding move as Chapter 29's
driverId hashing — every client editing document X must land on the same server,
because that server is the single sequencer for X's operations.
💡 Interview signal: naming why one document needs one authoritative server — it's not a scaling choice, it's a correctness requirement. Without a single sequencer per doc, you have no consistent order to transform operations against.

5. Deep Dive — Why Concurrent Edits Diverge

Two users, both viewing revision N of a document, both type at position 5 at the same instant:

Doc at revision N: "helloworld"  (positions 0-9)

User A inserts "X" at position 5  -> intends: "helloXworld"
User B inserts "Y" at position 5  -> intends: "helloYworld"

If the server applies A's op, then naively applies B's untouched op (still "insert Y at 5"):
  after A:  "helloXworld"   (revision N+1)
  after B:  "helloYXworld"  (B's op landed at position 5, shoving X right — WRONG, B meant to insert after X)

Client A's local view differs from what the server produced. Divergence.

This is the problem Operational Transformation (OT) exists to solve.

6. Deep Dive — Operational Transformation vs. CRDTs

Operational Transformation (OT)CRDTs (Conflict-free Replicated Data Types)
TopologyCentralized — one authoritative server per document sequences all opsDecentralized — any replica can merge with any other, no central sequencer needed
MechanismTransform an incoming op against every op committed since the client's known revision, so its effect is correct against the new stateEach element carries metadata (unique ID, causal ordering) so merges are commutative and always converge
Offline supportWeak — needs a live connection to the sequencer to resolve opsStrong — this is the reason CRDTs exist; peers reconcile whenever they happen to connect
CostTransform logic gets genuinely intricate for rich structures (tables, formatting, nested lists)Tombstones/metadata for every character ever inserted or deleted — significant memory/storage bloat on long-lived documents
Used byGoogle Docs' real-time editing modelPeer-to-peer / offline-first editors (e.g. some note-taking apps)

The corrected server-side flow using OT:

client_op arrives with (baseRevision, op)

server:
  if baseRevision == currentRevision:
    apply op directly, currentRevision += 1
  else:
    # client was behind — transform op against every committed op since baseRevision
    for committedOp in log[baseRevision:currentRevision]:
        op = transform(op, committedOp)   // adjusts position/index, not content
    apply transformed op, currentRevision += 1
  broadcast transformed op + new revision to all other connected clients

Re-running the earlier example: B's op (still tagged baseRevision = N) arrives after A's is committed. The server transforms it against A's committed insert — shifting B's target index from 5 to 6 — before applying. Both clients converge on "helloXYworld".

💡 Interview signal: don't just say "use OT" — walk through a concrete divergence scenario and show the transform step fixing it. That's the difference between reciting a buzzword and demonstrating you understand the mechanism.

7. Storage: Op Log + Snapshots, and Ephemeral Presence

The durable op log doubles as version history for free — replaying ops between any two revisions reconstructs any past state, so "restore this version" is just a replay-and-checkpoint, not a separate feature. Periodic snapshots (e.g. every 500 ops) bound how much of the log must be replayed when a client opens a document cold.

Presence and cursor positions are the opposite of the op log: high-frequency, latency-sensitive, and disposable. They're published over the same pub/sub channel the Doc Server already holds open, never written to durable storage — the same hot/cold split Chapter 29's driver-location pings used (live position in Redis/pub-sub, only trip-level records persisted).

Key Takeaways

  • Convergence — every client reaching identical content — is a hard correctness requirement, not a tunable tradeoff
  • One document maps to one authoritative sequencer server (consistent hash on docId), because a consistent transform order requires a single source of truth
  • OT transforms incoming operations against everything committed since the client's last known revision; CRDTs sidestep the need for a sequencer entirely at the cost of offline support vs. metadata bloat
  • The append-only op log plus periodic snapshots gives you version history without building a separate system for it
  • Ephemeral state (cursors, presence) never touches durable storage — same pattern as Chapter 29's live location pings

Interview Tips

  • Always demonstrate the divergence problem with a concrete two-user example before naming OT as the fix
  • State plainly that Google Docs uses OT, not CRDTs — CRDTs solve a different problem (offline/P2P), don't conflate them
  • Call out the sharding requirement (one doc, one server) as a correctness constraint, not a scaling afterthought
  • Separate durable state (op log, snapshots) from ephemeral state (presence, cursors) early in the design
