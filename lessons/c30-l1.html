High-Level Design & Seat Reservation Flow

🎯 Learning Objectives

  • Separate the immutable venue layout from the volatile seat-availability overlay, and cache each differently

High-Level Design & Seat Reservation Flow

Per Lesson 1, the design must isolate a tiny, hot, highly-contended dataset (seat status) from everything else. The architecture below draws that line explicitly: mostly-static data goes through a normal cache/CDN path, while seat status gets its own tightly-controlled path built around a state machine.

2. Immutable Layout vs. Volatile Availability

A venue's physical layout (section shapes, row/seat coordinates) almost never changes once an event is on sale. Seat status (available/held/booked) changes constantly, especially during a flash sale. Conflating the two — as a single "seat map" API — leads to the wrong caching answer for both halves:

DataChange frequencyCaching strategy
Venue layout (geometry, seat coordinates)Effectively static per eventCDN-cacheable, long TTL (hours) — safe to serve stale
Seat availability overlayChanges on every hold/release/booking, bursts during on-saleNever CDN-cached; read from the live seat-status store, short-lived client-side cache (seconds) at most

The client fetches the layout once (cache hit, cheap) and polls or subscribes (e.g., WebSocket/SSE) for the availability overlay only — a small, frequently-refreshed payload of just seat statuses, not the whole map.

💡 Interview signal: Explicitly splitting "what rarely changes" from "what changes constantly" — and giving each an opposite caching answer — is exactly the kind of design instinct interviewers are listening for. Serving both from one cached endpoint is a common shortcut that breaks under a flash sale.

3. Seat State Machine

                 holdSeat()                confirmBooking()
    AVAILABLE ──────────────► HELD ──────────────────────► BOOKED
        ▲                      │  (payment succeeds)
        │                      │
        └──── TTL expiry ──────┘
        └──── releaseHold() ───┘  (user cancels, or payment fails)

A seat is never sold directly from AVAILABLE — every booking passes through a time-boxed HELD state (TTL ~10 minutes, matching how long checkout realistically takes). This is what makes the seat inventory behave like a small pool of leased resources rather than a simple boolean flag, and it's the state machine Lesson 3 builds concurrency control around.

4. End-to-End Flow

1. Client → Venue Service: getSeatMap(eventId)       // cached layout + live status
2. Client → Reservation Service: holdSeat(eventId, seatId, userId)
     → seat: AVAILABLE → HELD, TTL 10 min            (Lesson 3: how this stays correct
                                                        under massive concurrent attempts)
3. Client → Payment Service: charge(holdId, paymentToken)
4. Payment Service → Reservation Service: confirmBooking(holdId)
     → seat: HELD → BOOKED (permanent)
     → Notification Service: send ticket/confirmation
5. If step 3/4 doesn't complete within the hold TTL:
     → seat: HELD → AVAILABLE (automatic release, no manual cleanup needed)

Key Takeaways

  • Venue layout (immutable, CDN-cacheable) and seat availability (volatile, never CDN-cached) are architecturally separate concerns, not one "seat map" endpoint
  • Every seat passes through a time-boxed HELD state before BOOKED — this state machine is what later lessons build correctness and queueing around
  • A hold's TTL expiry is the default release path — no manual cleanup job is needed to reclaim abandoned holds
  • The reservation service owns the highest-contention write in the system; every other service (catalog, venue, payment) is comparatively low-contention

Interview Tips

  • Draw the layout/availability split before drawing services — it's the architectural decision everything else depends on
  • Name the seat state machine explicitly (AVAILABLE/HELD/BOOKED) rather than describing booking as a single atomic step
  • Explain the hold TTL in product terms (checkout time budget) as well as system terms (bounded resource lease)
  • Flag upfront that the reservation service's write path is where all the interesting concurrency problems live — it previews Lesson 3 well
