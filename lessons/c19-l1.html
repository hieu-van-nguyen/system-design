Client Architecture — Desktop Deep Dive

The desktop client is the most complex component. It must handle OS-level file events, maintain local sync state, and coordinate uploads without blocking the user.

File Upload Flow (6 Steps)

Step 1 — File Watcher detects change
  inotify (Linux) / FSEvents (macOS) fires MODIFY event for ~/Dropbox/report.pdf
  Client reads new file → runs Rabin CDC → produces chunks: [sha256_A, sha256_B, sha256_NEW, sha256_D]

Step 2 — Dedup check with server
  POST /v1/files/init-upload
  Body: { file_id: "f123", name: "report.pdf", size: 16MB, chunk_hashes: ["sha256_A","sha256_B","sha256_NEW","sha256_D"] }

  Server queries: SELECT sha256 FROM chunks WHERE sha256 = ANY($1)
  Returns: existing = ["sha256_A", "sha256_B", "sha256_D"]
           new      = ["sha256_NEW"]
  Response: { upload_id: "u789", presigned_urls: { "sha256_NEW": "https://s3.aws.../put?X-Amz-..." } }

Step 3 — Client uploads ONLY new chunk directly to S3
  PUT https://s3.amazonaws.com/dropbox-chunks/sha256_NEW?X-Amz-...
  Body: [raw 4 MB chunk data]
  Bypasses all API servers — 4 MB at client's full network speed

Step 4 — S3 event triggers async virus scan
  S3 EventBridge → SQS → ClamAV worker scans chunk
  Result written to chunks table: { sha256_NEW, scanned=true, threat=false }
  (Non-blocking — commit can proceed while scan runs)

Step 5 — Client commits file version
  PUT /v1/files/f123/commit
  Body: { parent_version_id: "v6", chunk_hashes: ["sha256_A","sha256_B","sha256_NEW","sha256_D"], modified_at: "..." }
  Server: checks parent_version_id == current → no conflict → insert file_versions row → publish to Kafka

Step 6 — Sync Service fans out to other devices
  Kafka consumer (Sync Service) reads file-changes topic
  Looks up WebSocket connections for all users with access to file f123
  Pushes: { type: "file_changed", file_id: "f123", version: 7, chunk_hashes: [...] }
  Other devices: compare with local SQLite → request presigned URLs for sha256_NEW → download delta

Download / Sync Receive Flow (5 Steps)

Step 1 — WebSocket push (or long-poll response):
  { "type": "file_changed", "file_id": "f123", "version": 7,
    "chunk_hashes": ["sha256_A", "sha256_B", "sha256_NEW", "sha256_D"] }

Step 2 — Client compares with local SQLite:
  SELECT sha256 FROM chunks WHERE sha256 IN ("sha256_A","sha256_B","sha256_NEW","sha256_D")
  Found locally: sha256_A, sha256_B, sha256_D   ← already cached from prior sync
  Missing:       sha256_NEW                      ← only chunk that changed

Step 3 — Request presigned download URL for missing chunk only:
  GET /v1/chunks/sha256_NEW/download-url
  Response: { url: "https://s3.aws.../get?X-Amz-...", expires_in: 900 }

Step 4 — Download missing chunk from S3 (direct, bypasses API servers):
  GET https://s3.amazonaws.com/dropbox-chunks/sha256_NEW?X-Amz-...
  Download: 4 MB at full network speed

Step 5 — Reassemble + write to disk:
  Concatenate [sha256_A, sha256_B, sha256_NEW, sha256_D] in order
  Write to ~/Dropbox/report.pdf atomically (write tmp file, then rename)
  Update local SQLite: files.version = 7, files.sha256 = new_overall_hash
Latency breakdown for delta sync: WebSocket push receipt 0ms → SQLite lookup 1ms → presigned URL fetch 10ms → 4 MB download at 100 Mbps = 320ms → disk write 5ms = 336ms total end-to-end for a typical edit.

Technology Choices

ComponentChoiceWhy (one-sentence rationale)
Chunk storageS3 (content-addressed by SHA-256)Unlimited scale, 11 nines durability, globally replicated; content addressing enables dedup by construction
Current file metadataPostgreSQL (sharded by user_id)ACID transactions needed for conflict detection (parent_version_id check); rich JOIN queries for folder trees
Version historyCassandraAppend-only writes at 900T eventual rows; wide-row model (file_id PK, version_number clustering) = O(1) history fetch
Metadata cacheRedis (read-through, 60s TTL)Folder listing at 11,574 reads/sec; Redis at <1ms vs PostgreSQL at 5–10ms round-trip
Sync transportWebSocket (primary) + long-poll (fallback)WebSocket: bidirectional, persistent, 2 KB overhead per connection; long-poll for clients behind strict firewalls
Change fan-outKafka (file-changes topic)Durable, replayable; consumer groups allow Sync Service, Search indexer, Notification service to consume independently
SearchElasticsearch + Apache TikaFull-text search with permission-aware bool filter; Tika extracts text from PDF/DOCX for content indexing
Local client stateSQLiteEmbedded, zero-config, ACID; stores file→chunk mapping for delta sync dedup without server roundtrip
Virus scanningClamAV via SQS queueAsync non-blocking; 99.9% of files are clean, so zero latency impact on upload path
NotificationFCM (Android) + APNs (iOS)Mobile background sync; push wakes app to pull delta when WebSocket not connected
File watcherinotify (Linux) / FSEvents (macOS) / ReadDirectoryChangesW (Win)OS-native event APIs; polling would consume CPU and miss rapid edits

Key Takeaways

  • Two planes: control plane (metadata, auth, conflict detection) through API servers; data plane (chunk bytes) directly to S3 via presigned URLs
  • Client SQLite is critical: it enables local dedup check before server roundtrip and offline operation queueing
  • Kafka decouples consumers: Sync Service, Search indexer, and Notification service all consume file-changes independently without coupling
  • PostgreSQL for current state, Cassandra for history: split because conflict detection needs ACID; version history needs append-throughput
  • Delta sync latency < 336ms: only the changed chunk (4 MB) is transferred, not the full 40 MB file

Interview Tips

  • Draw the architecture split clearly: "API servers handle metadata (kilobytes); S3 handles chunk bytes (megabytes) — they never mix"
  • When asked about the client, explain the SQLite state machine: it's what makes offline mode and delta sync possible without constant server roundtrips
  • Justify WebSocket + long-poll as a pair: "WebSocket for connected clients; long-poll for corporate firewalls that block persistent connections"
  • For shared folders: "Kafka consumer looks up all users with access — O(1) per user if we maintain an inverted index of file_id → [user_ids]"
  • Always mention atomicity on the client side: write to temp file, then rename — prevents corrupt partial files on crash
