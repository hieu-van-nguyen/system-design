🎯 Learning Objectives

  • Enumerate the 5 rate limiting algorithms (Token Bucket, Leaky Bucket, Fixed Window, Sliding Log, Sliding Counter) with concrete tradeoffs
  • Clarify the 6 key dimensions that define a rate limiter before designing (scope, limit granularity, enforcement layer, burst tolerance, response behavior, consistency model)
  • Quantify the fixed-window boundary spike: a 2× burst at window edges and why it fails for traffic smoothing
  • Select the right algorithm for a given scenario: Token Bucket for API burst tolerance, Sliding Window Counter for balanced production systems

Requirements & Rate Limiting Algorithms

1. Clarifying Questions

Rate limiting seems simple but hides significant design decisions. Ask these before drawing anything:

2. Functional Requirements

  • Rate limit enforcement: Reject requests exceeding the configured threshold with HTTP 429 and a Retry-After header.
  • Multi-tier limits: Free: 100 req/min; Basic: 1,000 req/min; Enterprise: 10,000 req/min. Limits configurable per API key without deployment.
  • Response headers: Every API response includes X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset so clients can self-throttle.
  • Multi-dimension limiting: Enforce per user AND per endpoint simultaneously (e.g., 100 req/min globally but 10 req/min to POST /payment).
  • Audit log: Log every rate-limit rejection (user_id, endpoint, timestamp) for analytics and abuse investigation.
  • Dynamic rule updates: Change limits in real-time (no redeploy) — stored in DB, cached in memory with 30s TTL.

4. The 5 Rate Limiting Algorithms

4.1 Token Bucket


// Bucket starts full (capacity = limit). Tokens refill at fixed rate.
// Each request consumes 1 token. If bucket empty → reject.

state = { tokens: 100, last_refill: now() }

def allow_request(state, capacity, refill_rate):
    now = current_time()
    elapsed = now - state.last_refill
    # Refill tokens proportional to elapsed time
    tokens = min(capacity, state.tokens + elapsed × refill_rate)
    if tokens >= 1:
        state.tokens = tokens - 1
        state.last_refill = now
        return ALLOW
    else:
        return REJECT (HTTP 429)

// Config: capacity=100 (burst limit), refill_rate=100/60 tokens/sec (100/min steady state)
// Result: allows burst of 100 req instantly, then 1.67 req/sec steady state
AspectToken Bucket
Burst handling✅ Yes — can consume all tokens instantly
Memory2 values per key (tokens + last_refill) → minimal
Smoothness❌ Traffic is NOT smoothed — allows bursts
Used byAWS API Gateway, Stripe, GitHub API, Cloudflare

4.2 Leaky Bucket


// Requests enter a FIFO queue (the "bucket"). Processed at a fixed output rate.
// If queue full → reject incoming request.

queue = Queue(maxsize=100)   // bucket capacity

# Request handler:
if queue.full():
    return REJECT (HTTP 429)
queue.put(request)

# Leak thread (runs at fixed rate: 100 req/min = ~1.67/sec):
while True:
    if not queue.empty():
        process(queue.get())
    sleep(1 / leak_rate)
AspectLeaky Bucket
Burst handling❌ No — bursts queued, processed at fixed rate
Output rate✅ Perfectly smooth — constant downstream rate
MemoryQueue storage per user (can be large)
Used byShopify, network traffic shapers (QoS)

4.3 Fixed Window Counter


// Divide time into fixed windows (e.g., each minute). Count requests per window.
// If count exceeds limit → reject.

window_key = "ratelimit:{user_id}:{endpoint}:{minute_timestamp}"
# minute_timestamp = floor(now / 60)  →  1725000060, 1725000120, ...

count = INCR window_key
if count == 1:
    EXPIRE window_key 60   // auto-cleanup after window expires
if count > limit:
    return REJECT (HTTP 429)
return ALLOW
⚠️ Fixed Window Boundary Spike: A user can send 100 requests at 11:59:59 and 100 more at 12:00:00 — 200 requests in a 2-second span, yet both windows show count=100. The effective rate at the boundary is 2× the limit. For APIs where burst causes downstream harm (payment processors, SMS gateways), this is unacceptable.
AspectFixed Window Counter
Implementation✅ Trivial — single Redis INCR + EXPIRE
Memory✅ O(1) per user per window
Accuracy❌ 2× burst possible at window boundary
Used bySimple internal APIs; acceptable when burst is OK

4.4 Sliding Window Log


// Store timestamp of every request in a sorted set. Count requests in rolling window.

def allow_request(user_id, endpoint, limit, window_secs):
    key = "ratelimit_log:{user_id}:{endpoint}"
    now = current_time_ms()
    window_start = now - window_secs × 1000

    # Atomic operations via pipeline or Lua:
    ZREMRANGEBYSCORE key -inf (window_start - 1)  // remove expired entries
    count = ZCARD key                               // count remaining in window
    if count < limit:
        ZADD key now now                            // add current request (score=member=timestamp)
        EXPIRE key window_secs
        return ALLOW
    else:
        return REJECT (HTTP 429)
AspectSliding Window Log
Accuracy✅ Exact — no boundary spike
Memory❌ O(requests_per_window) per user — for 1,000 req/min limit: 1,000 entries in sorted set
Burst handling✅ Naturally handles burst (counts actual timestamps)
Used byStripe for critical payment endpoints; acceptable when accuracy > memory

4.5 Sliding Window Counter (Hybrid — Production Choice)


// Approximate sliding window using two fixed-window counters + weighted interpolation.
// Accuracy: within ±1% for uniform traffic.

def allow_request(user_id, limit, window_secs):
    now = current_time()
    current_window = floor(now / window_secs)
    prev_window = current_window - 1

    cur_key  = "ratelimit:{user_id}:{current_window}"
    prev_key = "ratelimit:{user_id}:{prev_window}"

    cur_count  = GET cur_key  or 0
    prev_count = GET prev_key or 0

    # How far into the current window are we? (0.0 → 1.0)
    elapsed_fraction = (now % window_secs) / window_secs

    # Weight: previous window contributes proportionally to how much of current window remains
    weighted_count = cur_count + prev_count × (1 - elapsed_fraction)

    if weighted_count < limit:
        INCR cur_key
        EXPIRE cur_key (window_secs × 2)
        return ALLOW
    else:
        return REJECT (HTTP 429)

// Example: window=60s, limit=100, now=45s into window (elapsed_fraction=0.75)
// prev_count=80, cur_count=30
// weighted = 30 + 80 × (1 - 0.75) = 30 + 20 = 50 ✅ ALLOW
AspectSliding Window Counter
Accuracy✅ Within ±1% (proven mathematically for uniform traffic)
Memory✅ O(1) — only 2 integers per user, regardless of request count
Burst handling✅ Partial — smooths the boundary spike significantly
Implementation complexityMedium — requires 2 Redis GETs + weighted math
Used byCloudflare Workers, nginx rate limiting, most production systems

💡 At Cloudflare Scale: 9M QPS makes a centralized Redis rate limiter impossible — even Redis Cluster at 1M ops/sec per node would need 9 nodes just for the check, with cross-datacenter latency dominating. Cloudflare uses local in-memory counters on each edge node, syncing periodically. This allows ~5% overage but eliminates the inter-node coordination cost entirely. Know this boundary — it comes up in senior interviews.

Key Takeaways

  • Token Bucket = burst tolerance: Used by AWS, Stripe, GitHub. Allows all tokens to be consumed at once — ideal for APIs where a short burst is OK.
  • Sliding Window Counter = production default: O(1) memory, ~1% accuracy, no boundary spike. Cloudflare's algorithm for Workers. The right answer for most interview scenarios.
  • Fixed Window has a 2× boundary spike: At the window boundary, clients can legally send 2× the limit in a 2-second window. Know this failure mode and when it matters.
  • Sliding Window Log is memory-expensive: Requires storing every timestamp. For a 1,000 req/min limit, that's 1,000 Redis sorted-set entries per user — impractical at millions of users.
  • Clarify burst tolerance first: It drives the algorithm choice more than any other requirement. Token Bucket if burst OK; Sliding Window Counter if smooth is required.
  • Fail open on Redis failure: The rate limiter must not become a single point of failure. If Redis is unreachable, allow requests through with reduced accuracy rather than rejecting all traffic.

Interview Tips

  • Name all 5 algorithms upfront: "There are 5 common rate limiting algorithms — let me briefly describe each and then explain which I'd choose for this system." This immediately signals breadth of knowledge.
  • Draw the Token Bucket visually: A bucket with water dripping in at a fixed rate and requests consuming drops is instantly understandable. Interviewers remember visual metaphors.
  • Derive the Fixed Window flaw mathematically: "At 11:59:59 a client sends 100 requests (window 1 = 100/100). At 12:00:00 they send 100 more (window 2 = 100/100). In the 2 seconds spanning midnight they sent 200 requests — 2× the limit." Math beats hand-waving.
  • State your production recommendation: After explaining all 5, say "For this system I'd use Sliding Window Counter — it gives O(1) memory, approximately correct counts within 1%, and is what Cloudflare uses in production."
  • Multi-dimension limits are common: Real systems have per-user AND per-endpoint AND per-tenant limits simultaneously. Redis key = ratelimit:{user_id}:{endpoint}:{window}. Check all dimensions in parallel with a Redis pipeline.
