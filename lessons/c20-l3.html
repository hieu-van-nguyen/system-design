Deep Dive — Group Chat & Presence

lesson
⏱ 10 min
📖 Chapter 20, Lesson 4

🎯 Learning Objectives

  • Calculate why write fan-out breaks at 500-member groups and design the hybrid threshold (≤ 100 members = write fan-out; > 100 = group mailbox + read merge)
  • Design the presence system for 500M users: derive why naive heartbeats generate 100M writes/sec and how presence sampling reduces it to 10M writes/sec
  • Implement typing indicators as ephemeral WebSocket-only events — explain why persistence would waste 6+ TB/day on zero-value data
  • Build the consistency model table for messaging and justify which operations require strong vs. eventual consistency

1. Group Chat — The Fan-Out Problem

Why write fan-out breaks at scale

Write fan-out model:
  When Alice sends a message to group G (500 members):
  → Chat server writes 500 inbox entries (one per member) into Cassandra
  → 500 WebSocket pushes (or 500 notification checks)

Math for a single message to a 500-member group:
  500 Cassandra writes × 5ms each = 2.5s sequential (unacceptable)
  500 parallel Cassandra writes = ~50ms (with enough nodes)
  But at scale:

  If 1M active groups send 1 message each simultaneously:
  1M × 500 members = 500M fan-out writes/sec
  At 50K Cassandra writes/node: 500M ÷ 50K = 10,000 Cassandra nodes — operationally impossible

Hybrid Fan-Out Strategy (Facebook Messenger's actual approach)

Group SizeStrategyWrite AmplificationRead Cost
1:1 chat (2 members)Write fan-out to both inboxes2× writesO(1) inbox read
Small group (≤ 100 members)Write fan-out to each member's inbox100× writesO(1) inbox read
Large group (> 100 members)Write once to group mailbox; read-time merge1× writeO(k) where k = group size, but cached

Group Mailbox Design (for large groups)

-- Group message store: single mailbox, all members read from it
CREATE TABLE group_messages (
    group_id    UUID,
    message_id  BIGINT,
    sender_id   BIGINT,
    content     TEXT,
    -- ... (same fields as messages table)
    PRIMARY KEY (group_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

-- Member last-read cursor (for unread count + pagination)
CREATE TABLE group_member_cursors (
    group_id    UUID,
    user_id     BIGINT,
    last_read_id BIGINT,   -- highest message_id the member has seen
    PRIMARY KEY (group_id, user_id)
);

Read-time merge for a member's inbox view:
  1. Fetch their DM conversations (from personal inbox table, sorted by last_msg_time)
  2. Fetch their large-group conversations (from group_member_cursors, get last_read_id)
  3. For each large group: SELECT from group_messages WHERE message_id > last_read_id LIMIT 50
  4. Merge and sort by timestamp → unified inbox view

This trades write amplification for read-time computation — acceptable because:
  - Large groups have many readers per writer (500 readers per write = 500× read > write)
  - Redis caches the group's last N messages (cache-hit rate ~95% for active groups)

Group Fan-Out to Connected Members

For small groups (≤ 100 members, write fan-out path):
  Chat server writes message to Cassandra.
  Kafka consumer reads message.
  Delivery worker: batch lookup Redis for all member connections:
    MGET connection_registry:user_1 connection_registry:user_2 ... connection_registry:user_100
    → Returns server_ids for all online members in one Redis round-trip

  Route to each server:
    - Members on THIS server: direct WebSocket push (0ms routing overhead)
    - Members on OTHER servers: Redis pub/sub channel (ws:server:{server_id})

For large groups (> 100 members):
  Chat server writes ONCE to group_messages table.
  Kafka event: { type:"group_message", group_id, message_id }
  Notification Service: fan-out push notifications to all offline members
    → Uses group_members table: SELECT user_id FROM group_members WHERE group_id = ?
    → Batch push (FCM supports 500 recipients per API call)
  Online members: already subscribed to group WebSocket channel → receive immediately

2. Presence System

The Scale Problem

Naive approach: each client sends heartbeat every 5 seconds → server updates Redis TTL.

500M DAU × (1 heartbeat / 5 seconds) = 100M Redis writes/sec

Redis throughput per node:          ~100K writes/sec
Nodes needed:                        100M ÷ 100K = 1,000 Redis nodes
Memory per presence entry:           ~100 bytes (user_id + timestamp + device)
Total memory for 500M users:         500M × 100 bytes = 50 GB (fits in 1 Redis cluster)

The problem is WRITE throughput (1,000 nodes), not memory.

Presence Sampling — Reduce from 100M to 10M writes/sec

Key insight: You don't need presence for ALL 500M users.
You only need presence for users whose contacts are actively viewing a conversation with them.

Presence-on-demand (lazy publication):
  When Alice opens a 1:1 conversation with Bob:
    Alice's client subscribes: SUBSCRIBE presence:{bob_user_id}
    Bob's chat server detects Alice's subscription → starts publishing Bob's heartbeats
    Bob's heartbeats: published every 5s ONLY while someone is subscribed

  When Alice closes the conversation:
    Alice unsubscribes from presence:{bob_user_id}
    If no more subscribers for Bob: Bob's server stops publishing heartbeats
    → Redis TTL expires naturally → Bob shown as "offline" after 30s

Presence active subscribers at any time:
  500M users × 2 avg open conversations × 2 parties per conversation = 2B subscriptions
  But only: 500M × 10% viewing DMs at same time = 50M active subscriptions
  Heartbeats needed: 50M ÷ 5s = 10M heartbeat writes/sec (10× reduction)
  Redis nodes: 10M ÷ 100K = 100 nodes (vs 1,000 naive)

Presence Schema

Redis structure:
  Key:   presence:{user_id}
  Value: { status: "online", last_seen: epoch_ms, device_count: 2 }
  TTL:   30 seconds (refreshed by heartbeat; expires if no heartbeat = gone offline)

Heartbeat write:
  Client → Chat Server: WebSocket ping frame (every 5s)
  Chat Server: SET presence:{user_id} {status:online, last_seen:now} EX 30

"Last seen X ago" when offline:
  When user disconnects: SET presence:{user_id} {status:offline, last_seen:epoch_ms} EX 86400
  → Persists "last seen" for 24 hours; then clears (user was offline > 24h → show nothing)
  → Use PostgreSQL for permanent last_seen if required (not Redis)

Group presence (who's online in a group):
  Not computed for every message (too expensive for 500-member groups)
  Client-pull: GET /v1/groups/{group_id}/presence → batch lookup 500 Redis keys in pipeline
  Cached at CDN edge: 60s TTL (group "who's active" rarely needs real-time accuracy)

3. Typing Indicators — Ephemeral, Never Persisted

If we stored typing indicators in Cassandra:
  500M users × 20 conversations active × 5 typing events/min = 833M rows/min = 13.9M writes/sec
  Each row: 50 bytes (user_id, conv_id, timestamp, is_typing)
  Storage: 13.9M × 50B × 86,400s/day = 60 TB/day of zero-value data (users never view typing history)
  → Never persist typing indicators

Correct design: WebSocket-only, no Cassandra:
  Alice starts typing in conversation with Bob:
    Alice's app → Chat Server S1: { type:"typing_start", conv_id:"c789" }
    S1: route to Bob's server via connection registry (if online)
    Bob's app: shows "Alice is typing..." indicator
    No Cassandra write. No Kafka publish. Zero durability.

  Alice stops typing (or sends message):
    Alice's app → S1: { type:"typing_stop", conv_id:"c789" }
    S1: route to Bob → Bob's app hides indicator

  Fallback if routing fails (Bob's connection dropped):
    Bob misses "typing_start" — indicator never shows.
    Bob misses "typing_stop" — indicator shows until timeout.
    Client timeout: auto-hide after 5 seconds of no typing_heartbeat.
    This is acceptable: ephemeral UX, not correctness-critical.

For groups:
  Typing indicator fan-out: "Alice is typing..." to all online members
  But only publish if group size ≤ 50 (large groups suppress typing indicator)
  Reason: 500-member group with 100 simultaneous typers = 500 × 100 = 50,000 routing ops/indicator

4. Group Chat Read Receipts — Aggregation

1:1 chat: easy — blue tick when Bob reads.

Group chat (500 members): display "Seen by Alice, Bob, and 47 others"

Schema (reuses message_status from previous lesson):
  CREATE TABLE message_status (
    conv_id     UUID,
    message_id  BIGINT,
    user_id     BIGINT,
    status      TEXT,    -- 'DELIVERED' or 'READ'
    PRIMARY KEY ((conv_id, message_id), user_id)
  )

Aggregation query (on demand, not pre-computed):
  SELECT COUNT(*) as read_count,
         COUNT(CASE WHEN status='DELIVERED' THEN 1 END) as delivered_count
  FROM message_status
  WHERE conv_id = 'g456' AND message_id = 8675309

For "who read this?" expanded view:
  SELECT user_id FROM message_status
  WHERE conv_id = 'g456' AND message_id = 8675309 AND status = 'READ'
  LIMIT 100   -- paginated; not all 500 members shown at once

Optimization: Cache aggregates in Redis:
  Key: receipt_count:{conv_id}:{message_id}
  Value: { delivered: 423, read: 98 }
  TTL: 300s (5 minutes; stale by at most 5 min — acceptable for group receipts)
  INCR on each new receipt event (O(1), no Cassandra query needed for counts)

5. Conversation List — Inbox Design

What users see on app open: sorted list of conversations, most recent first.

Schema:
  CREATE TABLE user_inbox (
    user_id         BIGINT,
    last_msg_time   TIMESTAMP,   -- used for sort ORDER
    conv_id         UUID,
    conv_type       TEXT,        -- '1:1' or 'group'
    last_msg_preview TEXT,
    unread_count    INT,
    PRIMARY KEY (user_id, last_msg_time, conv_id)
  ) WITH CLUSTERING ORDER BY (last_msg_time DESC);

  Query: SELECT * FROM user_inbox WHERE user_id = ? LIMIT 30
  → 30 most recent conversations in O(1)

On message send (write fan-out updates inbox):
  UPDATE user_inbox SET last_msg_time=now, last_msg_preview=?, unread_count=unread_count+1
  WHERE user_id=recipient AND conv_id=?

  For 1:1: 2 inbox updates per message
  For small group (50 members): 50 inbox updates per message
  For large group (500 members): group mailbox approach — inbox entry points to group mailbox;
    client-side unread_count derived from last_read_id vs. group_messages latest_id

6. Consistency Model

OperationConsistencyMechanismAcceptable Lag
Message persistence (after ACK)Strong — zero lossKafka durability (acks=all) + Cassandra quorum write before delivery0 — loss after SENT is catastrophic
Message delivery to recipientEventualWebSocket push; offline → FCM → fetch on reconnect30s (user expectation: "near real-time")
Message ordering within conversationCausal (within sender)Snowflake ID monotonic per server; Cassandra clustering sort0 for same sender; cross-sender ties broken by server_id
Delivery receipts (DELIVERED)EventualACK on WebSocket receive → async Cassandra status write5s (sender sees ✓✓ within 5s of delivery)
Read receipts (READ)EventualBatch receipt on conversation open; 30s TTL on status rows10s (blue tick appears within 10s of read)
Presence (online/offline)EventualRedis heartbeat TTL 30s; sampling reduces precision30s (acceptable for "online now" indicator)
Typing indicatorsBest-effortWebSocket-only, no persistence; 5s client timeout5s auto-hide (ephemeral UX)
Group membership changesStrongPostgreSQL transaction for add/remove member + Kafka event0 — security: removed member must not receive messages
Conversation list (inbox)EventualRedis cache (10s TTL); Cassandra user_inbox read10s (inbox reorders within 10s of new message)
Two-domain insight: Facebook Messenger has two distinct consistency domains:
  1. Security domain (group membership, message deletion, account blocking) — must be strongly consistent. A removed member receiving messages is a security violation; a blocked user's messages appearing is harassment.
  2. UX domain (delivery receipts, typing indicators, presence, inbox ordering) — can be eventually consistent. 30-second lag in "online" status or 5-second delay in double-tick is imperceptible noise to users.

Key Takeaways

  • Hybrid fan-out threshold: ≤ 100 members = write fan-out (manageable amplification); > 100 = group mailbox + read-time merge (prevents 500M fan-out writes/sec)
  • Presence sampling: 100M writes/sec (naive) → 10M writes/sec (publish-on-subscription) by only tracking presence when someone is actively watching
  • Typing indicators = zero persistence: WebSocket-only with 5s client timeout; persisting would waste 60 TB/day on data users never retrieve
  • Group receipts use Redis counters: INCR delivered_count and read_count in Redis (O(1)) instead of COUNT(*) Cassandra queries per refresh
  • Group membership is the one strong consistency requirement: removed members must stop receiving immediately; this justifies a PostgreSQL transaction + Kafka event fence

Interview Tips

  • Group chat fan-out math is a classic interview probe: "500-member group × 1M active groups = 500M writes/sec — that's why we use a group mailbox for large groups"
  • Presence sampling is an advanced answer: "naive heartbeats = 1,000 Redis nodes; presence-on-demand = 100 Redis nodes by only publishing when subscribed" — most candidates miss this
  • For typing indicators: "we explicitly do NOT persist this — 60 TB/day of data users never query; WebSocket-only with 5s timeout is the correct answer"
  • When asked "how do you handle a user added to a group receiving old messages?" → "group_member_cursors stores join_time as the initial last_read_id; member only sees messages after their join"
  • Group membership strong consistency is often tested: "if Alice removes Bob from a group, what prevents Bob from receiving the next message?" → "Kafka consumer checks group_members before fan-out delivery; PostgreSQL write + Kafka event ensure Bob's removal is visible before next delivery"
