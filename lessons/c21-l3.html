Deep Dive — Search, Replication & Sharding

🎯 Learning Objectives

  • Explain Twitter's Earlybird near-real-time search: time-based index sharding, 15-second indexing lag, and why time-sharding enables efficient GDPR erasure
  • Design like-count storage using Redis INCR with a 60-second Cassandra flush — and calculate why this is the only viable approach at 57,870 likes/sec
  • Shard the Cassandra tweet store by user_id and explain the hot-partition problem for celebrities + the mitigation (virtual nodes, prefix salting)
  • Build the consistency model matrix for all Twitter operations and justify the strong-consistency requirement for follow/unfollow vs. eventual for timelines

1. Near-Real-Time Search — Earlybird Architecture

Twitter's Earlybird (internal name) is an Elasticsearch-based near-real-time index that makes tweets searchable within 15 seconds of posting. Standard Elasticsearch refresh is 1 second but propagation to replicas + query routing adds up; optimizing for 15s end-to-end requires specific tuning.

Time-Based Index Sharding

Standard approach: shard by tweet_id hash → tweets distributed randomly across shards
Problem: a search for "#WorldCup" in the last 24 hours must query ALL shards (scatter-gather)

Twitter's approach: shard by TIME (time-based index rolling):
  Index "tweets-2024-08-30" contains all tweets from 2024-08-30
  Index "tweets-2024-08-29" contains all tweets from 2024-08-29
  ...
  Hot index: tweets from last 7 days → kept in SSD-backed nodes (high IOPS)
  Warm index: tweets 7d–90d → HDD-backed nodes (lower IOPS acceptable)
  Cold index: tweets > 90d → S3-backed or archived (rarely searched)

Benefits of time-sharding:
  1. Recency search ("recent" result_type): query only today's + yesterday's index → 2 shards, not all
  2. Date-range search: skip irrelevant time shards entirely (partition pruning)
  3. GDPR delete: delete entire day's index if user's tweet is there → O(1) deletion vs O(N) per-tweet delete
  4. TTL management: drop old index files by date without per-document GC

Near-Real-Time Indexing Pipeline

Kafka topic: tweet-events → Elasticsearch Indexer consumer group

Per-tweet indexing:
  Elasticsearch document:
  {
    "tweet_id": 8675309,
    "user_id": 42,
    "content": "Hello world! #hello",
    "hashtags": ["hello"],
    "mentions": [],
    "lang": "en",
    "created_at": "2024-08-30T10:00:00Z",
    "like_count": 0,
    "retweet_count": 0,
    "is_verified": false,
    "follower_count": 5000    -- for ranking (verified/popular users ranked higher)
  }

Refresh interval: index.refresh_interval = "5s"
  → New tweets visible to search within 5s of indexing
  → End-to-end: Kafka lag (1s) + indexer processing (2s) + refresh (5s) + replica propagation (7s) ≈ 15s

Search query example:
  GET /tweets-*/_search   ← query all time-sharded indices (or date-range filtered)
  {
    "query": {
      "bool": {
        "must": [{"match": {"content": "World Cup"}}],
        "filter": [
          {"term": {"lang": "en"}},
          {"range": {"created_at": {"gte": "now-24h"}}}
        ]
      }
    },
    "sort": [
      {"_score": "desc"},
      {"created_at": "desc"}
    ]
  }

GDPR Delete via Time Shard

Problem: user requests erasure → must delete all their tweets from search index.
         Standard: DELETE BY QUERY {user_id: X} → O(N) document scans across all shards.
         At 500M users × avg 1,000 tweets = 500B documents to potentially scan.

Time-shard solution:
  SELECT created_at FROM tweets WHERE user_id = X → list of tweet dates
  For each date: DELETE FROM tweets-{date} WHERE user_id = X (scoped to 1 time shard)
  → Still per-document, but within bounded time shards (much smaller scan)

Nuclear option (if legally required fast erasure):
  For accounts with many tweets in an old time shard:
  Mark tweets in a deletion bitmap → filter at query time (pseudo-delete)
  Nightly job: reindex shard without deleted tweets → clean shard
  Within 24 hours: tweet disappears from search permanently

2. Like Count — Redis INCR + Cassandra Flush

Scale: 57,870 likes/sec (500M users × 10 likes/day ÷ 86,400)

Option A — PostgreSQL row update:
  UPDATE tweets SET like_count = like_count + 1 WHERE tweet_id = ?
  Throughput: ~5,000 writes/sec per node (MVCC + WAL + index update)
  Nodes needed: 57,870 ÷ 5,000 = 12 PostgreSQL nodes
  Problem: hot tweets (viral posts) all update same row → single-row lock contention
           Single viral tweet at 10K likes/sec → 1 row holding back ALL 12 nodes

Option B — Redis INCR (correct approach):
  INCR like_count:{tweet_id}
  INCR is atomic, O(1), lock-free at the Redis hash slot level
  Redis throughput: ~1M INCR/sec per node (vs 5K for PostgreSQL)
  Nodes needed: 57,870 ÷ 1M = <1 node (easy!)

  Periodic flush to Cassandra (every 60 seconds):
    -- Cassandra like_counts table (separate from tweets to avoid COUNTER quirks)
    CREATE TABLE like_counts (
        tweet_id  BIGINT  PRIMARY KEY,
        count     BIGINT
    );

    Flush job:
      keys = redis.scan("like_count:*")
      for tweet_id, count in batch_mget(keys):
        cassandra.execute("UPDATE like_counts SET count = count + ? WHERE tweet_id = ?",
                          [count, tweet_id])
        redis.decr(f"like_count:{tweet_id}", count)   -- subtract flushed amount atomically
      -- Note: DECR not DELETE because new likes may arrive during flush window

  Flush math:
    57,870 likes/sec × 60s = 3.47M likes accumulated per flush interval
    Cassandra write throughput: 50K writes/sec → 3.47M ÷ 50K = 70 seconds to flush
    → Overlap between windows: use 2 flush workers alternating 60s windows

  Cache consistency:
    READ like_count: MGET like_count:{tweet_id} (Redis, real-time) + cassandra fallback if key expired
    Tweet hydration: Redis like_count + Cassandra stored count are eventually merged (TTL reconciliation)

3. Cassandra Sharding — Hot Partition Problem

Cassandra partitioning: partition key hashed via Murmur3 → assigned to a virtual node (vnode).
For the tweets table: partition key = tweet_id (Snowflake ID).

Problem with celebrity accounts:
  Katy Perry (user_id = 42) posts 20 tweets/day.
  All her tweets have tweet_ids that hash to different vnodes (good — tweet_id is globally distributed).
  But: user_tweets table partition key = user_id (42).
  → ALL of Katy Perry's 20 tweets/day write to the SAME partition on the SAME node.
  → 200M fans read her user timeline → all reads hit the same Cassandra node = HOT PARTITION.

Mitigations:

  1. Vnode replication factor (already built in to Cassandra):
     replication_factor = 3 → 3 copies of each partition across 3 nodes
     Read: any of 3 replicas can serve → distributes read load 3×

  2. Application-level read replicas (additional):
     Cassandra read consistency = LOCAL_ONE (reads from nearest replica)
     + Redis cache in front of Cassandra (celebrity timelines cached in Redis, TTL=60s)
     → 95%+ cache hit rate for celebrity timelines → Cassandra barely touched

  3. Prefix salting (for extreme cases):
     user_tweets partition key = (user_id % NUM_SALT_BUCKETS, user_id)
     NUM_SALT_BUCKETS = 10 for celebrities
     Spread one user's timeline across 10 partitions → 10× read throughput
     Cost: scatter-gather 10 partitions at read time → merge-sort

Tweets table sharding (tweet_id as PK):
  tweet_id = Snowflake → Murmur3(tweet_id) distributes uniformly across vnodes
  No hot partition risk: every tweet on a different node
  Read for single tweet: O(1) — direct hash lookup

4. Multi-Region Architecture

Twitter regions: US-East, US-West, EU-West, AP-Southeast, AP-Northeast (5 active regions)

Cassandra multi-datacenter replication:
  NetworkTopologyStrategy: replication_factor = 3 per datacenter
  Total replicas per row: 3 × 5 DCs = 15 copies globally (99.9999% durability)
  Write consistency: LOCAL_QUORUM (2 of 3 in local DC must ACK before success)
  Read consistency: LOCAL_ONE (nearest replica, lowest latency)

Why LOCAL_QUORUM for writes (not QUORUM):
  QUORUM requires acks from majority of ALL DCs → cross-region latency (100–200ms)
  LOCAL_QUORUM: acks from local DC only → < 5ms write latency
  Trade-off: if local DC fails before cross-DC replication, up to 1 write window of data may lag
  Acceptable: eventual consistency across regions; tweets appear in other regions within 1–5s

Redis multi-region:
  Timeline cache is per-region (not globally replicated):
    US user on US-East → US-East Redis
    EU user on EU-West → EU-West Redis
  Fan-out workers run per region; each region fans-out to its local Redis cluster
  Cross-region fan-out: only if user's followers span multiple regions (use Kafka cross-region replication)

Active-active vs. active-passive:
  Twitter: active-active (every region handles traffic)
  Conflict resolution: Cassandra last-write-wins (LWW) by timestamp for tweet updates
  Follow graph: eventually consistent cross-region (1–5s lag for new follows to propagate)

5. Consistency Model

OperationConsistencyMechanismAcceptable Lag
Tweet post (own timeline)Strong (immediate)Synchronous Redis ZADD before Kafka publish; user sees own tweet instantly0 — user expects to see own tweet immediately
Tweet delivery to followersEventualKafka → fan-out workers → Redis ZADD; async pipeline< 5s for normal users; celebrity tweets appear at read time
Follow / unfollowStrong (for fan-out correctness)Cassandra QUORUM write to followers table; fan-out decisions based on this data0 — unfollow must propagate before next fan-out batch
Like count displayEventualRedis INCR (real-time per node) + 60s Cassandra flush; cross-region eventual< 60s (acceptable: "47 likes" vs "48 likes" is imperceptible)
Tweet delete / unsendStrong (for visibility)Cassandra write + Redis removal + Kafka delete event; fan-out removes from caches< 5s propagation (deleted tweet must disappear quickly; safety/legal requirement)
Search indexNear-real-time (eventual)Kafka → Elasticsearch indexer; 15s end-to-end< 15s (breaking news context; 15s is acceptable)
Trending topicsEventualFlink 5-minute sliding window; Count-Min Sketch aggregation< 5 min (trends update every 5 minutes)
User profile updatesStrongPostgreSQL primary write; read replicas with 1s lag< 1s (username/avatar changes must be consistent for trust)
Push notificationsAt-least-onceKafka → notification service → FCM/APNs; retry on failureDelivered within 30s; may duplicate on retry (idempotent client handling)
Cross-region timelineEventualKafka cross-region replication; each region's Redis cache independent1–5s cross-region (EU follower sees US tweet within 5s)
Two-domain insight for Twitter:
  1. Safety domain (tweet delete, account block, unfollow) — must propagate strongly. A deleted tweet staying visible is a legal/safety violation. A block not propagating means continued harassment.
  2. Engagement domain (timeline delivery, like counts, search indexing, trending) — can be eventually consistent. 5-second fan-out lag is invisible. 60-second like count lag is imperceptible. 15-second search lag is acceptable.

Key Takeaways

  • Time-based Elasticsearch sharding: query pruning by date + O(1) GDPR erasure by dropping entire time shard — much better than per-document scatter-gather delete
  • Like count = Redis INCR + 60s Cassandra flush: 57,870 likes/sec requires Redis; PostgreSQL at 5K writes/sec would need 12 nodes and still suffers single-row lock contention on viral tweets
  • Celebrity hot partition mitigation: replication factor 3 (3× read throughput) + Redis cache in front (95%+ hit rate) = Cassandra never touched for most celebrity timeline reads
  • LOCAL_QUORUM not QUORUM: cross-region QUORUM adds 100–200ms latency; LOCAL_QUORUM gives 5ms write latency with eventual cross-region consistency (1–5s lag)
  • Follow/unfollow is strongly consistent: the one operation that must not be eventual — an unfollow must propagate before the next fan-out batch to prevent continued delivery to ex-follower

Interview Tips

  • Time-based search sharding is high-signal: "partition by tweet creation day, not tweet_id hash — this enables date-range query pruning and O(1) GDPR erasure by dropping the day's index"
  • When asked "how do you handle a viral tweet with 10M likes?" → "Redis INCR is lock-free at the hash-slot level; 10M INCR/sec on a single key across Redis cluster = no contention because INCR is atomic per slot"
  • For multi-region, distinguish CAP tradeoff: "we choose AP (availability + partition tolerance) for timelines and CP (consistency + partition tolerance) for safety operations like block and delete"
  • Push notification idempotency: "FCM guarantees at-least-once delivery; client deduplicates by notification_id (tweet_id + notification_type) so double-delivery doesn't show double push"
  • Mention Cassandra repair: "WITH replication_factor=3, Cassandra async anti-entropy repair reconciles replicas that diverged during network partitions — this is how cross-region consistency is restored after a DC outage"
