High-Level Design & Driver Location Updates

Per Lesson 1's numbers, the system must absorb ~250,000 driver location writes/sec while handling only ~116-350 ride requests/sec. That asymmetry drives every decision below: the location path is optimized purely for high-throughput writes, kept entirely separate from the transactional booking path.

1. Service Decomposition

                     ┌─────────────┐
                     │  API Gateway │
                     └──────┬──────┘
            ┌───────────────┼────────────────────┐
            ▼                ▼                    ▼
     ┌─────────────┐  ┌──────────────┐     ┌──────────────┐
     │ Rider Service│  │ Driver Service│     │ Location Svc │◄── 250K writes/sec
     └──────┬──────┘  └──────┬───────┘     └──────┬───────┘    (driver app pings)
            │                │                     │
            └───────┬────────┴──────────┬──────────┘
                     ▼                   ▼
             ┌───────────────┐   ┌───────────────┐
             │ Matching Svc  │   │  Pricing Svc  │
             │ (Lesson 3)    │   │  (Lesson 4)   │
             └───────┬───────┘   └───────────────┘
                     ▼
             ┌───────────────┐
             │  Trip Service │──► Trip DB (durable, ~18TB/5yr, Lesson 1)
             └───────────────┘

Rider/Driver services handle profile and app-session concerns. Location Service is the high-write-throughput path. Matching and Pricing are read-heavy consumers of live location + demand signals. Trip Service is the durable system-of-record, written once per ride rather than once per ping.

2. Driver Location Ingestion

OptionTradeoff
HTTP request per pingSimple, but connection setup overhead (TLS handshake) at 250K/sec is wasteful — most of each request is protocol overhead, not payload
Persistent WebSocket per driverOne long-lived connection per online driver (1M concurrent); pings become tiny frames on an already-open socket — chosen approach

Each driver's app holds one WebSocket to a Location Service instance (behind a connection-aware load balancer, so reconnects are cheap). A ping is a small frame: {driverId, lat, lng, ts}, roughly 50 bytes. The same channel pushes ride offers and cancellations down to the driver — no separate push-notification path needed while the socket is open.

💡 Interview signal: Naming the connection-count problem (1M concurrent sockets) and how it's sharded across Location Service instances (consistent hashing on driverId) shows you're thinking about the ingestion tier as infrastructure, not just an API endpoint.

3. Storing Live Location: Building on Chapter 28

Chapter 28's Lesson 3 previewed this exact case: geohash the driver's (lat, lng) to ~1km precision, and store it in Redis as GEOADD driver_locations {geohash} {driverId} (Redis's native geo commands are a sorted-set-backed geohash index). Each write:

1. Driver ping arrives over WebSocket → Location Service
2. GEOADD driver_locations lng lat driverId      // O(log N), ~250K/sec aggregate
3. SET driver:{driverId}:meta {status, lat, lng, ts} EX 15   // TTL — stale if no ping in 15s
4. PUBLISH driver_updates:{geohash_cell} {driverId, lat, lng} // for riders actively tracking a trip

The TTL matters more here than in Chapter 28: a driver who goes offline without explicitly signaling it (app killed, phone dies) must disappear from nearby-driver queries automatically, not linger as a stale, unreachable match candidate. The pub/sub channel per geohash cell is what powers the rider-facing "your driver is 2 minutes away" live map — riders subscribe to the cell(s) their driver is currently in.

💡 Interview signal: If you covered Chapter 28, say so explicitly: "this is the moving-entity variant of the QuadTree design — same nearby-search problem, but the index must tolerate constant churn, hence Redis geohash + TTL over a tree structure that's expensive to rebalance under high write rates."

4. Separating Hot Path from Analytics/History

The Redis geo-index above is a cache of current position only — it is overwritten on every ping and holds no history. Trip receipts, ETA-accuracy analysis, and driver-earnings dashboards need historical location data, but that must not sit on the write-critical path:

Location Service ──► Kafka topic "driver_pings" (fire-and-forget, async)
                                    │
                                    ▼
                     Stream consumer batches + compresses
                                    │
                                    ▼
                 Cold storage (S3/HDFS): route polyline per trip, ~2KB/trip
                                    │
                                    ▼
                   Batch jobs: ETA-model training, surge analytics (Lesson 4)

Because this path is async and decoupled via Kafka, a slowdown in the analytics pipeline never backs up into the live ping-ingest path — the two have independent failure domains, which matches the availability-over-consistency NFR from Lesson 1.

Key Takeaways

  • Service boundaries follow the load profile: Location Service is a write-optimized tier, entirely separate from the transactional Trip Service
  • Persistent WebSocket connections amortize protocol overhead across 250K/sec of tiny location pings
  • Chapter 28's geohash + Redis pattern extends naturally to moving entities by adding a TTL (staleness) and pub/sub (live tracking) on top
  • Live location (Redis, overwritten) and location history (Kafka → cold storage, appended) are two different systems serving two different consistency/durability needs

Interview Tips

  • Draw the write path (ping → Location Service → Redis) separately from the read path (matching/rider tracking) — conflating them is a common mistake
  • Justify WebSocket over HTTP with the connection-overhead argument, not just "it's faster"
  • Explicitly connect back to prior location-indexing knowledge if you have it — interviewers reward recognizing a known pattern in a new context
  • Call out the TTL/staleness mechanism unprompted — "what if a driver's app crashes?" is a near-guaranteed follow-up
