Core Components

Upload Service (Write Path)

Handles post creation metadata. Issues S3 presigned PUT URLs — clients upload media bytes directly to S3, bypassing the Upload Service entirely. This is critical: 14.4 GB/s of upload traffic never touches your application servers.

Media Processing Workers

Kafka consumers triggered by S3 events. Resize photos into 4 WebP variants, transcode videos to HLS (360p/720p/1080p), run content moderation (PhotoDNA for CSAM, ML nudity classifier), and compute perceptual hashes for deduplication. All processing is async — the user's post is "live" optimistically while workers finish.

Feed Service (Read Path)

The hottest service in the system. Reads from a Redis sorted set per user (pre-populated by the fan-out worker). For celebrity followees (>5M followers), merges their recent posts at read time rather than pre-fanning. Returns hydrated post objects with CDN URLs.

Social Graph Service

Manages the asymmetric follow graph — 2B users × 500 avg following = 1 trillion edges. Stored in Cassandra with dual-table sharding: one table by follower_id ("who do I follow?"), one by followee_id ("who follows me?"). Both traversals must be O(1) for fan-out and notification.

CDN (Multi-tier CloudFront)

Three tiers: 300+ edge PoPs → 12 regional Origin Shields → S3 origin. With content-addressed immutable URLs (cdn.instagram.com/v/{media_id}/{variant}.webp), Cache-Control is max-age=31536000, immutable. CDN hit rate: >99%. Origin sees <1% of 868K req/sec.

Stories Service

Redis-first: metadata stored in Redis HASH with 86400s EXPIRE. S3 lifecycle rule deletes media after 25 hours. View receipts in Redis SET per story. No GC job needed — TTL is the expiry mechanism.

Explore Service

Two-stage ML ranking: offline FAISS ANN retrieval produces 1,000 candidates per user (refreshed every 4 hours), stored in Redis. Online neural ranker (100ms budget) scores candidates using real-time signals (engagement velocity, session context). Viral content injected via Flink within 10 minutes of going trending.

Core API Endpoints

# Upload
POST   /api/v1/media/upload/init     → { media_id, s3_presigned_url, expires_in: 3600 }
POST   /api/v1/posts                 → { post_id } (after media confirmed ready in S3)
POST   /api/v1/stories               → { story_id }

# Feed & Discovery
GET    /api/v1/feed?cursor=&limit=12 → { posts[], next_cursor }
GET    /api/v1/explore?cursor=       → { posts[], next_cursor }
GET    /api/v1/users/{id}/posts      → profile grid (paginated)

# Social
POST   /api/v1/follow/{user_id}
DELETE /api/v1/follow/{user_id}
POST   /api/v1/posts/{id}/like
POST   /api/v1/posts/{id}/comments   → { comment_id }

# Stories
GET    /api/v1/stories/feed          → { story_rings[] } ordered by recency, unseen first
GET    /api/v1/stories/{id}          → { media_url, expires_at }
POST   /api/v1/stories/{id}/view     → records view receipt

Request Flow: Photo Upload

1. App → POST /api/v1/media/upload/init
   Response: { media_id (Snowflake), s3_presigned_url, expires_in: 3600 }

2. App → PUT {s3_presigned_url}  ← direct to S3, bypasses ALL Instagram servers
   (5 MB photo payload never touches your API)

3. S3 → EventBridge → Kafka "media.uploaded" { media_id, user_id, s3_key }

4. App → POST /api/v1/posts { caption, media_ids: [media_id], hashtags, location }
   → Post Service: validate media ready, create post_id, write to Cassandra
   → Publish Kafka "post.created" { post_id, user_id, media_ids, timestamp }

5. Kafka consumers (async, parallel):
   ├── Media Processor  → resize, compress, WebP variants, content mod, pHash
   ├── Fan-out Worker   → push post_id to followers' Redis feed caches
   ├── Search Indexer   → index caption + hashtags in Elasticsearch
   └── Notification Svc → notify @mentioned users

6. Response to app: 201 Created { post_id, permalink }
   ← App shows post immediately (optimistic UI) while workers run async

Request Flow: Read Home Feed

1. App → GET /api/v1/feed?cursor=null&limit=12

2. Feed Service:
   a. Redis ZREVRANGE feed:{user_id} 0 11 WITHSCORES
      → Returns [(post_id, timestamp_score), ...]  ← sub-ms

   b. For celebrity followees (>5M followers) not pre-fanned:
      ZREVRANGE user_posts:{celeb_id} 0 4  per celebrity
      In-memory k-way merge with pre-computed feed  ← adds ~5ms per celebrity

   c. Redis MGET post:{id1} post:{id2} ... post:{id12}  ← batch hydration
      → Returns cached post metadata JSON

   d. Construct CDN URLs (computed, not stored):
      "https://cdn.instagram.com/v/{media_id}/medium.webp"

   e. Attach engagement: SISMEMBER post_likers:{id} {user_id} per post
      (did the viewing user like this post?)

3. Response: 12 posts with CDN URLs
   App fetches media images directly from CDN (never through your API)
Latency breakdown: Redis ZREVRANGE ~1ms + celebrity merge ~5ms + MGET hydration ~3ms = ~9ms total for Feed Service. The 300ms p99 budget is dominated by CDN image fetch (~80ms at edge) and client render, not backend processing.

Technology Choices

ComponentTechnologyWhy
Post storageCassandraHigh write throughput (1,157 uploads/sec), time-ordered per user, linear scale-out, RF=3
Feed cacheRedis Sorted SetO(log N) insert, O(1) range read, score = ranked timestamp, native TTL
Follow graphCassandra (dual-shard)1T edges, directional O(1) queries both ways, high write throughput
User profilesPostgreSQLStructured, rich queries needed (e.g., username uniqueness), moderate scale
Media storageS3 + multi-tier CDNPetabyte scale, immutable objects, 11-nine durability, global delivery
Video transcodingFFmpeg + GPU clusterIndustry standard, hardware H.264/HEVC acceleration, auto-scaling spot instances
StoriesRedis (TTL-native) + S3 lifecycleEXPIRE matches 24h product requirement exactly; no GC job
Explore rankingFAISS ANN + neural rankerBillion-scale candidate retrieval offline; fast online scoring per request
Fan-out pipelineKafka (2,000 partitions)Durable, parallel, replay on failure, back-pressure handling
Like countingRedis INCR → Cassandra flush48,600 likes/sec; O(1) atomic increment; 60s batch flush
SearchElasticsearchFull-text, hashtag, geospatial; near-real-time indexing

Key Takeaways

  • The write path (upload → S3 → Kafka → workers) is entirely async after the 201 response — never block the user on processing
  • The read path (Feed Service → Redis → CDN) is the critical path; keep it under 10ms backend latency
  • Kafka decouples producers from consumers — a fan-out worker crash doesn't affect the upload API
  • Content-addressed CDN URLs (/v/{media_id}/{variant}) allow max-age=31536000 — aggressive caching with zero staleness risk
  • Cassandra's dual-table sharding for the follow graph is non-obvious — be ready to explain why a single table doesn't work
