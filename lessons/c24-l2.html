Deep Dive — Distributed Rate Limiting

lesson
⏱ 10 min
📖 Chapter 24, Lesson 3

🎯 Learning Objectives

  • Identify and resolve the race condition in distributed rate limiting: why two API nodes checking simultaneously can both see "under limit" and both allow a request that should be rejected
  • Design Redis Cluster sharding for rate limit counters with consistent hashing to prevent hot-shard problems
  • Compare centralized Redis vs. local in-memory counters with periodic sync, quantifying the accuracy-latency tradeoff at each scale tier
  • Build a resilient rate limiter that fails open gracefully when Redis is unavailable, with circuit-breaker protection

Deep Dive — Distributed Rate Limiting

1. The Race Condition Problem

Rate limiters run on multiple nodes. Without careful design, two nodes can both think a request is allowed when combined they exceed the limit:


// RACE CONDITION: user's limit = 100 req/min, current count = 99

// Timeline (two API nodes, centralized Redis, no Lua):
// T=0: Node A reads count = 99  → 99 < 100 → ALLOW
// T=0: Node B reads count = 99  → 99 < 100 → ALLOW  ← reads BEFORE A's write!
// T=1: Node A writes count = 100
// T=2: Node B writes count = 100  ← overwrites! (should be 101)
// Result: 2 requests allowed when only 1 slot remained → limit violated

// WHY THIS HAPPENS: Redis GET and INCR are separate operations
// Between GET (read) and INCR (write), another node can interleave

// SOLUTION 1: Redis Lua script (eliminates race — all ops atomic server-side)
// SOLUTION 2: Redis INCR directly (don't GET first — check count AFTER increment)
local count = redis.call('INCR', key)
if count == 1 then redis.call('EXPIRE', key, window_secs) end
if count > limit then
    redis.call('DECR', key)  -- rollback (but this is also not atomic with above!)
    return REJECT
end
return ALLOW
-- Problem: INCR → check → DECR still not atomic as a unit without Lua

// CORRECT: Single Lua script (previous lesson's approach is right)
// The GET-GET-weighted-math-INCR-EXPIRE in one Lua script = no race possible

2. Redis Cluster Sharding

At 500K checks/sec, a single Redis node (1M ops/sec max) would operate at 50% capacity — too close to the limit. Redis Cluster distributes keys across nodes automatically using hash slots.


// Redis Cluster: 16,384 hash slots distributed across N nodes
// Key → CRC16(key) % 16384 → hash slot → node

// 10-node Redis Cluster:
// Node 1: slots 0–1637      (keys hashing to these slots)
// Node 2: slots 1638–3275
// ...
// Node 10: slots 14745–16383

// Rate limit key routing:
// KEYS[1] = "ratelimit:user:u_abc123:1725000060"
// CRC16("ratelimit:user:u_abc123:1725000060") % 16384 = 7,423
// → routed to Node 5

// Each node handles: 500K req/sec ÷ 10 nodes = 50K QPS/node ✅ (20× headroom)
⚠️ Hot Shard Problem with Redis Cluster: Redis Cluster routes by key hash. If one user generates enormous traffic (e.g., a high-volume enterprise customer), all their rate limit keys hash to the same node — that node becomes a hot shard. Mitigation: hash tags to spread across nodes, or add local counters (Section 3) to absorb traffic before hitting Redis.

2.1 Hash Tags for Multi-Key Atomic Operations


// Redis Cluster PROBLEM: Lua scripts can only touch keys on the SAME node
// (cross-slot Lua is forbidden in Redis Cluster)

// Sliding Window Counter uses 2 keys: current + previous window
// These hash to DIFFERENT nodes → Lua script fails!

// SOLUTION: Redis Hash Tags force multiple keys to the same slot
// Hash tag = the part inside {}: only {this part} is hashed

// Without hash tag:
"ratelimit:user:u_abc123:1725000060"  → may be on Node 3
"ratelimit:user:u_abc123:1725000000"  → may be on Node 7 ← DIFFERENT NODE!

// With hash tag (user_id is the tag):
"ratelimit:{u_abc123}:1725000060"  → hashed as "u_abc123" → always same node
"ratelimit:{u_abc123}:1725000000"  → hashed as "u_abc123" → always same node ✅

// Now the Lua script can touch both keys — they're guaranteed to be on the same node

3. Centralized vs. Local Counters

The central architectural decision in distributed rate limiting: where does the counter live?

StrategyAccuracyLatency AddedScalabilityBest For
Centralized Redis~99% (±1% due to sliding window approximation)0.5–2ms (Redis round-trip)Up to ~5M QPS with Redis ClusterGeneral-purpose; most production APIs
Local in-memory + periodic sync~90% (up to 10% overage possible)0ms (memory read)Unlimited (no shared state)Very high-throughput (CDN, edge nodes) where Redis latency is unacceptable
Hybrid (local + Redis)~95% (5% overage)0ms (hot path) + async Redis syncScales to 10M+ QPSCloudflare Workers, large-scale ad serving

3.1 Local Counter + Periodic Sync (Cloudflare Pattern)


// Each API node keeps a local in-memory counter.
// Every 100ms, all nodes sync their local counts to Redis.

// Local state per node (in-memory HashMap):
localCounters = {
  "ratelimit:{u_abc123}:1725000060": 15,  // this node processed 15 requests from u_abc123
  "ratelimit:{u_abc123}:1725000120": 3,
  ...
}

// Every 100ms (background thread):
for key, localDelta in localCounters:
    globalCount = redis.incrby(key, localDelta)  // add this node's delta to global total
    localCounters[key] = 0                         // reset local counter
    if globalCount > limit:
        localLimitReached.add(key)                 // mark as over limit

// Hot path (per request, 0ms):
if key in localLimitReached:
    return REJECT
localCounters[key] += 1
return ALLOW

// TRADEOFF:
// If limit=100 and 10 nodes each have local count=10 before sync:
// Each node thinks global count=10 (old sync value) → all ALLOW
// After sync: global count = 100 → limit reached
// During 100ms between syncs: up to 10× overage possible (10 nodes × 10 local)
// Acceptable for CDN rate limiting; NOT acceptable for payment APIs

4. Multi-Region Rate Limiting


// Problem: user in US makes 60 requests via US datacenter.
// Same user (via VPN) makes 60 requests via EU datacenter.
// Both US-Redis and EU-Redis see count=60 → both ALLOW.
// Actual count = 120 → 20% over limit of 100.

// Option A: Cross-region Redis sync (strong consistency)
// US Redis ──CRDT sync──▶ EU Redis (Conflict-free Replicated Data Type)
// Both regions see eventually consistent count
// Latency: 80–150ms cross-region → unacceptable in request hot path
// VERDICT: ❌ Too slow for synchronous check

// Option B: Per-region limit (recommended)
// US: limit 100/min (user gets 100 in US)
// EU: limit 100/min (user gets 100 in EU)
// Global effective limit: 100/region × N_regions = 100 × 3 = 300/min
// VERDICT: ✅ Simple, no cross-region latency, minor overage at region-level

// Option C: Home region routing
// User's account has a "home region" (where they registered)
// All rate limit checks route to home-region Redis (async via API routing)
// Cross-region requests add 80ms latency for rate check → too slow
// VERDICT: ❌ Adds latency for users far from home region

// Production choice: Option B (per-region limits)
// Set per-region limit = global_limit / num_regions × 1.5 (buffer for skewed traffic)

5. Failure Modes and Resilience

5.1 Redis Failure — Fail Open


// What happens when Redis goes down?

// Option A: Fail closed (reject all requests)
// Every request returns 429 while Redis is down
// VERDICT: ❌ Catastrophic — Redis outage kills entire API (worse than rate limit bypass)

// Option B: Fail open (allow all requests)
// Every request allowed while Redis is down
// VERDICT: ✅ Correct — minor abuse during outage is far less harmful than API downtime

// Implementation: circuit breaker around Redis call
rateLimitResult = circuitBreaker.execute(
    primary=lambda: redis_lua_check(key, limit, window),
    fallback=lambda: {allowed: True, remaining: -1}  // fail open
)

// Circuit breaker states:
// CLOSED (normal): all Redis calls go through
// OPEN (Redis down): all calls use fallback (fail open)
// HALF-OPEN (testing): let 1% of calls through to test Redis recovery

// Alert: rate limiter in fallback mode → PagerDuty page immediately

5.2 Redis Node Failure in Cluster


// Redis Cluster: each node has 1 replica (async replication)
// On primary failure: replica promoted in ~10–30 seconds

// During failover window (30 seconds):
// Keys on failed node return errors → circuit breaker activates → fail open
// After failover: new primary has slightly stale data (async replication lag)
// → may allow a small number of extra requests for users on that shard
// VERDICT: Acceptable — 30-second window, minor overage, self-healing

// Configuration:
// min-slaves-to-write = 1     → don't write if replica disconnected
// min-slaves-max-lag = 10     → replica must be within 10 seconds of primary
// This ensures rate limit writes reach at least 1 replica before acknowledging

7. Complete Consistency Model

DomainStrategyConsistencyWhy
Counter increments (single region)Redis Lua script (Sliding Window Counter)Strong within region (~1% overage from algorithm)Lua = atomic; no race conditions within a single Redis node/shard
Counter increments (multi-region)Per-region independent countersEventual across regions (~10–20% cross-region overage)Cross-region sync latency (80–150ms) is unacceptable in hot path
Rule configurationDB → Redis → in-memory (30s TTL each)Eventual (up to 30s lag)Emergency limit changes (DDoS response) propagate within 30s — acceptable
Redis Cluster replicationAsync primary → replicaEventual (seconds during failover)Synchronous replication would double write latency; async lag is tiny in practice
Audit logKafka → ClickHouse (async)Eventual (seconds to minutes)Audit is for analytics, not enforcement; async write keeps hot path clean
💡 Two-Domain Insight: Rate limiting has two fundamentally different consistency domains. Counter enforcement must be near-strongly-consistent within a region (Lua atomicity handles this) but can tolerate multi-region lag. Rule configuration can tolerate 30-second staleness — ops teams don't need sub-second propagation for limit changes. Mixing these into a single strong-consistency model would over-engineer both.

Key Takeaways

  • Race conditions require Lua, not just INCR: Two nodes reading count=99 simultaneously both allow the 100th request. Only Lua scripts (or Redis INCR-then-check pattern) prevent this.
  • Hash tags are mandatory for multi-key Lua in Redis Cluster: The current and previous window keys must share a hash tag ({user_id}) to guarantee they land on the same node — otherwise cross-slot Lua fails.
  • Fail open is always the right answer for Redis failure: A rate limiter outage that blocks all traffic is catastrophically worse than allowing some excess requests. Circuit breaker + fail-open is the correct resilience pattern.
  • Per-region limits eliminate cross-region latency: Global limit consistency requires cross-region coordination (80–150ms). Per-region limits add 0ms at the cost of higher effective global limit. This tradeoff is almost always correct.
  • Local counters unlock CDN-scale rate limiting: At 10M+ QPS, Redis coordination becomes the bottleneck. Cloudflare and similar CDNs use local in-memory counters with periodic Redis sync, accepting ~10% overage.
  • Rate limiting ≠ DDoS protection: Rate limiters work at Layer 7. Volumetric DDoS attacks (Layer 3/4) bypass them entirely. Understand this boundary — it comes up in every senior FAANG interview on this topic.

Interview Tips

  • The race condition question is a gimme — answer it precisely: "Two nodes read count=99 simultaneously, both see it as < limit, both ALLOW. We prevent this with a Redis Lua script that executes GET-INCR atomically on the Redis server — no client-side race possible."
  • Bring up hash tags unprompted if using Redis Cluster: "Since we're using Sliding Window Counter with two keys (current + previous window), I need Redis hash tags — ratelimit:{user_id}:window1 and ratelimit:{user_id}:window2 — to guarantee both keys land on the same node so my Lua script can touch them atomically." This is an advanced detail that distinguishes strong candidates.
  • Fail open is a values question: When asked "what happens if Redis goes down?", the answer reveals how you prioritize availability vs. correctness. Say: "I fail open — the rate limiter uses a circuit breaker and returns 'allowed' when Redis is unavailable. A brief window of rate-limit bypass is far less harmful than returning 429 to all users."
  • Draw the 3-tier scale: Redis → Local → CDN: Show that the architecture changes at each scale tier. At 10K QPS: single Redis. At 500K QPS: Redis Cluster. At 10M QPS: local counters. This progression shows you understand the limits of each approach.
  • State the per-region overage explicitly: "With per-region limits, a user could theoretically get 300/min across 3 regions against a 100/min limit. This is a known tradeoff — we accept it to avoid 150ms cross-region latency on every request."
