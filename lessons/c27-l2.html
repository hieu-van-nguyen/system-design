Deep Dive — Feed Publishing & Fan-out

Lesson 1 showed that pushing every post to every follower costs ~1.7M fan-out writes/sec. Lesson 2 introduced the hybrid model as the fix. This lesson designs the actual fan-out pipeline: how a post gets from createPost() into followers' feed caches, and exactly where the celebrity threshold kicks in.

1. The Celebrity Problem

A post from a user with 300 friends triggers 300 fan-out writes — trivial. A post from a celebrity account with 100M followers triggers 100M fan-out writes from a single post. At Facebook's post rate, a handful of these accounts posting during peak hours can dwarf the fan-out load generated by the other 999,999,000+ users combined.

ProblemWhy push-only fails
Write amplificationOne post → tens of millions of feed-cache writes, all triggered synchronously by a single event
Hot key contentionThe celebrity's fan-out job floods the queue and worker pool, delaying fan-out for ordinary users' posts
Wasted workMany followers of a celebrity never open the app before the post is stale/irrelevant — precomputing their feed entry may be wasted effort

2. Hybrid Fan-out Threshold

on createPost(post):
  followerCount = SocialGraphService.getFollowerCount(post.authorId)

  if followerCount < FANOUT_THRESHOLD:      // e.g., 10,000 followers
      enqueue(FanoutJob(post))               // push path — Lesson 2's default
  else:
      markAsCelebrityPost(post)              // no fan-out write at all
      // Instead: every getFeed() call merges in recent posts from
      // celebrities the user follows, at read time (bounded fan-in,
      // since a user follows far fewer celebrities than they have friends)

This flips the cost model for celebrity posts from fan-out (O(followers)) to fan-in at read time (O(celebrities followed)) — and the latter is small and bounded per user, unlike the former.

💡 Interview signal: State the threshold as a tunable config (e.g., 10K followers), not a hardcoded constant — and mention it can be set per-account based on observed post frequency × follower count, not just raw follower count.

3. Fan-out Worker Pipeline

Post Service ──▶ Message Queue (Kafka/SQS) ──▶ Fan-out Worker Pool
                     topic: post-created                │
                                                          ▼
                                          for each follower batch (e.g., 1,000 at a time):
                                            ZADD feed:{followerId} score postId
                                          // batched pipeline writes, not one round-trip per follower

Queue partitioning: partition by authorId
  // Guarantees a single non-celebrity author's posts fan out in order,
  // and isolates one hot author's backlog from delaying unrelated authors.
  • Workers pull follower lists from the Social Graph Service in pages, not all at once, to bound memory per job
  • Feed-cache writes are pipelined/batched (e.g., Redis MULTI/pipeline) rather than one round trip per follower
  • Failed batches are retried idempotently — ZADD is naturally idempotent, so at-least-once delivery from the queue is safe

4. Worker Pool Sizing

Non-celebrity fan-out writes/sec ≈ 1.7M (from Lesson 1, upper bound if unfiltered)
  // In practice, after excluding celebrity posts (a tiny fraction of posts,
  // but the source of the largest fan-out fanout), the *actual* push volume
  // is far lower — but we still provision for spikes.

If one worker sustains ~20,000 feed-cache writes/sec (batched pipeline calls):
  Workers needed = 1,700,000 / 20,000 ≈ 85 workers (steady state)
  Provision 2-3× for peak/retry headroom ≈ 200-250 workers

// Horizontally scalable: add workers, add queue partitions — no
// coordination needed between workers since each just drains its partition.

5. Handling Late/Out-of-Order Fan-out

  • If a user opens the app mid-fan-out, they may briefly see an incomplete feed — acceptable given the eventual-consistency NFR from Lesson 1
  • Feed Service always merges in the celebrity fan-in at read time regardless of push-fan-out progress, so celebrity content is never delayed by queue backlog

Key Takeaways

  • A fixed follower-count threshold splits authors into push (fan-out-on-write) and pull (fan-in-on-read) paths
  • The celebrity path turns an O(followers) write problem into an O(celebrities-followed) read problem — bounded either way
  • Partition the fan-out queue by author ID to isolate one hot author's backlog from delaying everyone else
  • Batch/pipeline feed-cache writes per job instead of one write per follower — this is what makes ~85-250 workers sufficient instead of thousands
  • Idempotent writes (ZADD) make at-least-once queue delivery safe without extra dedup logic

Interview Tips

  • Introduce the celebrity problem with a concrete number (100M followers) before proposing the hybrid threshold — motivate the design, don't just assert it
  • Be ready to size the worker pool from first principles (writes/sec ÷ writes/sec-per-worker), not just say "add more workers"
  • Explain why partitioning the queue by author ID (not round-robin) matters — it's an easy follow-up question
  • Mention idempotency explicitly when discussing queue-based delivery — interviewers probe for at-least-once vs. exactly-once awareness
