🎯 Learning Objectives

  • Justify WebSocket over long-poll and SSE for a chat system using latency, overhead, and bidirectionality arguments

Why WebSocket — Not Long-Poll or SSE

ProtocolLatencyOverheadBidirectionalVerdict
WebSocket2–5ms frame overhead2-byte frame header per messageYes — single TCP connection, both directions✅ Use this
Long-poll30–60ms (new HTTP conn per message)Full HTTP headers (~800 bytes) per responseNo — one direction per connection❌ 400× header overhead
SSE (Server-Sent Events)5–10msSmall (persistent HTTP/2 stream)No — server→client only; client sends via POST❌ Requires separate HTTP for client→server
WebSocket math: At 231K messages/sec, long-poll with 800-byte HTTP headers adds 231K × 800B = 185 MB/sec of pure header overhead per direction. WebSocket at 2 bytes/frame = 462 KB/sec. WebSocket is 400× more bandwidth-efficient for chat.

Chat Server Internal Design

Each chat server is a single-process, event-driven server (similar to Erlang's actor model):

Connection acceptance:
  io_uring (Linux) / kqueue (BSD/macOS) for async I/O — no thread-per-connection
  1 chat server handles 45,000 connections with 4 worker threads

Per-connection state (stored in memory, NOT in Redis):
  { user_id, device_id, last_heartbeat, conv_subscriptions[], ws_frame_buffer }

Message processing pipeline (per incoming frame):
  1. Parse WebSocket frame (2–10 byte header + payload)
  2. Authenticate (JWT validation, cached for connection lifetime)
  3. Assign Snowflake message_id (local atomic counter per server + server_id bits)
  4. ACK to sender: { message_id, status: "SENT" }  ← returned in < 5ms
  5. Publish to Kafka topic "messages" (key = conversation_id)
     → Kafka handles durability, fan-out, retry — chat server is fire-and-forget after publish
  6. Kafka consumer (on same server or separate) delivers to connected recipients

Message Send Flow — Online Recipient (7 Steps)

Alice sends "Hey Bob" from her iPhone:

Step 1 — Client sends WebSocket frame to Alice's Chat Server (S1):
  Frame: { type:"message", client_msg_id:"client-uuid", conv_id:"c789", text:"Hey Bob" }
  client_msg_id: client-generated UUID for dedup/idempotency

Step 2 — S1 assigns Snowflake message_id and ACKs Alice immediately:
  message_id = Snowflake(timestamp=now, server_id=1, seq=42)
  S1 → Alice: { type:"ack", client_msg_id:"client-uuid", message_id:8675309, status:"SENT" }
  Alice's UI: shows single grey tick ✓ (SENT)
  Total time: < 5ms

Step 3 — S1 publishes to Kafka (fire-and-forget after ACK):
  Topic: "messages", Partition: hash(conv_id) % 2000
  Payload: { message_id, conv_id, sender_id, text, sent_at }
  Kafka acknowledges to S1 within 1ms (producer acks=1)

Step 4 — Kafka consumer reads message:
  Consumer group "delivery-workers" on each chat server reads messages for their partitions

Step 5 — Delivery worker looks up Bob's connection:
  HGET connection_registry:{bob_user_id} → "server_id:7"
  Bob's WebSocket is on Chat Server 7

Step 6 — Forward to Bob's Chat Server (S7):
  S7 receives delivery task (via Redis pub/sub or direct internal HTTP)
  S7 pushes to Bob's WebSocket: { type:"message", message_id:8675309, ... }
  Bob's phone receives message
  Total latency: Step 1→6 ≈ 30–50ms (same region)

Step 7 — Bob's client sends DELIVERED receipt:
  Bob's app → S7: { type:"receipt", message_id:8675309, status:"DELIVERED" }
  S7 routes receipt back to Alice's S1 (via connection registry)
  S1 → Alice: { type:"receipt_update", message_id:8675309, status:"DELIVERED" }
  Alice's UI: shows double grey tick ✓✓ (DELIVERED)

Message Delivery Flow — Offline Recipient (5 Steps)

Bob's phone is off. Alice sends "Hey Bob":

Step 1–3: Same as online flow (Alice gets SENT ACK in < 5ms)

Step 4 — Delivery worker checks Bob's connection registry:
  HGET connection_registry:{bob_user_id} → (nil)  ← no TTL entry = offline

Step 5 — Publish to Notification Service via Kafka:
  Topic: "push-notifications"
  Payload: { recipient_user_id: bob, message_preview: "Hey Bob", badge_count: ++, ... }
  Notification Service → APNs (iOS) / FCM (Android)
  Bob's phone wakes from background:
    a. Opens WebSocket to Chat Server
    b. Sends sync request: { last_seen_message_id: 8675000 }
    c. Server fetches missed messages from Cassandra: SELECT ... WHERE id > 8675000
    d. Delivers all missed messages in order
    e. Bob's app sends DELIVERED receipts for all

Message preview in push: "Alice: Hey Bob" (truncated for privacy; full E2E encryption would send "New message")

Media Message Flow

Alice wants to send a photo:

1. Alice: GET /v1/media/upload-url?type=image/jpeg&size=204800
   Server: generate presigned S3 PUT URL (15 min TTL)

2. Alice: PUT https://s3.aws.../media/uuid-photo.jpg?X-Amz-...
   Uploads 200 KB directly to S3 — bypasses all chat servers

3. Alice: sends WebSocket message frame:
   { type:"message", conv_id:"c789", media_url:"https://cdn.fb.com/media/uuid-photo.jpg",
     media_type:"image", width:1280, height:720, thumbnail_b64:"..." }
   (thumbnail encoded inline as base64 so Bob sees preview before CDN loads)

4. Delivery: same as text message flow
   Bob's client: loads thumbnail from frame immediately; fetches full image from CDN URL

Technology Choices

ComponentChoiceWhy
Real-time transportWebSocket (WSS)Bidirectional, 400× less overhead than long-poll at 231K msg/sec
Chat server I/Oio_uring (Linux kernel 5.1+)Zero-copy async I/O; 10× throughput vs. epoll for small frames
Message busKafka (2,000 partitions)Durable, replayable, decouples chat servers from storage/notification/presence
Message storageCassandraWrite-heavy (231K/sec), wide-row for conversation history, LSM-tree for fast appends
Connection registryRedis (cluster, 3 shards)O(1) lookup user_id → chat_server_id; TTL-based expiry for disconnection
Media storageS3 + CloudFront CDNUnlimited scale; presigned URLs bypass chat servers; CDN for global delivery
Push notificationsFCM (Android) + APNs (iOS)Platform-standard; 99.9% delivery guarantee; background app wake
PresenceRedis (with TTL) + Kafka heartbeat aggregationRedis TTL for O(1) online check; Kafka for batched heartbeat writes (reduces 100M/sec → 10M/sec)
API (stateless)HTTP/2 RESTConversation list, history, search, auth — don't need persistent connection

Key Takeaways

  • WebSocket is 400× more efficient than long-poll for chat — 2-byte frames vs. 800-byte HTTP headers at 231K msg/sec
  • Chat servers are stateful (connection state in memory) + stateless for message routing — sticky L4 load balancing keeps user on same server; routing across servers via connection registry
  • Kafka decouples durability from delivery: ACK sender after Kafka publish (1ms), not after Cassandra write (5–10ms) — users see SENT immediately
  • Two delivery paths: online (WebSocket push via connection registry, 30–50ms) vs. offline (Kafka → push notification → app wake → Cassandra fetch)
  • Media never touches chat servers — 69 GB/s goes directly S3; chat server only carries the CDN URL in a tiny message frame

Interview Tips

  • Draw the Kafka bus between chat servers and Cassandra explicitly — interviewers probe "what if the Cassandra write is slow?" → answer: "Kafka absorbs backpressure; ACK happens after Kafka publish, not Cassandra write"
  • When asked about server failure: "WebSocket connections drop; L4 LB detects failure and reroutes; client reconnects in < 1s; missed messages fetched from Cassandra by message_id cursor"
  • io_uring is a high-signal detail for chat: "Linux io_uring lets one thread process 1M+ small I/O operations/sec — critical when each chat server has 45K connections sending tiny frames"
  • Always mention the client_msg_id for idempotency: "if the network drops after publish but before ACK, client retries with same client_msg_id — server deduplicates by checking if message_id already exists"
